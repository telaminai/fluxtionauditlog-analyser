### 1.5 Per-run cost split (INFERRED)

The transcripts are not committed [L, B], so per-request token buckets cannot be checked. Assume an over-100k
request averages ≈ 110k–120k tokens of mostly cache-read input ($0.05/M → ≈ $0.006) and an under-100k request
≈ 60k ($0.01/M → ≈ $0.0006). Baseline: 102 × $0.006 ≈ $0.61 and 350 × $0.0006 ≈ $0.21, so **input on over-100k
requests was ≈ 40% of the $1.49 total**. The remaining ≈ 60% is under-100k input (≈ $0.21, ≈ 14%), output and
cache writes. Moving every such request under
the tier would save **an estimated ≈ 30–35%** of the total (≈ 0.8 × $0.61). This is an estimate, not a bound:
tiering of output and cache-write tokens is not modelled, and including it could raise the figure. The same
method on the first ladder gives ≈ 36% [D, INFERRED]. L0 replaces this paragraph with a measurement.

## 2. The principle — Higgins lowering

The owner's direction, verbatim:

> "In reality the skill should be using the analyser to filter etc access to the audit log. Or pass a text log
> through the binary parser so smaller logs are sent to the cloud"

> "This is a huge saving. Effectively partial evaluation and greedy algorithms across multiple processes and
> activities. Design and diagnostic are two separate activities that can be combined"

> "This is the same idea as Higgins lowering: if a set of facts can be stated at a higher level then move it there
> and then reuse cheaply"

Stated so it can be built against:

1. **Lower each fact to the highest level at which it can be stated**, and compute it locally — in the compiler,
   the analyser or a project script — not in the model's context. "The graph compiled as declared" is a compiler
   fact; "these two runs log the same business entries" is an analyser fact; "the server stopped cleanly" is a
   script fact.
2. **Send the model only the residual**: the part no local stage can answer — selection, judgement, the
   explanation to the person. This is the mode selector's *fourth partial evaluation* (evidence → the toolbench)
   carried into the authoring loop, and P1 of the minimal-instructions spec (discovery aids expire once the answer
   is precomputed) applied to tool output instead of prose.
3. **Design and diagnosis are separate activities that share lowered facts.** Design produces a receipt (what was
   declared, what was generated); diagnosis consumes the receipt and the audit log. Neither needs the other's raw
   material, so they can run in separate contexts, or in one context that never holds both raw inputs.
4. **Reuse the lowered fact cheaply**: across turns (a small answer instead of a re-read), across sessions (a
   receipt or summary on disk), across runs (the M39 derived summary).
5. **Lowering never replaces the evidence.** The audit log stays the evidence (trust structure). Every projection
   names what it omitted and carries the qualifications that travel with its facts — as §H of the edit-loop spec
   already requires for `context {sections}`. A lowered fact that silently drops a qualification is a defect.

## 3. Proposals

Each item: **change** · **driver** (§1) · **expected saving** with basis · **acceptance** · **regression check**
(rule 8).

**Common acceptance protocol.** The baseline (PR #131) sizes the problem; it is not the control. Each acceptance
runs a **treatment arm and a control arm interleaved in the same session window** (control = the released stack
the treatment changes), Haiku 5.5, n = 3 per rung on the rungs the change reaches. Between-session noise was 26%
in cost for one arm [G], so a non-interleaved comparison against #131 is reported as indicative only. PASS must
not fall below the control's; the stated metric must move by more than the control's own min–max spread on that
rung; otherwise the item is reported as *no effect shown*, not as a saving.

### L0 — Measure the split before claiming it (prerequisite)

- **Change.** The G14 runner's scorer records per request `input_tokens`, `cache_read_input_tokens`,
  `cache_creation_input_tokens`, `output_tokens` and the tier, and classifies tool-result bytes as `auditLog` /
  `generated` / `build` / `server` / `analyser` / `docs` / `other`. It also assigns each tool call to a **phase**:
  *design* (until the last successful generate/build), *run* (run, settle, export, stop), *diagnosis* (from the
  first analyser call after the last export to the final answer). P3a already requires the cache buckets.
  **Because transcripts are never committed, the scorer writes derived per-run tables** (`buckets.json`,
  `categories.json`, `phases.json`) next to score.json, and those are committed; a re-score from a transcript is a
  check of the tables, not the evidence.
- **Driver.** §1.3's unmeasured ≈ 74% and §1.5's inferred split.
- **Saving.** None directly; it decides whether L1, L4 and L5 are worth building.
- **Acceptance.** On a fresh interleaved pair, the committed category bytes sum to `toolResultBytes` per run, and
  cost recomputed from the committed buckets is within 2% of `usage.costUsd`.
- **Regression check.** A scorer unit test on a frozen synthetic transcript: categories and phases sum to the
  totals; deleting a category or phase rule fails the sum assertion.

### L1 — A readable tabular projection is the author's default log read

- **Change.** `read` gains a view, `read {view: "table"}` (`read {fields}` stays the precise form; "profile" is
  not used because it names the project profile): one row per record, columns = the business keys present,
  framework trace keys collapsed into a dispatch column (`node.method@annotation`). The reply ends with an
  **omission and qualification statement**:
  - what was left out: records not shown, keys omitted, values truncated, identity hashes masked (with a count,
    as `audit-compare.py` reports it), the `recordIndex` range, and the exact call that returns the rest;
  - the qualifications that travel with the facts: the file-identity verdict (M68.7), `timeOrder`, producer
    findings, and in-flight / pending-EOF records.
  The `load-audit-log` / `add-a-node` skills say to use it (or `fields`, `series`, `aggregate`) and never to
  `cat`/`grep` the export.
- **Driver.** Tool results (≈ 55% of growth [S]); the owner's first quote.
- **Saving.** ≈ **16× fewer tokens** than the raw log for one audit log [S, one sample]. The raw-log share of tool
  bytes is unmeasured (L0), so the per-run saving is unknown.
- **Acceptance.** Against the interleaved control, L0's `auditLog` bytes per run fall ≥ 75%, every rung's oracle
  and CHART still pass at the control's rate, and no run reads the raw export with a shell tool.
- **Regression check.** On a frozen fixture: the table's byte count is recorded (not a token claim, per §H); every
  value equals the same field from a raw `read`; and separate assertions fail when the omission statement is
  removed, a record is dropped without being counted, or any one qualification (identity verdict, timeOrder,
  producer finding, in-flight) is dropped. `CanonicalSkillsTest` asserts the skills name the view.
- **Why the qualifications are load-bearing.** Baseline run base-r2-h55-3 failed CHART on an identity note: the
  charted file was rewritten after charting (design edited, then reverted, and the run re-written) [B, INFERRED — the note's text was not
  captured]. Its ORACLE passed; what went stale was the chart's evidence. A projection that dropped the
  file-identity verdict would have hidden exactly that.

### L2 — One comparison surface: lower `audit-compare.py` into the analyser

- **Change.** A read-only comparison that reads a second export with the analyser's own reader (RecordBreak, the
  C32/C33 positional trace rule). It returns the business and framework difference counts and the first N
  differences as `recordIndex` anchors. It changes no session state (rule 9 unaffected); the path is confined like
  other agent-supplied paths.
- **Relation to M39.** [`spec-baselines.md`](spec-baselines.md) M39.4 plans a `baseline` verb (D-N5: compare /
  build / list) comparing a log with a named derived summary (M39.2: coverage, counts, ranges). This lever asks a
  different question of a different operand — a positional, record-by-record diff of two same-input exports with
  `recordIndex` anchors (C32/C33) — so the two share a **verb and its refusal rules, not an engine**: M39.2 cannot
  produce first-N difference anchors.
- **Form — DECIDED (review of PR #132): one read-only verb, `compare`.** Operands: `compare {with: {export:
  "<path>"}}` (this lever) and `compare {with: {baseline: "<name>"}}` (M39.4's comparison). Reasons:
  1. **Read-only is a per-verb property.** `McpTools` marks each verb `readOnlyHint` or `destructiveHint` as a
     whole, and the verb reference marks verbs read-only. A `baseline` verb that both builds and compares could
     not be read-only, so every client would prompt before a comparison. That rules out a `baseline` verb carrying
     the export operand.
  2. **Not a parameter on `aggregate`.** Its reply is buckets over one log; its `filter` is the shape `context`
     returns, and a compare parameter would have to say whether it scopes both logs; `ReportResolver` stores an
     `aggregate` call as a table source that re-issues exactly (M33.7), which a compare parameter would make
     ambiguous between a bucket table and a differences table.
  3. **Token cost does not discriminate.** One verb schema is about the size of `coverage`'s; a parameter saves
     tens of tokens of schema and spends them on a longer `aggregate` description (INFERRED).
  - **M39.4 is re-scoped, not absorbed.** Only its *comparison* lands as an operand of `compare`. *Build* writes a
    project-tier artefact and *list* enumerates them; they keep a writing `baseline` verb (or *list* becomes a
    `context.baselines` section, as reports and walks are) when M39 ships. `VerbSchemasTest` pins 18 verbs today (`import` included); `compare` makes 19, and a
    writing M39 `baseline` verb 20;
    each addition is a Decisions entry, because that test pins the set, and changes the tool list,
    `/manifest`, the verb reference in `docs/site/user-guide/assistant.md` and the schemas together.
  - **Condition 1 — rule 9.** The second export is parsed, compared and discarded **inside the call**: no cached
    index, no "current comparison". If paging the first N differences ever needs a cache, that cache is session
    state and gets its own node, effect and fact. The chosen baseline (D-N4) comes from the `SessionSnapshot`, and
    D-N4's "ask" is a refusal that names the candidates, not a dialog.
  - **Condition 2 — M68.7.** The reply carries the file-identity verdict for **both** files, as a qualification
    (§2.5). The baseline's rung-2 CHART failure was a file rewritten after use [B, INFERRED]; a comparison without
    the verdict could compare the wrong bytes silently.
- **OWNER DECISION (open) — D-N3.** D-N3 says a comparison "never renders a verdict". `audit-compare.py`'s MATCH /
  DIFFER / INCONCLUSIVE is scoped to *same-input equality of logged business entries*, not to "normal". Until the
  owner decides, the surface returns the two facts and no verdict word. Points for the decision, from the author
  and both reviews of PR #132:
  - the author's preference, if a verdict is kept: the `export` operand only, never `baseline`, where D-N3 stands;
  - **same input cannot be checked** by the analyser or the script — the caller asserts it. A MATCH rests on that
    assertion, so either the caller *declares* same-input (as provenance is declared) or the reply states the
    count fact only ("0 business differences in N records");
  - **equality can be vacuous**: if the exports differ in per-node audit levels, trace setting or graph identity,
    the result must be INCONCLUSIVE, and "did not log" still does not mean "did not run";
  - the count fact already carries the information, so a verdict word saves no tokens.
- **Driver.** Turns and re-reads when the script is missing or misread; two readers of one format.
- **Saving.** **Small for tokens**: the script already prints a compact verdict (INFERRED). The real gain is one
  reader instead of two, and an answer for clients without Python.
- **Acceptance.** On rung-3 and rung-5 before/after captures, the analyser and `audit-compare.py` agree on counts
  (and on the verdict, if the owner keeps one) in every run.
- **Regression check.** `tools/test_audit_compare.py`'s fixtures run through both; any disagreement fails. A
  mutation that treats a trailing `annotation` as framework must fail C33.

### L3 — Lowered design facts: the compiler's receipt answers "did it compile as declared"

- **Change.** The compiler's validation report / authoring receipt carries, as structured data: declared vs
  generated nodes (with §F's aliases and canonical ids), edges, per-event-type dispatch order, guards and
  unresolved references. The analyser exposes the same facts from GraphML through `topology` / `context
  {sections}` for a session with no receipt. The skill names the receipt as the single answer to the design
  question. The producer side is upstream (compiler) work, to be filed in `upstream-asks.md` when L0 sizes it.
- **Driver.** Generated-code reads: 41 on the baseline, median 3.5, rung 4 unchanged at 3, 26% of tool bytes [B, D].
  **The guidance did not stop them**, which is P1 of the minimal-instructions spec in action: prose describing
  where not to look loses to an artefact that does not answer the question.
- **Saving.** Up to the 26% of tool bytes that are generated code [D], if a receipt removes the reads. Confidence
  is low: generated reads correlate −0.21 with cost on the baseline [D], so those bytes may not be the ones that
  push prompts over the tier.
- **Acceptance.** Against the interleaved control, median generated-code reads **0** on every rung, PASS not
  lower, no answer cites generated source as evidence, and L0's `generated` bytes fall ≥ 80%.
- **Regression check.** A receipt-schema test on the rung-4 fixture: dropping an edge or a guard from the receipt
  fails; the skill-text test asserts the receipt is named and generated source is not.

### L4 — Keep every request under 100k

- **Change.** (i) Project scripts cap their own output: full output to a file under `logs/`, and a bounded
  summary to stdout (exit status, the first error with its location, the file path). Builds run `mvn -q -ntp` by
  default, with a `--verbose` escape. (ii) Server output goes to a file, and the script prints lifecycle facts only.
  (iii) Skill guidance: start the diagnosis activity in a fresh context seeded with the design receipt (L3) and the
  run's export path, instead of carrying the design transcript forward (principle 3). (iv) Never re-read a file
  already summarised in the context.
- **Where the scripts live.** Both templates come from the **playground scaffold** (`fluxtion-web`), not this
  repo [B FIXTURES.md]. `run-and-export.sh` exists only in the analyser bundle (rungs 3, 5); the Spring starter
  (rungs 2, 4) has no single run/export command. (i)(ii) for rungs 2 and 4 therefore need the starter to gain one:
  filed as **UP-PG-06** in [`upstream-asks.md`](../proposals/upstream-asks.md).
- **Driver.** `over100k` (r = 0.94 / 0.985 [D]); `maxPrompt` (r = 0.96 / 0.92 [D]); 23% of baseline requests over
  the tier [D].
- **Saving.** An estimated ≈ 30–35% of Haiku run cost if no request crossed the tier (INFERRED, §1.5). The
  rung-3 evidence in §1.4 (over 100k 18 → 3, cost −66% [B]) shows the lever can work, with the confounds named
  there. (iii) carries the most uncertainty, because a fresh context re-pays the ≈ 22k base [S].
- **Acceptance, per rung, against the interleaved control.** Rungs 3 and 5, with (i)(ii) applied to the bundle:
  median `over100k` at most half the control's, and median cost below the control's by more than the control's
  min–max spread. Rungs 2 and 4: the same criteria, once UP-PG-06 ships, and not before. (iii) is accepted
  separately: rungs 3–5, total cost (both contexts) below the control's single-context cost, PASS not lower.
- **Regression checks.** (i)(ii): a script test runs each project script against a failing and a passing fixture
  and asserts that stdout stays within a fixed line budget while the full log file holds the error; removing the
  cap fails it. The test belongs with the scripts (upstream); this repo's copy of the canonical skills asserts
  they name the capped scripts. (iii)(iv) are skill prose, so they follow minimal-instructions P1–P3: a
  `CanonicalSkillsTest` assertion keeps the text present. The text stays only while an ablation shows it saves
  turns (P2: only a measurement retires a guardrail; P3: words are cheap, turns are not), and it is deleted once
  L3's receipt makes the procedure unnecessary (P1).

### L5 — One-call diagnosis summary

- **Change.** One surface: **`aggregate` with a per-node summary**. Today `aggregate.groupBy` is an enum
  (`dimension`, `thread`, `hour`, `minute`, `day`, `none`) and `metric` is required (`VerbSchemas`). `dimension`
  buckets by the record's event dimension, not by the node instance that wrote an entry, so the summary adds a
  `groupBy` value **`node`** (bucket by logging instance) and a `metric` value **`summary`**, valid only with
  `groupBy: "node"` and refused otherwise before any work: `aggregate {metric: "summary", groupBy: "node"}`.
  The other metrics may also take `groupBy: "node"`. It returns per node: record count, first/last `recordIndex`, and for each
  business key first/last/min/max. It is a query, not a workflow verb (the `add-a-node` skill rules out a compound
  build/run verb). It is **not** a `context` section (sections are exactly what the full context holds, and none
  carries per-node values) and **not** `coverage` (coverage is graph × log and refuses an inferred graph). It must
  be composed from the same index services that answer `aggregate` and `series`, and no value may be recomputed at
  a second call site (CLAUDE.md rule 9).
- **Driver.** Turns (r = 0.60 first ladder, 0.83 baseline [D]) and the read-around-and-look pattern of the
  diagnosis phase.
- **Saving.** A few turns per run (INFERRED; unmeasured until L0's phases exist). Each turn re-reads the whole
  context, so a turn saved late in a run is worth more than one saved early.
- **Acceptance.** Against the interleaved control, L0's diagnosis-phase analyser calls fall ≥ 50% and diagnosis-
  phase turns fall by more than the control's spread; PASS and CHART not lower.
- **Regression check.** Equal values do not show reuse, so the check is **structural**, in the style of
  `OneDispatchModelTest`: a static test names the one index service that computes counts, ranges and anchors for
  `aggregate` and `series`, and fails if the summary's implementation computes any of them itself (a second
  accumulator, its own min/max, its own record walk). Its witness is the mutation that inlines a min/max loop into
  the summary: it must turn the test red. A fixture test additionally checks that the summary's values equal
  `aggregate` / `series` over the same keys, and the schema test that `metric: "summary"` without
  `groupBy: "node"` is refused. A node that never
  logged appears with count 0; dropping it fails (the uncovered node is the finding, M40).

### L6 — Text-log → binary pre-parse, and why compression is not the route (a rejection)

- **Finding.** gzip + base64 of an audit log was **unreadable to the model** [S]. It removes bytes from storage,
  not meaning from the context, and base64 does not tokenise compactly (INFERRED). Rejected.
- **What the owner's second clause buys.** "Pass a text log through the binary parser" is valuable as **local
  parsing**: the analyser's index already parses once and answers `aggregate` / `series` / `read {fields}` from it.
  The saving is the projection sent (L1, L5), not the encoding. A binary export (M52) helps the producer and the
  local parse; the model must still receive text.
- **No acceptance test**: nothing is built. The only artefact is one skill line, "never paste or encode the raw
  log". Its rule-8 check is a `CanonicalSkillsTest` assertion that the line is present, and it is subject to the
  same P1–P3 retirement rule as L4 (iii)(iv).

### L7 — Model selection: the cheapest model that passes

Lowering (§2) is what lets a small model do the work; this lever states which model to use for the task family the
ladder measures (Spring and bundle authoring), and when to step up.

- **Evidence.**
  - **Haiku 5.5**: 11/12 on the first ladder (corrected scoring; 10/12 under the sealed rung-4 oracle) at a median
    $0.190 per run [L]; 10/12 on the baseline at $0.132 [B]. Both baseline failures are **rung 2, CHART only**:
    rung 2 is 1/3 [B].
  - **Sonnet 5**: 3/4 on the first ladder at a median $3.425 per run [L]. Its cost over the Haiku 5.5 rung median

- **Why it is a token lever.** Price per token differs by model far more than any lever in §3 moves token count;
  the wrong default undoes every other saving.
- **Driver.** Cost per run. The 5× Haiku 5.5 tier above 100k [L] interacts with L4: a model that needs larger
  prompts is penalised twice.
- **Saving.** Already realised by choosing Haiku 5.5 (18× per run against Sonnet 5 [D]); the lever's value is
  keeping it — stopping a default drifting to a larger model without evidence.
- **Acceptance.** A model is marked *meets acceptance* for this task family only when the latest baseline-style
  ladder shows it at ≥ 2/3 on **every** rung with ORACLE, VALID and CHART all counted; otherwise its row names the
  rungs where it is open. A negative row ("not for the chart step") names the check it rests on (S5). A per-activity
  recommendation needs L0's phases **and** a mixed-model arm (one model for design, another for the chart); a
  step-up rule needs an interleaved run in which the larger model passes a failure class the default fails,
  outside the noise band (§3). The rung-2 chart step is the first candidate for that run.
- **Regression check (rule 8).** `ModelChoiceEvidenceTest` parses the *Model choice* table. Every row has a
  status from a closed set — `meets acceptance` (with any `open` rungs), `advisory`, `negative`, `unmeasured` —
  and every row but `unmeasured` names its evidence folder and the field it reads (`PASS` per rung for the
  ladders; `S5` for the grid, whose score.json has no `rung` and whose `PASS` is the sealed value). Runs are
  selected by `model` id; `*-VOID-*` runs and score files with no `model` (the grid folder's A/B controls, e.g.
  `ab-ctl-r1`, and the empty `ab-ctl-r1b`) are excluded and listed in the test's output. The test
  applies the row's stated check (the last column) and fails if: a *meets acceptance* rung is below 2/3; an *open*
  rung is in fact ≥ 2/3 (stale); an *advisory* or *negative* row's check does not hold; a non-`unmeasured` row
  cites no folder or field; or a status is outside the set. **The score files are not sealed by the
  `MANIFEST*.sha256` files** — those seal predictions, tasks and harness inputs before the runs — so the test reads
  a committed digest file (`docs/specs/model-choice-evidence.sha256`, created with the test; one sha256 per cited
  `score.json`) and fails
  on any mismatch: editing evidence then fails the test unless the digest file is changed in the same reviewed
  diff. Witness: on a temporary copy of a cited folder, flip two `PASS` values on one claimed rung — the test must
  go red, both on the digest and, with the digest updated, on the claim.
- **Risks.** n = 3 per rung for Haiku 5.5 and n = 1 per rung for Sonnet 5 [L, B]; a policy drawn from one task
  family may not transfer; a model release can change the table overnight, which is why the test reads evidence,
  not a hard-coded name.

## 4. Ranking and the first slice

Score = expected saving × confidence ÷ cost to build (each High / Medium / Low). Ranked on both datasets. A "?"
marks a saving that is plausible but unmeasured; it is scored at face value, because confidence already carries
the doubt.

| rank | item | saving | confidence | cost | why |
|---|---|---|---|---|---|
| 1 | **L0** measure the split | — | High | Low | every other estimate depends on it |
| 2 | **L4 (i)(ii)** capped output, rungs 3/5 | High | Medium | Low–Medium | strongest driver in both datasets; rung-3 evidence; upstream bundle change |
| 3 | **L4 (i)(ii)** for rungs 2/4 (UP-PG-06) | High | Medium | Medium | the same lever, but the starter has no script yet |
| 4 | **L1** tabular view + skill default | High? | Low–Medium | Medium | one 16× sample [S]; raw-log share unmeasured |
| 5 | **L5** diagnosis summary | Medium | Medium | Medium | turns r = 0.83 on the baseline; one existing surface |
| 6 | **L4 (iii)** design/diagnosis split | High? | Low | Low | the biggest prompt cut, but the base is re-paid; model-dependent |
| 7 | **L3** design receipt | Medium | Low | Medium–High | 26% of tool bytes, but uncorrelated with cost; upstream |
| 8 | **L2** `compare` verb | Low | High | Medium | correctness and one reader, not tokens; form decided, D-N3 open |
| — | **L7** model selection | High (kept, not new) | Medium | Low | the 18× is already realised [D]; the lever stops it drifting; docs + one test |

## 5. Risks, and what would show the idea is wrong

- **Correctness — lowering must not hide evidence.** A projection that omits the record that disproves the
  conclusion, or drops the identity verdict that qualifies it (base-r2-h55-3 [B]), is worse than the raw log.
  Mitigation: every lowered reply states what it omitted and carries the qualifications (§2.5, L1). The audit log
  remains the evidence and is never deleted or rewritten. Acceptance always includes the oracle and CHART, not
  cost alone.
- **Model dependence.** Haiku 4.5 failed the chart step in all three grid runs [G]. Sonnet 5 claimed success on a
  rung-3 run whose counter ran on every trade [L]. A lever that helps Haiku 5.5 may do nothing for another model,
  and a compact answer can make an overclaim easier to write. Results are per model and are not transferred.
- **Measurement noise.** n = 3 per rung; same-arm sessions differ by 26% in cost [G]; rung 5 moved against rung 3
  on the same bundle [B]. Only interleaved arms and effects outside the control's spread count (§3).
- **Fresh-context cost.** L4 (iii) re-pays the ≈ 22k base [S] and loses implicit context; it may cost more turns
  than it saves.
- **Cache floor.** Shrinking early outputs can push a prefix under a model's minimum cacheable size (P3a). L0's
  cache buckets detect it.
- **The idea is wrong if**, with L0 in place: (a) runs whose `over100k` is ≤ 1 do not cost materially less than
  matched runs above it; or (b) L1/L4 cut tool-result bytes ≥ 50% and cost does not move outside the noise band;
  or (c) PASS or CHART falls on any rung under a lowering lever — evidence that the residual sent was not
  sufficient.
