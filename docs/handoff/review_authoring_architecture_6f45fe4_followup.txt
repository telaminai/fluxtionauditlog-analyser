C1 · HIGH — THE FINGERPRINT CORRECTION INVENTS A NEW NAME AND STILL CONFLATES TWO IDENTITIES
================================================================================

spec-authoring-modes.md:51-63 and tracker.md:843-852 now say sourceFingerprint was missed because the
capability ships as `descriptorFingerprint`. There is no product capability or contract field with that
name. The only occurrences are a private helper method in DescriptorFingerprintTest and the new prose.
The producer's shared identity is still named `sourceFingerprint`:

  * GraphML key: fluxtion.sourceFingerprint
  * generated descriptor API: DescriptorSupport.Meta.sourceFingerprint()
  * wire-envelope metadata: sourceFingerprint

`DescriptorFingerprintTest` is the TEST name because it inspects the descriptor carrier; it did not
rename the capability. The original search also could have found the literal name in this repository's
GraphML fixtures and GraphVocabularyTest. Correct the account rather than replacing one name error with
another.

The more consequential half remains unchanged. The text says the new audit-log carrier removes
`report.LogFingerprint`'s recomputation. It must not. These identities answer different questions:

  sourceFingerprint  = which compiled model?
  LogFingerprint     = which particular captured log/report observation?

Many logs from separate runs should share one sourceFingerprint. A persisted report must still refuse a
different log from the same model. Add sourceFingerprint alongside LogFingerprint and use both where the
claim requires both.

Finally, spec-authoring-modes.md:101 still says "compiler identity -> runtime artefact" is wholly
unpinned. The generated processor descriptor is a runtime artefact and its equality with GraphML is
exactly what DescriptorFingerprintTest pins. Replace that row with the two actual joints:

  compiler model -> GraphML + generated descriptor     PINNED
  generated model identity -> audit-log header         UNPINNED
