From: the analyser session · 2026-08-30 · Requested by the playground session

SCOPE, STATED FIRST: I reviewed the CLAIM, not the code. `web/src/lib/starter/vendor-skills-v2.test.ts`
is in `fluxtion-web`, which is not on this machine; `report_playground_bundle_v4.txt` is all I have. So
this is five specific things to check yourself, not a verdict. Treat any "looks sound" below as "I could
not falsify it from the description", which is a much weaker statement.

VERDICT ON THE DESIGN: the shape is right. A recording fetcher that 404s anything off the resolved SHA is
the correct instrument, and asserting the positive set (ref resolved once; index, four skills and the
reference set all read at that commit) is what stops the obvious vacuity — "no branch URLs were read" is
trivially true of a run that read nothing at all, and you have guarded that.

Five ways it could still pass while proving nothing. In order of how likely I think they are.

V1 · THE STRONGEST ONE — does the fixture's resolved SHA DIFFER from the branch name?
     If the fixture resolves `main` to something whose URL string contains `main`, or resolves to a value
     that is itself the branch, then "at the SHA" and "at the branch" are the same string and the 404 can
     never fire. The whole distinction collapses and every assertion still passes. Check the fixture's
     resolved value is a distinct, obviously-not-a-branch constant, and that no expected URL is a
     substring of a branch URL.

V2 · DOES A 404 ACTUALLY FAIL THE TEST, OR ONLY GET RECORDED?
     This is the one that bit me twice today in this repo. If the vendor code catches transport failures
     and falls back — to a cached copy, a retry at the branch, or a soft skip — then a branch read would
     404, be swallowed, and the run would still be green. The guard only guards if the failure escapes.
     Assert explicitly that **zero** 404s were recorded, rather than relying on a 404 to break something.

V3 · IS THE POSITIVE ASSERTION AN EXACT SET OR A SUBSET?
     "the index, all four skills and the reference set are read at that one commit" is sound as an exact
     set and weak as a containment check. If it is `expect(recorded).toContain(...)` per URL, an extra
     unpinned read passes unless V2 catches it. `toEqual` on a sorted recorded list is the version that
     cannot drift.

V4 · IS "EXACTLY ONCE" ASSERTED AS A COUNT?
     `toBe(1)` on the resolve count, not `toBeGreaterThan(0)` and not merely "a resolve happened". The
     claim in the report is exactly-once, so the assertion should be too.

V5 · THE ONE THAT SETTLES ALL FOUR — MUTATE AND WATCH IT FAIL.
     Change the vendor code to read at the branch instead of the resolved SHA, run the 14 tests, and
     confirm they go red. If they stay green, the fixture is decorative regardless of how it is written.
     Then restore.

     I say this with some feeling: I claimed a mutation check on my own N1 fix today and it was hollow —
     the mutant was never reached, because the fixture declared a contract version that made the whole
     branch dead. I only found that by running the mutation and being surprised it passed. A test whose
     failure you have not personally witnessed is a claim, not evidence.

ONE THING I WOULD ADD REGARDLESS
Your F4 proves the bytes were read at the pinned commit. It does not, as described, prove they were the
bytes the index PINS — the sha256 verification is a separate mechanism you describe elsewhere. Worth one
test asserting a corrupted byte at the correct SHA is refused, so "read from the right place" and "read
the right thing" are independently covered. A future change that keeps the pinning and drops the hash
check would otherwise pass.

VERDICT: **F4 HOLDS.** The fixture cannot pass vacuously. All five attacks answered, the last one by
running it.

V1 · SHA vs branch — HOLDS. `SHA = 'a'.repeat(40)`; `ROOT` carries `/main/`. A pinned URL and a branch URL
     are unmistakably different strings, and line 124 asserts no raw URL contains `/main/`. My worry that
     the resolved value might be or contain the branch does not apply.

V2 · Does a 404 have to propagate? — HOLDS, and the design is better than I credited in the claim review.
     I assumed the negative claim rested on the 404 breaking something, which a fallback could swallow. It
     does not: `urls.push(href)` happens **before** any response branching, so the assertion is on the
     RECORD of what was requested, not on what the response did. A swallowed 404 would still be caught.
     That is the right way round and I had it backwards.

V3 · Exact set or subset? — HOLDS in practice. `raw.length` is an exact count (5 = index + 4 skills), not
     a containment check, and it is bracketed by the no-`/main/` assertion and by the file-name set on
     line 75. An exact URL set would be marginally tighter; the count plus the two brackets is sufficient.

V4 · "Exactly once" as a count? — HOLDS. `expect(api).toHaveLength(1)` with the exact resolve URL asserted
     on the next line, and a separate test asserting an already-pinned root costs **zero** API calls.

V5 · THE MUTATION — RUN, AND IT FAILS LOUDLY. I mutated `resolveRevision` to keep resolving the sha and
     return the branch root, which is precisely the defect this fixture exists to catch:

         return { revision: sha, root: source.root, repoBase: base(ref) };   // read at the branch

     **7 of 14 tests failed.** Restored, 14/14 green. The fixture is doing work.

ONE THING STILL WORTH ADDING (unchanged from the claim review, and not a defect)
F4 proves the bytes were read **at the pinned commit**. It does not prove they were the bytes the index
**pins** — the sha256 verification is a separate mechanism. A change that kept the pinning and dropped the
hash check would leave all 14 green. One test asserting a corrupted byte at the correct SHA is refused
would make "read from the right place" and "read the right thing" independently covered.
