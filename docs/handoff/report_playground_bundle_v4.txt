§2 — PINNING A DRAFT, which the brief did not ask for and which the contract needs
  m19-skills/2 pins no revision, deliberately and correctly. But a generator still has to record
  WHAT IT READ, and "main" is not that. The vendor tool now resolves the ref to a commit BEFORE
  reading anything and fetches every path at that commit. Two consequences:

    · a draft can be vendored with a real, reproducible identity — this snapshot is
      619e048fb81a3046dc6c757ee2f1d7af62b3d4ea, not "main as of some moment";
    · it closes a race the branch form always had. Fetching the index from main and then each skill
      from main reads whatever main is at each fetch; a push landing mid-vendor produces a snapshot
      that never existed as a single commit.

  Provenance stays `canonical@<sha>`. An earlier attempt recorded `canonical-draft@`, which the bench
  correctly refused: it breaks the declared grammar (canonical|local)@… | mirror:… | none. Draftness
  is a property of the INDEX, not of the retrieval, and now lives in the manifest as `draft: true`.
  That was my error and the bench caught it, which is the bench working.

  When you publish v2 with a revision and per-path sha256, this tool will read the pinned revision
  instead of resolving one, and nothing else changes.

  So the check cannot distinguish "this file restates the triage rule" from "this file names the

  I did not go green on this. Rewording your `why` text to slip past a grep would have hidden a

  instead: "If the contract is wrong rather than merely awkward, say so."

        that could restate anything; the block is generated from your own data and cannot;

        surrounding prose), which is harder and probably not worth it.
  (a) is a few lines and preserves what the check is for. Everything else in check_v4 passed.
