4. THE WORK, CONCRETELY
================================================================================
A · SELECTION. Consume `m19-skills/2`: selection = `common` + the specialisations your template declares.
    - `common` today: `load-audit-log`, `guided-start`
    - specialisations: `mongoose`, `embedded`, `spring`, `replay`
    - **never select `replay` unless the template has a real replay entry point.** Its skill carries a
      required marker you could not substitute, and v3's acceptance already refuses a surviving marker.
      This is exactly the defect C1 caught in our own draft.
    - worked example to sanity-check against: a spring+mongoose template selects
      `common/load-audit-log`, `common/guided-start`, `spring/add-a-node`,
      `mongoose/run-mongoose-server` — and **not** `common/replay-a-run`.

B · SUBSTITUTION. Markers currently needing a project-owned value:
    - `spring/add-a-node` — the exact regeneration command, and whether it needs a Fluxtion API key
    - `mongoose/run-mongoose-server` — the exact clean-stop command (pre-existing)
    - `common/replay-a-run` — only if you select it

C · THE BUNDLE'S `CLAUDE.md`. Render from `reference-set.json`:
    - ship only `agreed` entries — four today
    - `appliesTo` **selects**, it does not annotate: a `spring` link must not appear in a non-Spring
      project. An always-in-context file is a tax on every turn
    - below the links, only what the set does NOT cover: this project's paths, commands, graph — and the
      audit contract until telaminai/fluxtion#22 lands
    - **restate nothing the agreed set already carries.** That duplication is why four wrong versions of
      the audit contract got written; pointing is what makes one upstream edit improve every project
    - generate `AGENTS.md` from it; never hand-maintain a twin

D · PROFILE. Register each selected skill as `runbook.N.*` with its frontmatter description, per v3's
    table. Unchanged by v4.
