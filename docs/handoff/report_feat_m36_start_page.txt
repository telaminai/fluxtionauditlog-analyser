1. SLICE 1 — the bundled demo set, and the claims it makes checkable
================================================================================
Every action on the start page must work with no configuration, no server and no API key (D-S2),
and each asset earns its place by making one of the page's sentences TRUE rather than by being
available. DemoAssets ships them in the jar and unpacks to ~/.fluxtion-analyser/demo on first use.

WHY ON DISK: every verb the actions use takes a PATH — open {log}, open {graphml},
source_root {add}. A classpath resource is not a path. Extracting also makes the demo behave
exactly like a real investigation: same open, same store, same everything. An in-memory special
case would demo something the product does not do.

DemoAssetsTest (7) asserts the claims rather than trusting them — each test is one sentence the
page is allowed to say:
  · every promised file is actually in the jar
  · the walkthrough log and the graph ACTUALLY pair (every logged node is declared)
  · coverage has a REAL answer — nodes that ran AND nodes that did not, so "which nodes never ran"
    demonstrates the feature instead of proving it by never exercising it
  · the traced log really is traced, so "did not run" is PROOF and not merely described
  · the series log has >100 records, because ten points is not a chart
  · the source declares the node types a topology click opens
  · the shipped demo carries no real names

2. FINDING — rule 1 has a hole, and this slice walked into it
================================================================================
The last test FAILED on first run:

    com/acme/demo/generated/DemoQuoteProcessor.java carries a real name: v12technology

The Fluxtion compiler writes a copyright header into generated source:

    Copyright: © 2025.  Gregory Higgins <greg.higgins@v12technology.com> - All Rights Reserved

FOUR files under examples/fixture-generator carry it, and slice 1 was about to bundle two of them
INTO THE SHIPPED JAR, where an employer-domain email would go out with every release and onto any
screenshot of the demo's source pane.

THE REASON IT WAS INVISIBLE: **CLAUDE.md's standing sweep is `aquis|talos|nonco`. It does not look
for `v12technology`** — although the same document discusses `@v12technology.com` at length in the
commit-metadata paragraph. The sweep has never been able to catch this class, so "sweep clean" has
been true and incomplete on every commit in this repo, including all of mine.

DONE HERE: the header line is stripped from the two bundled copies; the test now guards the shipped
set against all four terms, permanently and automatically, because this is content that ships.

NOT DONE — OWNER'S CALL, because it is a rule-1 policy matter and pre-existing:
  a) extend rule 1's sweep to `aquis|talos|nonco|v12technology`. It will then FAIL on the four
     examples/ files until they are cleaned, which is the point of extending it.
  b) decide about those four files. They are already public. The header is compiler boilerplate
     carrying a personal address, not project content — stripping it changes nothing but the leak.
  c) worth checking whether the compiler still emits that header, since every future generated
     processor in every user's repo carries it too. That is an upstream ask, not an analyser one.
