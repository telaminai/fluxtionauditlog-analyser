1. WHAT CHANGED, AND WHICH EARLIER DECISION EACH PART SUPERSEDES
================================================================================
D-SP2 said "One spotlight at a time; a new one replaces the last." Right for a tour, wrong for a diagnosis, where
the thing to show is a RELATION. That one sentence is superseded by D-SP6; the spec says so in place.

  spotlight {target, caption}                       unchanged; still REPLACES what is lit
  spotlight {targets: [{target, caption?} | "name"]} a SET, at most 6 (SpotlightVocabulary.MAX_LIT)
  … {add: true}                                     keeps what is lit; same target re-lit in place, same number
  spotlight {clear: true} / {clear: true, target}   all / exactly one

· ALL-OR-NOTHING. SpotlightTarget.resolveAll(names, Surface): parse EVERYTHING before the surface is touched; then
  reveal+measure each, and after each reveal re-measure every earlier member — revealing a chart note hides a
  topology node (different tabs). Such a pair is refused NAMING THE PAIR and saying "light them one after the other".
· NUMBERED. >1 lit → a badge on each cut-out, callout tagged "assistant · n", `n` in echo and context. A number
  lives as long as its spotlight: putting one out does not renumber, and a new one never reuses a spoken number
  (the chat that said "2 never logged" has already been read). Restart on replace/empty.
· LAYOUT. SpotlightGeometry.layout: same four sides, same order as the single rule; first side covering no cut-out
  and no placed callout wins; else least-covering. For one spotlight it IS the single rule (asserted over six cases).
· ONE SHAPE. Echo and context both: spotlight: {lit: [{n, target, caption?}]} (echo adds bounds). This REPLACES
  D-SP4's context.spotlight {target, caption} and the first echo's {lit: {target, bounds}}. Unreleased verb, so no
  client to keep compatible — but it IS a second shape within one day, and the reviewer may prefer I had kept the
  single form as an alias. I judged one shape learnt once to be worth more.
· A REFUSED CALL now re-measures what was standing. If the attempt's own reveal took a standing spotlight off
  screen, it goes out and the refusal says which. The first report's "a refused spotlight changes nothing" was true
  of the lit set but, by reading, not of where it was painted. Not reproduced before fixing; the new behaviour is
  what is tested (verify script: "the refusal says which standing spotlights its reveal took off screen").
· Caption validation and the request grammar moved out of MainFrame into SpotlightTarget.requests / captionError —
  pure, so the whole input grammar is tested headless. ActionExecutor reveals EVERY records:row in a set via goto's
  path; the last one is left selected.

M64.7 — SpotlightVocabulary.GUIDANCE, one paragraph, at every entrance an assistant arrives through:
  PromptBuilder.inProcessActionManifest   + the verb line and its targets. FINDING: the built-in assistant could

3. WHAT A REVIEWER SHOULD ATTACK
================================================================================
· `coverage` AS A TARGET NAME. It lights the Topology tab's status line, which states the PAIRING verdict ("fits this
  log 5/5"), not the coverage gap. My own mis-caption (above) is evidence the name misleads. M64 chose it because the
  spec's vocabulary had it and there is no coverage panel. Renaming it (e.g. `topology:verdict`) changes a pinned
  vocabulary and the re-pinned skill text mentions `coverage` — so I did NOT, and flag it instead.
· CALLOUTS STILL COVER CONTENT THAT IS NOT LIT. layout() avoids cut-outs and other callouts only. In both findings
  shots callout 1 sits on the MarketDataEvent node and callout 2 on QuotePublisher. Avoiding everything needs the
  overlay to know the scene; I judged that out of scope for a transient pointer. Same note as the first report,
  now more visible with four.
· ARROWS CAN CROSS. Arrows are drawn before boxes so none crosses a callout BOX, but two arrows may cross each other
  or pass over a cut-out. No test, no avoidance.
· THE BOUND OF SIX is a judgement. Four already fills the demo window.
· GUIDANCE LENGTH. GUIDANCE adds ~110 words to MCP `instructions` and to both manifests. Every client pays it on
  every session. I think "when to point" earns it; a reviewer weighing token cost may want it shorter.
· THE DOCS TABLE describes what an assistant CAN do with a request, and says so beneath it. Nobody has run those six
  sentences against a context-free client. It is the same owed held-out run as the first report's, now larger.
· `add` + REVEAL SIDE EFFECTS. {add:true, target: records:row:N} runs goto's reveal, which selects record N and so
  changes the detail pane; a standing detail:node spotlight then goes out (reported in wentOut). Honest, but an agent
  may be surprised. Tested only through remeasure's unit test, not end to end.
