M13.1 — net/RestEndpointFile
  Writes {url, token, pid, startedAt} to ~/.fluxtion-analyser/rest-endpoint on
  REST start, deletes on stop/exit. Created mode 600 BEFORE the token is written
  so it is never briefly world-readable. Endpoint.alive() is the ProcessHandle
  liveness check; a corrupt/half-written file reads as absent rather than
  throwing. 9 tests.

M13.2 — mcp/McpTools + mcp/McpBridge
  `analyser.jar --mcp`; Main routes before any UI bootstrap; bridge sets
  java.awt.headless first. One tool per verb derived from llm.VerbSchemas (no
  parallel schema holder), analyser_<verb>, readOnlyHint on aggregate+read only.
  Hand-rolled newline-delimited JSON-RPC 2.0. Zero new dependencies. 26 tests.

M13.3 — tools/call
  Reads the endpoint PER CALL (so a long-lived client survives an analyser
  restart), pid-liveness-checks it, POSTs {action, params} to /action with the
  token header. Tool failure (bad params, 401, 429) → isError:true with the
  dispatcher's own message; only an absent/dead endpoint is a JSON-RPC error
  (-32001) carrying the "enable it in Settings" hint. 12 tests including a live
  ActionServer round-trip over real loopback HTTP.

3. SPEC-VS-REALITY MISMATCHES FOUND (spec updated — nothing left divergent)
================================================================================
THE BIG ONE — MCP MOVED. spec-assistant-actions-mcp v1.1 was written against an
era of MCP that no longer exists. Current revision 2026-07-28 REMOVED the
initialize/notifications-initialized handshake entirely:
  - every request declares its version in
    _meta["io.modelcontextprotocol/protocolVersion"];
  - servers MUST implement a new server/discover RPC;
  - all results carry resultType; list results also require ttlMs + cacheScope;
  - version mismatch → UnsupportedProtocolVersionError, code -32022.
The handshake era (2025-11-25 and earlier) is now formally "legacy", and MCP's
own compatibility matrix marks legacy-server + modern-client as FAILS with no
client-side fall-forward.

  → Shipped DUAL-ERA (owner's decision): both eras answered, era chosen per
    request by how the client opens. Advertises
    ["2026-07-28","2025-11-25","2025-06-18"]. Cost ~60 lines.
  → Spec raised to v1.2: new §2.1 (dual-era table), §2.2, §6, §9, §12.
  → This was caught only by reading the live MCP spec during implementation.
    Recommend treating "re-read the vendor spec" as a standing step for any
    protocol work here, not a one-off.

M2. NOTIFICATIONS. Spec §2 said "everything else → -32601". Wrong, and it would
    have broken every legacy connection: notifications/initialized has no id,
    and answering a JSON-RPC notification is a protocol violation. Rule is now
    §2.2: no id → consume silently; unknown method WITH an id → -32601.

M3. llm.Json PARSES EVERY NUMBER TO Double AND WRITES "1.0". An echoed JSON-RPC
    id turns the client's `"id": 1` into `"id": 1.0`; strict clients match ids
    exactly and would drop the response. Fixed locally in the bridge (integral
    doubles narrowed to long on the write path). llm.Json itself deliberately
    untouched — it also backs the LLM clients and REST. Warning added to §9.

M4. §6's error mapping omitted the rate limit. ActionServer returns HTTP 429
    with an ok:false body (10/s bucket in MainFrame), so a busy agent WILL meet
    it. §6 now says: any HTTP status with an ok:false body → isError:true; only
    an absent/dead endpoint is a transport error.

M5. Spec §11's manual check assumed the desktop app; it also implicitly assumed
    the *client* starts the analyser. It does not — the client starts the
    bridge; the app must already be running. This was implicit everywhere and
    confusing in the drafted docs, so it is now stated explicitly on the user
    page. No spec change needed, but worth knowing it was never written down.

6. RECOMMENDATIONS FOR THE ORIGINATING SESSION
================================================================================
R1. Review McpBridge's use of ui.ReleaseNotes.version(). It is Swing-free (only
    InputStream/StandardCharsets) and is the single source of truth for the
    version, but it lives in the ui package — a `ui` import on a path the spec
    says must stay clean. McpBridgeHeadlessTest proves the compiled bytecode
    references no Swing/AWT/FlatLaf, so this is a taste call, not a bug. Moving
    ReleaseNotes to a neutral package would settle it.

R2. Decide the SDK-vs-hand-roll question above before the next MCP revision
    lands, not after it breaks something.

R3. When M13 ships in a release, jbang users need --fresh: the cached 1.0.0 jar
    has no bridge, and `analyser --mcp` against it now exits 2 with usage
    (before this handoff it silently opened the GUI). Worth a release-note line.

R4. Consider whether tools/call should also return MCP `structuredContent` (the
    payload as JSON alongside the text). Not done: it invites an outputSchema
    per verb, which is a real design step rather than a freebie.
