2. Q-B6 ANSWERED — the live catalogue was checked, and §C2 shrinks
================================================================================
Fetched https://fluxtion-playground.dev/starter-templates/index.json and the
fluxtion-spring-mongoose starter (rule 6, as the spec directed). Findings:

  · `type` already admits `mongoose` AND `hosted` — five of thirteen entries. Three carry a
    `web-admin` tag. "No starter appears to host a Mongoose server with admin REST on" is FALSE as
    of this reading.
  · The starter's own config already declares most of the proposed table:
      - admin REST: `mongoose.services.adminWebService` (WebAdminService, host, listenPort) +
        `serverAdmin` + `adminCommandRegistry` — and the `web-admin` tag marks it at index level.
        A `mongoose.adminRest: true` field would be a SECOND SOURCE OF TRUTH for a fact the
        services block and tag already encode — the exact mistake §C2's own correction avoided
        for `mode`.
      - source roots: `adminWebService.config.sourceRoots: ["src/main/java"]` — DECLARED already.
      - run command: `mongoose.addRunScript: true` — the command is a generated-project artifact,
        not a catalogue field.
      - graphml: genuinely absent from the starter — but §C1's registry file already carries
        `processors[].graphml`, which is the better home (it is a runtime fact about a running
        server, not a template fact). The catalogue ask dissolves into the registry design.
  · The REMAINING genuine asks are TWO: `agentBootstrap` (the M19.1 CLAUDE.md-stack pointer), and
    the top-level `catalogue` version integer that D-B4's additive-only rule references but which
    DOES NOT EXIST in the live index. D-B4 currently governs a field nobody ships.
  · Bonus finding: the starter sets `auditBackend: "chronicle"` — confirming the spike's projection
    (step 5's yaml export is required), AND opening a second path the spec should note: once an
    out-of-tree chronicle reader exists (M31.4r's sibling), the agent can open ./audit DIRECTLY
    through the reader SPI and step 5 disappears. The alternative gets stronger over time through
    a mechanism the analyser already shipped; M18 could never inherit that.

================================================================================
3. THE MISSING ARGUMENT FOR: this proposal RESOLVES O5
================================================================================
M18.0 raised O5 as gating: the audit-capture plugin's Phase 2 puts a web audit viewer with graph
replay inside svc-admin-web, overlapping this analyser. Under M18 the overlap is a positioning
problem — two tools linked to one server, competing on the same surface. Under THIS proposal the
split becomes natural and complementary: the server's web viewer is the LIVE, glanceable, in-situ
surface; the analyser is the deep forensic instrument fed by exports — reports, coverage, replay,
the agent surface. The adoption should answer O5 explicitly on these terms and close it; the spec
leaves its strongest positioning consequence unstated.

4. THE OPEN QUESTIONS, ANSWERED
================================================================================
Q-B1 (developer-only safe? does M18.2 deserve to survive?) — D-B6 is safe TODAY: the product's
  actual funnel is agent-first (the playground's /build-with-ai is the front door; the compiler key
  precedes any of this). But delete-forever is more finality than the evidence supports. PARK
  M18.2 with its revival trigger STATED: "revive as an onboarding affordance only if evidence shows
  no-agent developers bouncing off the export step". Falsifiable, like D-B6 itself. Everything else
  deletes cleanly.
Q-B2 (who owns ~/.mongoose/servers/) — an upstream-asks item, yes; and the dependency is acceptable
  BECAUSE the loop gets a conformance harness (F3/§1 point 7). Without the harness, no.
Q-B4 (provenance free text vs structured) — free text for v1, exactly as specced: it renders
  anywhere and never lies. The structured comparison earns its complexity only when someone needs
  the mismatch line to reason about systems, and nobody does yet. Revisit with evidence. Add the
  two one-liners from §1 point 9 (share disclosure; Q1-soft-banner treatment).
Q-B5 (does this weaken M12?) — no; it strengthens the restart leg (native per-call approval). One
  ordering rule worth writing down: NEVER restart before exporting — a restart can roll or truncate
  the very log that is the evidence. The loop in §C3 happens to order correctly (export at 5,
  restart at 9); make it a stated rule, not an accident of the example.
