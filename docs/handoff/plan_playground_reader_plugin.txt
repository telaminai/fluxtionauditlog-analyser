THE BLOCKER, AND WHY IT IS WORTH STATING
M31.5 defers the separate `analyser-reader-spi` artifact and says "plugin authors compile against the
fatjar meanwhile". I checked what that means in practice for someone outside this repo:

  · the analyser pom is `com.telamin:fluxtion-auditlog-analyser:0.0.0-SNAPSHOT`, with NO
    distributionManagement — it is published to no Maven repository, so `mvn` cannot resolve it;
  · but GitHub releases DO carry a real jar: `v1.12.0`,
    `fluxtion-auditlog-analyser-1.12.0.jar` (2,127,709 bytes), alongside `SHA256SUMS.sha256`.

So "compile against the fatjar" is achievable but not automatic, and every plugin author will hit
this. The example therefore has to answer it, visibly, rather than assume a resolvable dependency.

  CHOSEN: a `setup.sh` that downloads the released jar, VERIFIES IT AGAINST THE PUBLISHED SHA256, and
  `mvn install:install-file`s it into the local repo; the pom then depends on it as `provided`.
  Verifying the hash is not ceremony here: the FAQ's own trust boundary says installing a plugin jar
  is arbitrary code execution, and an example that teaches plugin authors to curl an unverified jar
  would undercut the sentence the analyser asks users to rely on.

  REJECTED, recorded so they are not re-proposed:
   · `<systemPath>` — deprecated, non-portable, and hides the version;
   · vendoring the SPI interfaces into the example — a second copy of a compatibility surface, which
     is the exact failure this collaboration has spent two days paying for;
   · waiting for M31.5 — it needs a multi-module build and is the owner's call, and this slice does
     not need to block on it.

  ASK BACK (not blocking): when M31.5 lands, this example should switch to the published SPI artifact
  and `setup.sh` should disappear. Worth a line in M31.5 so the cleanup is not forgotten.
