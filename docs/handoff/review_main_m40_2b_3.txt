2. F1 — A LOGGER UNDER ANY OTHER NAME WAS EXCLUDED — fixed here
================================================================================
The rule "no supertype ⇒ nowhere an inherited auditLog could come from" is right about INHERITANCE and
silent about the other way a class holds a logger: a field, handed in or built. The belt-and-braces
check protected against that only when the field was literally named `auditLog`:

    class A { private EventLogger log; void f(){ log.info("x", 1); } }   →  SILENT_BY_CONSTRUCTION

That is a node that demonstrably logs, dropped from the denominator — the false exclusion the class's own
javadoc calls "the harder error to notice", and exactly the direction the author asked to have challenged.
Fix, one condition: any mention of the logger TYPE (`EventLogger`) or the contract (`EventLogSource`) in
the body, not just the field name, keeps the node counted (UNKNOWN). Pinned by
aLoggerUnderAnotherFieldNameIsUnknown_neverSilent. The demo's spreadCalculator still excludes (its body
names neither), so the 1.0 stands on the shipped fixture.

3. NOTES — not blocking
================================================================================
N1 · A class that logs through a HELPER without naming the type (`Loggers.forNode(this).info(…)`) is still
     excluded. No text check catches that; only following the helper would. It is an unusual shape and the
     residual risk should be stated in the javadoc as the boundary of what "silent by construction" can
     prove from one file — the honest claim is "this file gives no way to reach a logger", not "this class
     cannot log".
N2 · declarationHeaderOf finds the FIRST `class <Simple>` in the file. For `p.B$A` with a top-level `A` in
     the same file, it reads the wrong class. Rare; a nested lookup that prefers the path through `$` would
     close it. Recorded, not fixed.
N3 · M40.3's choice — read the level from records, not the graph — is right and well argued: the GraphML
     carries no level and a build-time default is overridden at runtime. The lower-bound discipline
     ("nothing finer than INFO appears; the log cannot tell threshold from silence") is the correct claim,
     and attaching the note only when a gap exists is the right restraint: a caveat on a perfect score would
     teach people to ignore it.
N4 · The tracker's "COMPLETE" is honest about M40.2c (a project-local base that itself extends
     EventLogNode → UNKNOWN, counted). Correct-but-conservative is the right default here; close it when
     someone hits it.
