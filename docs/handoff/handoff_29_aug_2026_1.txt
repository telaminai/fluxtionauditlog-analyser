3. DECISIONS FIXED FOR THE AMENDED CONTRACT
================================================================================

D-X1 — ONE VERSIONED CONTRACT, OWNED HERE

The final cross-repository table lives in spec-onboarding-example.md and carries `M19 bundle contract v1`.
It names every field/path/command and the repository that produces and consumes it. This coordination
brief remains live correspondence; it is not a second normative definition.

D-X2 — REPOSITORY OWNERSHIP

  Analyser repository owns:
    · canonical SKILL.md content;
    · profile parsing/context/Project-panel representation;
    · key-file management UI and its value-safety boundary;
    · `New project…` offers;
    · resolved Codex/Claude/generic MCP setup;
    · the final cross-repository bundle bench.

  Mongoose repository owns:
    · the processor's keyless runtime/start path;
    · real audit-record production and file lifecycle;
    · exact start, stop and regenerate entry points;
    · effective build-key resolution and build diagnostics;
    · Mongoose-native tests proving those behaviours.

  Playground repository owns:
    · bundle generation and exact project-relative layout;
    · selecting and copying the pinned canonical skill tier at generation time;
    · substituting project-specific commands/paths and rejecting unresolved markers;
    · generating README.md, CLAUDE.md, AGENTS.md and the analyser profile consistently;
    · skills-source retrieval and safe source provenance;
    · generator tests for the complete downloaded artifact.

No session edits another repository's owned artefact to make its own tests pass. Interface corrections go
back through the contract and are accepted by both sides before either implementation changes.

D-X3 — KEY CONTRACT: V1 DOES NOT GUESS AN EFFECTIVE BUILD WINNER

Current Fluxtion Builder 1.0.64 resolves `-Dfluxtion.apiKey` over `apiKey` in the configured/default key
file. It does not itself read `FLUXTION_API_KEY`. Therefore:

  · the canonical v1 sources are the system property and the key file;
  · the preferred writable home is `~/.fluxtion/fluxtion.apiKeyFile`, `apiKey=...`;
  · `FLUXTION_API_KEY` is NOT documented as effective unless the Mongoose/build implementation explicitly
    maps it to the builder, with a test proving the real generation call receives it;
  · the startup path never requires a key when the generated processor is present;
  · key preflight belongs only to regenerate;
  · the analyser never claims which source a separate Maven/JVM build used.

For M19 v1, choose the smallest honest UI: the analyser may write the canonical file and report only
locally observable setup facts such as `canonical key file present`; it must not render `your build used
the file/environment/property`.

If the owner later requires effective-build provenance, that is an additive contract: the build owner
emits a VALUE-FREE result and the analyser labels it `build-declared`. It must define schema/version,
freshness and processor/build identity before implementation. No key value, hash of the key, command-line
option or secret-bearing path may enter the result. Do not invent that result independently in either
repository during v1.

D-X4 — AUDIT OUTPUT IS NOT A NORMAL MESSAGE SINK

Fluxtion business sinks registered through DataFlow.addSink/DataFlowConnector.addSink are not audit-log
processors. Audit records are delivered through DataFlow.setAuditLogProcessor(LogRecordListener), or the
Mongoose audit service built on that mechanism. The Mongoose implementation must prove that the configured
file contains analyser-readable audit records. A growing business-output file is not acceptance evidence.

The embedded host tier is analyser-owned canonical content and remains blocked until its complete
setAuditLogProcessor/file-lifecycle route is grounded. The Mongoose/playground session must not copy the
currently incorrect embedded skill into a bundle.

D-X5 — SKILLS HAVE ONE SOURCE OF TRUTH

Canonical content stays under this repository's docs/skills/. A generated Mongoose bundle takes `common`
plus the `mongoose` host tier at a pinned analyser-repository revision. The playground does not maintain a
fork.

The accepted v1 set must cover, with project-real procedures:

  · start;
  · stop;
  · exact audit-log location/opening;
  · record a run, if the bundle claims recording;
  · replay and an actual comparison of outputs, if the bundle claims replay;
  · regenerate after a graph/design change, with the key prerequisite at that point only.

A template may substitute explicitly marked fields when generating the copy. The generated bundle MUST
contain no `TODO(bundle)` and no placeholder command/path. Name/description/frontmatter and profile
runbook declarations must describe the same final files.

D-X6 — BUNDLE PATHS ARE PROJECT-RELATIVE AND GENERATED ONCE

The signed contract table must give one value for each generated project:

  · audit log path;
  · GraphML path;
  · generated processor source path and processor FQN;
  · source roots;
  · start command;
  · stop command;
  · regenerate command;
  · skill paths;
  · `.analyser/project.fluxtion-settings` fields.

Values may contain a generator-known project/deployment name, but after generation they are concrete
project-relative values. README, CLAUDE/AGENTS, skills, profile and tests are generated from that single
model. The analyser does not infer an unopened log path, and a skill must not tell an agent that context
knows a log which has never been opened.

D-X7 — MCP SETUP USES THE ANALYSER'S RESOLVED ROUTE

The bundle never ships `java -jar /path/to/...`. Its client-neutral instruction is:

  1. install/start the analyser through the documented current route;
  2. open `AI ▸ Connect an AI client…`;
  3. use the exact resolved Codex, Claude Code or generic configuration shown there;
  4. verify connection with MCP discovery and `analyser_context`.

The basic path and AI path are stated separately: running the example and inspecting its log has the
documented Java/analyser prerequisites; AI operation additionally requires a supported MCP client and any
client entitlement. Do not retain the governing `only a JDK` headline for the full AI-assisted promise.

D-X8 — skills.source BELONGS TO THE GENERATOR, NOT THE PROJECT OR ANALYSER RUNTIME

Skills are late-bound at bundle-generation time. Therefore the control named `skills.source` belongs to
the playground generator's machine/service configuration. It is never read from downloaded project input,
the analyser project profile, or at analyser/runtime use.

The minimum v1 retrieval contract must define:

  · one deterministic index/layout and its contract version;
  · canonical, corporate mirror, local/air-gapped and explicit `none` modes;
  · host-tier selection;
  · the difference between `none`, not found, invalid content and transport failure;
  · bounded content and rejection of unresolved markers;
  · a credential-free source identity recorded in the generated bundle.

Separate control from provenance. A profile may carry an inert, declared `skills.provenance` string for
context/Project-panel display only if the amended analyser schema accepts it; it must never carry
`skills.source` or cause a fetch. URLs with user info, query, fragment or credential-shaped content are
refused before storage/display. Hash pinning, redirect restrictions and signing are recommended hardening,
not minimum v1 acceptance unless promoted by the signed contract.

D-X9 — VERSION COMPATIBILITY MUST HAVE AN ENFORCER

`x-analyser-min-version` is not decorative. At minimum the generator checks each selected skill against
the analyser version its README requires and fails generation on incompatibility. The bundle names that
minimum and the setup instructions account for JBang caching. Merely writing frontmatter which every
consumer ignores is not acceptance.

D-X10 — TRUST BOUNDARY

The bundle and analyser may state what the declared graph and supplied record support. They do not claim
to authenticate the record's origin, completeness, semantic correctness or freedom from author influence.
Do not add stronger `independently proven` language in cross-repository docs.

================================================================================
6. CROSS-REPOSITORY ACCEPTANCE — NOBODY CLAIMS THIS FROM LOCAL TESTS ALONE
================================================================================

The integration is complete only when a freshly generated, downloadable-equivalent bundle proves:

  1. Its inventory exactly matches `m19-bundle/2` and declares that version.
  2. No key is configured; the committed processor builds/starts without regeneration.
  3. The real Mongoose runtime captures Chronicle records; the bundle's own export command writes
     analyser-readable YAML to the declared project-relative path.
  4. The declared GraphML fits the written log and source navigation reaches bundled source.
  5. The generated profile declares every shipped skill with its final description/path.
  6. No shipped file contains `TODO(bundle)`, `/path/to/`, a secret, an absolute developer path or an
     invented command.
  7. The analyser opens graph-first, then the log, and reports audit readiness/pairing honestly.
  8. A supported client uses the analyser's resolved MCP setup; discovery and `analyser_context` succeed.
  9. Start, clean stop and export/open skills work exactly as written.
 10. Regeneration without a key fails at the documented step with the documented remedy; the initial run
     remains a success. A valid-key regeneration is tested only in an authorised credential-bearing
     environment, with the value absent from all captured output.
 11. `skills.source=none`, canonical and one non-canonical fixture behave distinctly; project input cannot
     redirect the source.
 12. The complete supported path is timed against the prerequisite tier it actually requires.

The existing `tools/bench/loop-bench.py --stub --launch` remains a regression check for the brokered seam.
It is not evidence that a real starter produced the native audit file or that the playground generated a
correct bundle. Extend or add a bundle-mode bench only after the real generator output exists.
