REQUIRED CHANGE

R1 — P2 — The new stripper can consume real Java after the header.
VERIFIED. examples/fixture-generator/pom.xml:116-117.

The expression is anchored at the start of the file, but its lazy wildcard stops
at the first SPACE-prefixed " */" followed by LF, not the first Java "*/".
A valid opening notice whose terminator loses the leading space therefore allows
the match to cross out of the comment and into the package/imports and subsequent
documentation. This is a formatting-sensitive source-deletion boundary.

Concrete input, using the exact prefix the production expression recognises:

    /*
     * This source code is protected under international copyright law.
     * DEMO notice
    */
    package com.acme.demo.generated;
    /** DEMO later documentation */
    public class NoSpace {}

I copied the candidate fixture pom into a scratch project, placed this file in its
configured generated-source directory, and ran only:

    mvn -q org.apache.maven.plugins:maven-antrun-plugin:3.1.0:run@strip-generated-attribution

The result was exactly:

    public class NoSpace {}

The named assertion failed:
    UPS2-STRIP: real Java package declaration was deleted

The positive control, differing only by a space before the header's closing */,
kept its package and later documentation. Both outputs compiled: the control
produced com/acme/demo/generated/Normal.class, whereas the damaged source produced
NoSpace.class in the default package. This is not a compiler-error witness.
The current hosted generator uses the expected spacing and the candidate's
committed sources are NOT damaged. The failing scenario is a legal variation in
the input that this newly introduced source-transform step processes.

Remedy: identify the first comment terminator independently of its indentation,
and never scan beyond it while deciding whether the leading comment is the notice.
Either leave an unrecognised header untouched and fail a publication check, or
remove only that comment. Test normal, column-zero and CRLF terminators, a second
comment, and package/import/code preservation using the actual stripping task.

There is also no maintained notice-return check to close this correction under
rule 8. I disabled ONLY the notice regex, kept attribution stripping enabled, and
regenerated all three DEMOs through the real plugin. All six Java copies acquired
"This file is confidential". GeneratedSourceIsPublishableTest still passed
2 / 0 / 0 / 0; FixtureGeneratorToolchainTest passed 3 / 0 / 0 / 0.
The publication test at lines 62-76 checks only the four sweep terms. Add a cheap
check of the chosen DEMO notice policy plus a negative control for the strip task;
the two successful regenerations in the handoff are evidence, not a future guard.
