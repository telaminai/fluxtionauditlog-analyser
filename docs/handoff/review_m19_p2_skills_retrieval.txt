VERDICT

CHANGES REQUESTED. The retrieval core has a good shape and most of the contract is present, but P2 is
not yet closed and the source-mode matrix must not be treated as acceptance evidence yet.

The blocking defect is concrete: `skills.source=none` deletes both `.SKILL.md` files, while bundle.ts
still statically imports them. The production build then fails before it can emit the promised
runbook.count=0/provenance=none bundle. Content validation also accepts body text as "frontmatter" and
accepts malformed version strings through parseInt. A non-none index can select zero Mongoose skills
and still return `ok`. Finally, the configured default canonical URL returns 404 for the required index;
the local `--declare-canonical` relabelling escape hatch does not make the default HTTPS mode live.

The later 266132a Download-seam change does not touch the P2 retrieval logic. Its packaging correction
is independently accepted here: the focused real-zip test passes and the analyser handoff records the
same generated artifact passing bundle-bench 49/49.

2. FINDINGS
================================================================================

F1 (BLOCKING — `none` CANNOT BUILD): vendor-skills.mjs writeSnapshot removes every existing
`.SKILL.md` when the selected file set is empty. bundle.ts nevertheless has unconditional static raw
imports for load-audit-log and run-mongoose-server. The dry-run test at vendor-skills.test.ts:142 never
writes the snapshot or imports the generator, so it misses the integration failure.

Reproduced in a disposable checkout:

  node scripts/vendor-skills.mjs --source none
    -> manifest mode none, provenance none, skills []; both skill files deleted
  ./node_modules/.bin/vite build
    -> Could not resolve "./skills/load-audit-log.SKILL.md?raw" from bundle.ts

Required correction: make the generated content registry genuinely mode-aware (for example an eager
glob or generated content module that can be empty), or retain build-only imports without shipping them.
Then test the real sequence: vendor none into a disposable checkout -> production build -> actual
Download zip -> bundle-bench. Assert no `.claude/skills`, runbook.count=0 and provenance none.

F2 (HIGH — INVALID CONTENT PASSES AS VALID FRONTMATTER): frontmatter() searches the entire document for
three matching lines. It does not require opening/closing `---`, does not confine fields to that block,
and does not reject duplicates. A file containing only:

  # no frontmatter delimiters
  name: fake
  description: body fields only
  x-analyser-min-version: 1.12.0

returns outcome `ok`. That contradicts "valid ... frontmatter" and is stricter downstream:
bundle-bench's actual frontmatter parser rejects the same file.

The version check has the same false-pass class: Number.parseInt accepts
`x-analyser-min-version: 1.12.0junk`, and vendorSkills returns `ok`. The analyser checker requires the
contract's exact three-part numeric version.

Required correction: parse exactly one leading `---` frontmatter block, reject duplicate/missing fields,
validate name/description there, and require both minimum and named analyser versions to match
`digits.digits.digits` before comparison. Add both reproduced false-pass fixtures.

F3 (HIGH — A NON-NONE SOURCE MAY SELECT NOTHING AND RETURN `ok`): validateIndex filters common plus the
requested tier but does not validate the selected bundle set. An otherwise valid index containing only
an embedded entry returns:

  {"outcome":"ok","provenance":"local@r1","skills":[]}

The generated Mongoose bundle then has non-none provenance but no required load/run-export-stop
runbooks. bundle-bench correctly rejects that artifact, but the build/release retrieval boundary should
not call the source valid.

Required correction: for the Mongoose snapshot, require the supported selected names exactly once
(`load-audit-log`, `run-mongoose-server` at present), reject duplicate selected names/output filenames,
and distinguish this as invalid-content. Literal none remains the only successful zero-skill mode.

F4 (BLOCKING P2 ACCEPTANCE, CROSS-REPO OWNER INPUT — DEFAULT CANONICAL MODE IS NOT LIVE): the configured
default is https://fluxtion-playground.dev/skills, but on 2026-08-29 its required
`m19-skills/1/index.json` returns HTTP 404. Running the real CLI with no `--source` exits 1 with the
distinct not-found result. This is honest error handling, but it means "defaults to canonical" is not
an operational source mode and the proposed canonical matrix cannot run.

`--declare-canonical` is only a temporary manual assertion: it fetches a local root and then rewrites
local provenance to canonical without comparing bytes or the revision to a canonical HTTPS source. The
currently committed bytes do match the stated analyser commit (verified above), so this is not a finding
against that snapshot; it is not a reproducible implementation of future canonical retrieval.

Required owner decision/correction: publish the versioned index and files at the configured root, or name
and configure another stable HTTPS root controlled by the canonical-content owner. Once live, remove the
relabelling workaround. Pin a real default-CLI test against a controlled canonical fixture/server; do not
make ordinary unit tests depend on the public network.

F5 (MEDIUM — MODE INTEGRATION IS NOT TESTED): the committed-snapshot test hard-codes mode canonical and
canonical provenance, while the `none` test is dry-run only. Therefore a legitimate mirror/local/none
snapshot is not exercised through bundle.ts, the project generator, production build or Download zip;
for mirror/local the consistency test itself would fail merely because the mode is not canonical.

Required correction: make snapshot consistency assertions mode-aware, and add an isolated matrix that
vendors canonical, none and a clean mirror/local fixture, then loads the generator and checks the actual
zip with bundle-bench. This matrix should follow F1–F4, not precede them.

F5a (HIGH — DOWNLOAD TEST FAILURE IS SWALLOWED): the matrix runs Vitest through
`... | grep ... || true`. With `set -o pipefail`, `|| true` still converts every Vitest or grep failure
to success. A later failure after an artifact is written, or a stale/artifact-producing failure mode,
can therefore continue into bundle-bench and report the leg green. The best-effort WIP rsync is also
silently ignored, so the script may test archived HEAD while claiming to test pending changes.

Required correction: preserve the test runner's exit status (for example, pipe through `tee` with
pipefail and inspect/print the summary only after success). Either test committed HEAD only and remove
the WIP-copy claim, or make that copy fail closed. Add a deliberate failing fixture proving the matrix
exits non-zero before calling the leg successful.

F5b (MEDIUM — LEG IDENTITY AND HTTPS MIRROR ARE NOT PROVED): the script prints `mode` and `provenance`
with grep but never asserts the expected values for the named leg. Its third leg is `file:` local, which
uses readFileSync; an HTTPS mirror uses fetch plus HTTP-status and redirect handling. The handoff's claim
that these are an "identical non-canonical code path" is therefore false. The live canonical leg does
exercise the ordinary successful network-fetch path, and the separate parser/provenance/checker tests
are useful, but no test currently exercises mirror fetching or same-origin/cross-origin redirects.

Required correction: assert each leg's exact mode/provenance family and run the third actual-zip leg
through a controlled credential-free HTTPS mirror fixture. Pin at least successful mirror retrieval and
the specified cross-origin redirect refusal at the retrieval seam. A local leg may remain as additional
air-gapped coverage; it cannot stand in for HTTPS transport behavior.
