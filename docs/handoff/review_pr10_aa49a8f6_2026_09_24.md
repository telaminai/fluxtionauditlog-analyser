### R1 — High: duplicate global chart definitions abort log opening after partial binding

**RUN and READ.** `config/ConfigStore.java:90` accepts duplicate graph names. Opening a
log reaches `ui/MainFrame.java:3998`, where `GraphTabs.restore` calls

`config/SavedGraphMerge.java:64`). The exception escapes the EDT success callback:
`core/Background.java:40` schedules it outside the worker's `try/catch`.

Concrete input: an isolated `user.home` with two charts named `Same`, saved using the
real `ConfigStore.save` to `.fluxtion-analyser/config`; no active project; open a valid
one-record log. The action accepts the asynchronous open, then the EDT throws:

```text
java.lang.IllegalArgumentException: Duplicate chart name 'Same': give each saved chart a unique name before loading or saving
GLOBAL_STATUS=Loading <isolated-fixture>/sample.yml …
GLOBAL_STORE=true
GLOBAL_GLASS=false
```

The exception was captured by an EDT uncaught-exception handler in the probe. The status
remains `Loading`, although the store and some panels have been bound. The rest of
`onLoaded`, including its completion status and subsequent configuration, is skipped.
This is not a claim that the entire event thread stops or that a blocking glass pane
remains: the probe explicitly observed `GLOBAL_GLASS=false`. The config file remained
byte-identical during this trial; I did not reproduce data deletion.

**Important narrowing of the PR's concern:** a duplicate *project profile* follows a
different path. `ProjectProfile.load` calls `SettingsShare.preview` before clearing the
target (`config/ProjectProfile.java:292`) and catches the validation exception at line 326.
My separate probe opened such a profile through the actual `ActionExecutor` while another
project was loaded. It returned `ok=false` with the duplicate-name explanation, preserved
the file bytes and preserved the existing chart/configuration. That path does not reach
`applyProjectSettings` with these duplicates. The global path does fail; a clean project
refusal does not establish safety for all legacy configurations.

**Required:** handle duplicate global definitions before partially applying a log, with
an actionable user-visible diagnosis and preservation of both definitions. Do not silently
choose a winner or simply turn the late throw into an uncaught startup throw. A refusal or
a preservation-oriented migration needs its own end-to-end regression and mutation. If
migration changes names or chooses a repair policy, obtain that policy from the owner.
The review does not choose it. The premise that older releases could create duplicates
makes this a compatibility issue, not merely hostile-input hardening.
