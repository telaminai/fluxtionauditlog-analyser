2. The A4 correction is true in code: Find skills… OFFERS; it does not add — CORRECT
================================================================================
PointerDialog.java: the Find skills… button builds a JList of SkillDiscovery.Candidate, shows it in a
JOptionPane with the caption "Nothing is added until you choose one and confirm it", and on OK calls
addRunbook(parent, config, projectRoot, picked.path(), picked.name(), picked.description()) — the SAME
method a hand-typed pointer uses. That method opens the Add runbook dialog with the fields PREFILLED
and only on its own confirm(), after Runbooks.refuse / refuseDescription pass, does
config.runbooks.put(...) run (line 195). Cancel at either step stores nothing. So: discovery changes
where the suggestion came from, never whether a person declared it — and context.runbooks[] is served
from config.runbooks, so nothing reaches it without that put. The SkillDiscoveryTest header says
"to OFFER"; onlyOffersWhatCouldActuallyBeSTORED pins that no refusable path is even offered. The owner's
eyeball CHECK B (2026-08-28) exercised this exact path live: prefilled, then stored what the person left in
the box. The report's correction of the earlier review's "surfaced … with no work on either side" is
therefore right, and it was right to make it.
