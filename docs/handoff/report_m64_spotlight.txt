1. THE SPEC'S ONE WRONG ASSUMPTION — AND WHY IT MATTERS MORE THAN ANYTHING ELSE HERE
================================================================================
D-SP1 and D-SP5 both rest on: "`screenshot` already paints the glass pane because it captures the window the
app painted". IT DOES NOT. The verb paints getContentPane() (or one panel for a scoped shot). The glass pane is
a sibling of the layered pane under the root pane — part of neither. The whole verification loop the spec
designs (spotlight → screenshot → "is it lit where I meant?") would have returned an UNDIMMED image of a window
that was visibly dimmed on screen: the tutor would have been checking nothing, and told it had checked.

Found by the display test on its first real-frame run: brightness outside the cut-out `696 → 696`. Fixed by
compositing: SpotlightOverlay.paintOnto(g, painted), called from the screenshot verb after it paints, translated
so the cut-out lands on the same pixels it covers on screen — for the default shot and for the scoped ones.
MUTATION-CHECKED: remove that one call and SpotlightFrameTest goes red with exactly those numbers. The spec is
corrected in place (rule: fix the spec too; never silently diverge).

2. WHAT WAS BUILT, SLICE BY SLICE
================================================================================
M64.1  ui/SpotlightTarget — the closed vocabulary (15 forms in 8 families), parse(), and
       resolve(name, Surface): parse → reveal → measure → LIT | NOT_VISIBLE | UNKNOWN. `Surface` is three
       methods (reveal, bounds, whyNotVisible); the frame implements it with Swing, the tests with a map.
       An UNKNOWN name never touches the surface. The vocabulary text the verb schema prints
       (llm/SpotlightVocabulary — VerbSchemas cannot depend on ui) is asserted identical to the parser's.
M64.2  ui/SpotlightOverlay — the frame's glass pane. Dim, cut out, ring, caption, arrow; out on any mouse press
       and on Escape. Caption styled after the topology callout and TAGGED "assistant": it is testimony (D-SP2).
       ui/SpotlightGeometry — "the caption sits in whichever quadrant has room" as arithmetic: below, above,
       right, left, else INSIDE the cut-out rather than off screen; always clamped into the frame.
M64.3  The verb, along the established path (VerbSchemas → dispatcher → ActionExecutor → AppControl → frame).
       ONE list — SpotlightTarget.VIEW_CHANGING_VERBS — applied in ONE place (ActionExecutor.render, before the
       verb runs). `context.spotlight {target, caption}` only while lit, and ABOVE context()'s fresh-start
       early return. SpotlightIsNeverPersistedTest checks the CODE: no package that persists anything
       (config, report, graph, export, session) may contain the word.
M64.4  SpotlightFrameTest — real frame, real screenshot verb, pixel-sampled: INSIDE the cut-out the image is
       byte-identical to the unlit shot; OUTSIDE it is dimmed; `context` reports the target; a view-changing
       verb clears it; an unknown node is refused and lights nothing. Added to ci.yml's ui-frame job in BOTH
       places: the -Dtest list and the fail-if-skipped guard.
M64.5  docs/skills/common/guided-start/SKILL.md — a "Point before you speak" section and one spotlight line per
       beat. Written so a client on an analyser OLDER than the verb carries on: `x-analyser-min-version` stays

       gates for a verb the tour does not need). Re-pinned by the established two-commit practice.

Panel accessors added, all read-only: TopologyCanvas.screenBoundsOf (+ static toScreen, tested),

3. DECISIONS I TOOK WHERE THE SPEC LEFT ROOM — each is reversible
================================================================================
· The spec's two "Open for the owner" questions were taken AS PROPOSED (scroll to the target; one-line caption),
  because the owner asked for the implementation without answering them.
· `coverage` lights the Topology tab's own status line. There is no separate "coverage panel" in the UI; that
  line is where the pairing/coverage verdict is stated for a person.
· `project:<row>` lights a SECTION of the Project panel, mapped log→Audit log, graph→Graph,
  processors→Event processors, roots→Source roots.
· A REFUSED spotlight leaves a standing one lit. The spec says "a new one replaces the last"; it does not say
  what a FAILED new one does. Fail-closed seemed right: a failed request changes nothing.
· The dismissing click is CONSUMED — it puts the spotlight out and does nothing else. Passing it through would
  make "click anywhere to dismiss" also press whatever was under the pointer.
· A SIXTEENTH VERB. The owner confirmed `handoff` as the fifteenth the same day with the rider that the next
  verb clears the same bar. Nothing points: goto/topology SELECT, screenshot RECORDS. The four guard tests
  state both additions and their reasons. The spec itself specifies the verb (M64.3), so I did not treat this
  as a fresh decision — but it is the second growth of the surface in one day, and worth a conscious nod.

5. WHAT A REVIEWER SHOULD ATTACK
================================================================================
· THE CAPTION CAN COVER CONTENT. Placement avoids the CUT-OUT and the frame edge; it does not avoid other
  things on screen. In spotlight.png the caption box overlaps the QuotePublisher node beneath. For a transient
  pointer I judged that acceptable; a reviewer may not.
· FIRST-SHOW LAYOUT. reveal() calls sideTabs.validate() so a just-selected tab has a size before it is measured,
  and the adapter re-measures via invokeLater and on resize. The canvas's own first fit-to-view happens on a
  queued resize event, so the ECHO's bounds can be stale for a Topology tab shown for the very first time, while
  the overlay itself corrects a moment later. The display test sleeps 300 ms for this. Is there a cleaner way?
· THE OVERLAY SWALLOWS INPUT WHILE LIT. The glass pane is visible and has a mouse listener, so every press goes
  to it. That is the design ("any click dismisses") but it means a person cannot interact with the app while a
  spotlight is up without first dismissing it — one extra click. Keyboard focus is NOT taken.
· THE HUMAN HAS NO WAY TO LIGHT ONE. By design (it is a tutor's act) — but it also means the only way to see a
  spotlight is an agent, which is why the eyeball evidence is a generated screenshot and not a menu item.
· `SpotlightIsNeverPersistedTest` names the persisting packages by hand. A NEW persisting package would not be
  covered until someone adds it; the test fails if a listed package disappears, but not if one appears.
