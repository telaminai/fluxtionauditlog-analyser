1. THE DEFECT, REPRODUCED BEFORE IT WAS FIXED
================================================================================
Driving the shipped app: open sample.yml (21 records), then open the supermarket POC's
StoreProcessor.graphml (301 nodes, an entirely unrelated system). The app holds both happily and
`coverage` reports 301 declared nodes against a 21-record log that shares nothing with it. There was
no way back short of restarting: File had "Close project" but no "Close log", and onLoaded() never
touched the topology.

That is the M33 defect class — a confident answer computed from mismatched inputs.

================================================================================
2. WHAT SHIPPED — M35.1
================================================================================
closeLog() / closeGraph() / resetAll() in MainFrame, File menu items enabled only when there is
something to close, and `open {close: "log"|"graph"|"all"}` for agents — on the EXISTING verb
rather than a 15th one, pinned by test, because closing is the same lifecycle concept as opening.

THE RULE (owner's, from the brief) is implemented as written:
  DERIVED clears   store · table model · filter · search · time slider + histogram · event
                   checklist · summary · detail · flags + findings (per-file row indices) ·
                   topology execution shading + step cursor · follow · time-order report · status
  PROFILE survives named graph specs · named focuses · source roots · saved reports · project
                   settings. closeLog() deliberately does not go near `config`.

The panels had bind(...) and no unbind, so explicit clear()/unbind() were added to SummaryPanel,
EventFilterPanel and GraphTabs, plus clearGraph()/clearExecution() on TopologyPanel. Deliberately
NOT done by binding a fake empty store: `store == null` is the "no log is loaded" sentinel used
across the verb surface, so an empty store would make the app believe a log was open. Explicit
clearing also makes each panel own what it clears — the brief's "a half-cleared app is worse than
an uncleared one".

SummaryPanel needed real work: rebuild() returns early on a null store, which would have left the
previous log's rows on screen. clear() blanks the model rather than relying on the guard.

The LOADED GRAPH is not touched by closeLog(). It is a separate artefact the user opened
deliberately; only its shading goes. closeGraph() is its counterpart, and the status line names a
graph still loaded after the log closes so the pairing is never silent.

8. M35.2 — COMPLETE, and it uncovered a second defect
================================================================================
GraphPairing (pure, 7 tests) reuses NodeCoverage.of() as the brief required — the comparison
"which logged instanceIds does this graph declare?" already existed, and a second scorer would be a
second answer to one question. Verdict: keep when a majority of what the log writes is declared;
otherwise close, ALWAYS with the counts, so the decision is checkable rather than magic.

IT ACTS RATHER THAN OFFERS, and the reason is the agent path. An offer was considered — it matches
D-I3a's announce-never-forbid — but a modal question on every log open is friction for humans and
UNANSWERABLE for an agent, so it would be silently defaulted, and silently defaulting to "keep" IS
the defect. Closing is safe, one action to undo, and the comparison use case (build A's graph against
build B's log) is served by reopening the graph after the log — an explicit act rather than an
accident. Recorded here because it departs from the codebase's usual preference.

--------------------------------------------------------------------------------
D4 · FINDING — a modal dialog inside onLoaded can strand an agent-driven open
--------------------------------------------------------------------------------
The first cut of M35.2 did not fire, and the reason is worth more than the fix. onLoaded() assigns
`this.store = loaded` and then calls maybeOfferProject() (M20.3), which shows a MODAL
JOptionPane. Everything after it — the table, filter, slider, and my re-pair — waits for a human
click. On the agent path there is nobody to click.

The dangerous part is the ORDER: `store` is already assigned, so while the app sits behind a dialog
nobody can see, the NEW log is live and answerable against the OLD graph. Driving it over REST
produced exactly that: 21 records reported, coverage answering "301 declared, 0 covered" — the M35
defect, occurring inside the code meant to prevent it.

FIXED HERE only by moving repairLoadedGraph() ahead of maybeOfferProject(), so the pairing is
settled before anything can block. THE UNDERLYING HAZARD REMAINS and is not M35's to fix: any modal
in the load path strands an agent-driven open, and every verb after it blocks on the EDT. It did not
reproduce on the final run only because projectDetect remembers a declined offer for that log.
Recommend a slice (M20 or M35.7): the project offer must be non-blocking, or suppressed when the
open came from the action socket rather than a human.

9. M35.7 — COMPLETE (the defect M35.2 uncovered)
================================================================================
Opens that arrive from the ACTION SOCKET no longer show the modal project offer. They record it and
report it as data: `context.projectOffer` names the settings file and states plainly that loading a
project replaces source roots, event processors, graphs and hidden columns — so it is offered and
never applied. The status bar names it too. Opening by hand is UNCHANGED and still gets the dialog.

Mechanism: openLocation(location, fromActionSocket). The flag is CONSUMED AND RESET in
maybeOfferProject, so a human chooser following an agent open cannot inherit "do not ask" — the
default has to be the interactive one, and defaulting the other way is the class of bug this whole
milestone is about.

VERIFIED with a fixture that makes the offer genuinely fire (a log inside a directory carrying
.analyser/project.fluxtion-settings — the first attempt proved nothing because the offer never
triggered, and a test that cannot fail is not a test):
    open {log: <inside a project>}   -> ok
    context.records                  -> 21
    context.projectOffer             -> {"settings": ".../project.fluxtion-settings", "note": "..."}
    filter verb 4s later             -> ok, no human present
Before this change that sequence left the app behind an invisible dialog with every verb blocked.

D5 · ACCEPTING the offer still needs a verb. There is no project verb today, so an agent can see the
offer and cannot act on it. That is deliberate scope: opening a project is a large mutation
(source roots, processors, graphs, hidden columns) and deserves its own decision about confirmation
rather than being smuggled in here. Recommend it as M20.6 — `open {project: path}` with the echo
naming everything it replaced.
D6 · The human path is unchanged BY CONSTRUCTION rather than by test: openLocation(String) delegates
with false, the recent menu goes through it, and the flag consumes to false. Swing, so eyeballed
reasoning rather than an assertion — added to the eyeball list as E5.

10. M35.3 — COMPLETE (switch processor without reopening the log)
================================================================================
Opening a graph against an already-open log now judges the pair immediately and reports it in the
verb echo, so an agent switching processors does not have to call `context` to learn whether what it
just opened fits.

THE ASYMMETRY IS THE DESIGN, and it took a wrong first cut to see it. One comparison, two verbs:
  a LOG arrives and finds a graph  -> that graph is RESIDUE. Nobody asked for it here. CLOSED (M35.2).
  a GRAPH arrives against a log    -> that graph is INTENT. Someone named this processor. KEPT, with
                                      the mismatch announced (M35.3).
Announce-never-forbid (D-I3a) applies where there is an intention to respect; comparing build A's
graph against build B's log is a real forensic act and closing it would destroy the request.

Consequence, and the bug this caught: GraphPairing.reason() now states the FACT and never the
action. The first cut baked "closed — ..." into the reason, so `context.graphPairing.verdict` said
a deliberately-opened graph had been closed when it plainly had not — the tool asserting something
untrue about its own behaviour, which is the defect class this milestone exists for. The callers
supply the verb; the class javadoc was corrected in the same pass, because a doc that contradicts
the code is the same failure one level up.

ALSO FIXED: ActionExecutor.doOpen was discarding the inner result's payload and echoing back only
the path the caller already knew. The pairing verdict never reached the caller. It now carries the
inner echo up.

VERIFIED IN THE RUNNING JAR (POC log open throughout):
  open matching graph  -> {"nodes": 301, "appliesToOpenLog": true, "loggedNodes": 211,
                           "declaredByGraph": 211, "verdict": "the graph declares 211 of the 211..."}
  open unrelated graph -> {"nodes": 10, "appliesToOpenLog": false, "declaredByGraph": 0,
                           "verdict": "...different system or build — kept anyway, because you
                           opened it deliberately (M35.3). A stale graph is only closed when a LOG
                           arrives and finds it there."}
                          still loaded afterwards; coverage answers against the graph the user chose.

D7 · The supermarket POC has only ONE .graphml (StoreProcessorFast is .java only), so the genuine

standing in for the second processor. The code path is identical; the realistic fixture is not

11. M35.4 — COMPLETE (find the graph, never choose it)
================================================================================
GraphmlDiscovery walks the configured source roots, parses each .graphml, and ranks the candidates
against the open log — reusing GraphPairing, which reuses NodeCoverage. One comparison now serves
four callers (M35.2 re-pair, M35.3 switch, M35.4 ranking, coverage), which is what the brief meant
by "do not invent a second scorer".

IT OFFERS AND NEVER SELECTS, which is the whole slice and the thing most easily lost by being
helpful. The best candidate is FIRST, not loaded. Both surfaces say so:
  · File ▸ Find GraphML in source roots… — a picker. Cancel loads nothing.
  · open {discover: "graphml"} — returns candidates and echoes
    "opened": "nothing — this lists candidates; open one with open {graphml}"

Bounded on purpose (depth 12, 25 candidates, 32 MB/file): source trees contain build output and an
unbounded walk of a monorepo is a hang. A truncated scan SAYS SO rather than presenting a partial
list as the whole answer.

VERIFIED IN THE RUNNING JAR, roots pointed at both projects so there was a right and a wrong answer:
  StoreProcessor.graphml        301 nodes  appliesToOpenLog true   211 of 211   <- ranked first
  demo-quote-processor.graphml   10 nodes  appliesToOpenLog false    0 of 211

12. M35.5 — COMPLETE (the profile is the session boundary)
================================================================================
An explicit project switch, create, or close now closes the log AND the graph. afterProjectChange()
is the single shared hook for every project change, so the behaviour lands once rather than at six
call sites (chooser, recent menu, create, close, and the auto-detect path).

WHY UNCONDITIONAL, and not the M35.2 re-pair treatment: a project owns source roots, event
processors, named graphs, focuses and reports. Swap it and all of them change underneath the open
log. Unlike M35.3's graph-open there is no surviving "I meant to compare them" case — nobody
switches profile in order to keep looking at the same investigation through the wrong settings. And
this is the WORST of the M35 holes, because nothing re-checks anything when a profile changes: the
log-open re-pair (M35.2) does not run, so a stale graph would simply persist with new focuses
pointing into it.

THE ONE EXCEPTION, and it is a real bug avoided rather than a nicety: applyProjectResult is also
reached from maybeOfferProject DURING a log load. Ending the session there would close the log that
had just arrived. That path passes endsSession=false and says why in a comment.
