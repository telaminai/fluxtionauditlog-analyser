## Implementation

- `DesignDiscovery.scan` reads only authorised real source roots off the EDT, bounds regular files (10,000),
  metadata (20,000) and UTF-8 reads (2 MiB), and returns path-sorted Spring/builder candidates. It does not follow
  directory or file links into other roots. Over-budget/traversal failure yields no partial list. Individual
  unreadable/oversized files are disclosed by name without erasing readable candidates (review response below).
- `DesignSession` owns discovery state, tickets, supersession and zero/one presentation. It asks typed effects;
  `MainFrame` only performs background reads and reports facts. Accepted profile/restoration and changed roots
  trigger scans. A separate discovery generation avoids losing a valid root scan to an unrelated file glance.
- Released echo keys and order are unchanged; four additions are pinned in `CustomerApiKeysTest`. `nodes` is empty
  until PR2. The `BuilderDocument` text-only shell is introduced here solely to support Java DESIGN text; its
  bounded lexical index belongs to PR2. XML parsing remains unchanged.
- One discovered file is presented as a glance, not silently made the session design. Explicit adoption still
  uses `open {design}`. Several candidates are stated but have no chooser until PR3. Discovery preparation does
  not start a competing explicit read, so a client can immediately use the context path without a retry race.
- Processor and GraphML were regenerated together with the Maven profile, never hand-edited. Generated header
  retained; normal profile attribution stripping applied. A temporary constructor bridge allowed the old committed
  processor to compile during initial generation; removed and regenerated again before verification.

## Response to the independent review at `6c31ef53`

This is the implementer's response, not independent approval. The earlier counts above describe the original
candidate; the following checks describe this correction.

- **Failed-read form:** omit `kind` when an explicit initial read has loaded neither form. A failed refresh may
  retain the last good Java form, but a failed read of a different file cannot borrow it.
  `failedDesignReadNeverInventsASpringForm` reads invalid UTF-8 Java and XML through the real reader;
  its before-fix wrong-result assertion found a fabricated Spring kind. The retained-revision neighbour also passes.
- **Individual read failures:** retain readable candidates and name unreadable/oversized files in the existing
  context `note` and the Design pane. No fifth additive API key was introduced.
  `individualReadFailuresKeepCandidatesAndNameEveryUnreadableFile` combines a readable Java builder, invalid UTF-8
  Java and oversized XML. Before the fix, its candidate-count assertion found zero rather than one.
  `readableCandidateAndReadWarningsReachTheDesignPaneAndContext` verifies both real displayed notes and context,
  including an explicit glance after discovery. A failure-only neighbour does not claim a completed empty search.
- **Whole-scan limits:** the file and metadata caps still return UNAVAILABLE with no partial candidates, with
  distinct reasons. The file-cap test was red before the correction at the specific-reason assertion.
  Root/traversal failures remain whole-scan failures; a known file's content-read failure is a disclosed warning.
- **Small corrections:** removed the dead root-count guard, restricted the echo-key extraction to the method
  body, and shortened the zero-file human line. The extraction regression was red before the correction because
  a later method's key was included. The human line no longer contains an agent JSON example.
