F1 · BLOCKING — “appearance is automatic” collapses registration, invocation tracing and value logging
into two mechanisms when the runtime has three conditions.

The handoff §3b says nodeInvoked “is what makes a node APPEAR” and nodeRegistered hands a logger only to
EventLogSource. fluxtion-runtime 1.0.13 says otherwise:

  EventLogManager.nodeRegistered, lines 107–116
    - constructs an EventLogger for every registered node;
    - injects that logger only when the node implements EventLogSource;
    - stores the logger in node2Logger unconditionally.

  EventLogManager.nodeInvoked, lines 137–148
    - looks the logger up in node2Logger, defaulting to NullEventLogger;
    - calls logNodeInvocation(traceLevel).

  EventLogger.logNodeInvocation, lines 238–242
    - adds the trace only when the configured logger level admits the trace level.

  EventProcessorConfig.addEventAudit()
    - explicitly installs EventLogManager.tracingOff(); addEventAudit(level) installs tracingOn(level).

Therefore the precise contract is:

  1. the generated processor registers its graph nodes with each auditor;
  2. with invocation tracing enabled, an invoked, registered node gets a method/trace entry (subject to
     the configured level);
  3. EventLogSource controls whether the runtime can inject a logger for the node's own values;
  4. with tracing off, an invoked node that emits no value need not appear at all;
  5. an unregistered invocation resolves to NullEventLogger and also does not appear.

This is not a terminology nit. The analyser already distinguishes traced and untraced logs because
absence supports different claims in each. The current wording overstates what an ordinary untraced audit
record proves.

Affected at minimum:

  - handoff_30_aug_2026_2_report.txt §3b;
  - proposals/upstream-content/audit-authoring.md (“Every node that is dispatched appears”);
  - specs/spec-trust-structure.md D-T3 (the “unforgeable” participation/order claim needs a traced-log
    boundary);
  - skills/spring/add-a-node/SKILL.md (“Appearing in the record is automatic”);
  - the round-03/round-05 conclusions and upstream-asks wording that inherit the same split;
  - public Fluxtion issues #21 and #22, which repeat the mechanism as filed.

Keep the useful EventLogSource ask, but correct it to “can receive a logger and record its own values”.
State automatic participation/order only for registered graph nodes in a traced record. The traced demo is
the right proof surface; the untraced demo is not.

F4 · REQUIRED — round 05 records an observed difference, not evidence for the direction “the resources
help”, and its underlying evidence is not reproducible from the repository.

The build-failure table is 3/3 control versus 1/3 treatment. If treated as a simple 2x2 experiment,
Fisher's exact p is 0.20 one-sided (0.40 two-sided). With one task, one model family, one machine and only
three runs per arm, the honest statement is:

  “This round observed fewer build failures in the treatment arm. It is hypothesis-generating and too
   small to infer a direction or effect size.”

“Supports a direction” and “the resources help” over-read it. Correct that wording in the handoff,
spec-authoring-experience D-AX5, round-05/round.md and round-05/prediction.md. “Best available quantitative
signal” may describe which recorded number moved; it must not be presented as a supported treatment effect.

There is also no reviewer-reproducible run evidence under round-05: no exact task/prompt per arm, model
identifier, bundle SHA/rig manifest, raw responses, generated patches, build logs or per-run scoring
record. docs/experience/README.md says a round records prompt, task, NOTES, findings and environment, and
spec-authoring-experience lines 472–488 says the rig manifest is mandatory. round-05 contains only
prediction.md and the aggregate write-up. Preserve enough redacted artefacts to audit each C/T row, or
label this as an observational internal note that cannot support attribution.

F5 · REQUIRED — the exact cold guided-start install has an undocumented interactive branch.

I ran the page's exact first command with an empty isolated Java home:

  jbang app install analyser@telaminai/fluxtionauditlog-analyser

Before installing, JBang refused to run the GitHub release URL until one of four trust choices was made;
it would automatically cancel after 30 seconds. After “Trust once”, installation succeeded and printed:

  Command installed: analyser
  Setting up JBang environment...
  Please start a new Shell for changes to take effect

The pasted prompt says the two commands install then start the application, but tells neither the user nor
the agent how to handle the trust decision or the first-shell PATH boundary. A non-interactive agent can
time out at the first prompt, and the immediate analyser command can be unavailable in the same shell.

Document the expected JBang trust prompt and make the human own that trust choice; then explicitly start a
new shell or invoke the installed path in a way that is valid on the supported platforms. Keep the report's
larger caveat: I did not count this as an end-to-end guided-tour acceptance. A genuinely held-out,
context-free client still needs to run it through the human connection pause and all three UI beats.
