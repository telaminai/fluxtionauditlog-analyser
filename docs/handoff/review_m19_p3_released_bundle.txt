F1 (BLOCKING DISTRIBUTION — “ONLY A JDK” IS FALSE FOR THE SHIPPED LIFECYCLE)

The README and artefact handoff both say “No prerequisites beyond a JDK”. The actual commands require:

  export-audit.sh  -> bash + curl + python3
  stop-server.sh   -> bash + python3 + ps

Neither Python nor curl is supplied by a JDK, Python 3 is not guaranteed on a fresh macOS install, and
the two lifecycle commands have no Windows `.cmd` equivalents even though the bundle ships mvnw.cmd.
The producer's clean-machine proof isolated HOME and Maven resolution; it did not remove these host tools,
so it could not prove the stated prerequisite. This is the same false-pass class as the earlier JBang and
key findings: a developer machine compensates for something the product claims to supply.

Choose one honest correction before the Download is accepted:

  A. preserve the stated acceptance: make export/stop use a helper supplied and run by the JDK, and ship
     equivalent POSIX + Windows entry points; or
  B. narrow the product target and every README/guide/acceptance line to the actual supported platforms
     and explicitly list bash, curl, Python 3 and ps as prerequisites.

Given the milestone's repeated JDK-only headline, A is the contract-faithful correction. Pin the commands
with a test whose PATH contains the JDK plus only the bundle-owned launchers; an ordinary developer PATH
does not test this requirement.

F2 (REQUIRED PORTABILITY CORRECTION — SHELL HOME AND JVM HOME CAN DISAGREE)

`run-server.sh` launches `java` without binding `-Duser.home`. Mongoose publishes the registry under
Java's `user.home`. `export-audit.sh` and `stop-server.sh` look under shell `$HOME`. Reproduction:

  HOME=<isolated> ./run-server.sh

on this Mac published `/Users/greg/.mongoose/servers/fluxtion-spring-mongoose`, while both scripts looked
under `<isolated>/.mongoose/servers` and refused to export/stop. Ordinary interactive shells hide the
defect because the two homes normally agree; containers, launchers and isolation harnesses need not.

Make all three commands use one resolved registry home. The narrow generator fix is to pass
`-Duser.home="$HOME"` to the launched JVM (while preserving an explicit MONGOOSE_SERVERS_DIR contract if
that is intended), then add a fixture where shell HOME differs from the parent JVM's default user.home.

N1 (NON-BLOCKING FOR THE BUNDLE; LOOP CONTRACT FOLLOW-UP)

Immediately after the released server booted, its registry entry carried `processors: []`. The current
loop-bench assumes `processors[0]` and failed its GraphML export. The delivered M19 bundle is not blocked:
its profile and skills declare the committed local GraphML and the accepted consumer bench uses that
authoritative path. The producer report says processors populate after a dashboard poll, which means the
generic real-server bench and publisher have a lazy-publication seam to resolve separately: either publish
processor routes eagerly or make the registry contract/bench wait on the endpoint that earns them. Do not
count the existing loop-bench as a real-server pass on this released startup shape until that is pinned.
