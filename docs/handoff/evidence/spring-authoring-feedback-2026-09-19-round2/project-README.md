# my-app

**Demonstrates:** a Spring-XML-wired Fluxtion graph, AOT-generated (native-ready), with auditors (event audit).

A standalone Fluxtion application, generated by the [Fluxtion project starter](https://fluxtion-playground.dev/start).

## Build & run

```bash
./check-fluxtion-key.sh    # verify your free Fluxtion API key first
./run.sh                 # builds the fat jar on first run, then launches FluxtionMain
```

Requires **JDK 21+**. Or run **FluxtionMain** from IntelliJ — a run configuration is included. To build + run by hand: `./mvnw package` then `java -jar target/my-app-1.0.0-SNAPSHOT.jar` (no `--add-opens` needed, Fluxtion 1.0.16 runtime).

## Native image (GraalVM)

The AOT processor is reflection-free static dispatch — a near-ideal GraalVM target. With a
**GraalVM JDK** on the path (e.g. `sdk install java 21-graal`), the `native` profile builds a
standalone binary (millisecond startup, tiny RSS, no JVM, no `--add-opens`):

```bash
./mvnw -Pnative package
./target/my-app
```

`@ServiceRegistered` service wiring *does* reflect at runtime (the generated `ServiceRegistryNode`), but the build emits the matching GraalVM **reachability metadata** automatically (`META-INF/native-image/…/reachability-metadata.json`, via `configureGeneration`) — so injection works in the native image with no hand-written config.

## Fluxtion API key (remote compiler) — needed **once at build time**

This project is **AOT**: `./mvnw package` runs the `fluxtion-maven-plugin`, which calls the Fluxtion
source-gen API on **RapidAPI** to generate the processor. A valid, *subscribed* key is needed at
**build** time — but **not at runtime** (the generated processor is baked into the jar, and
fluxtion-builder is `provided` scope).

1. Register and subscribe to the Fluxtion source-gen API at **https://rapidapi.com/hub**.
2. Configure the key — the compiler reads exactly two sources (`FLUXTION_API_KEY` is **not** one of them):
   - `~/.fluxtion/fluxtion.apiKeyFile` → `apiKey=YOUR_KEY` (preferred; auto-created on first run)
   - `./mvnw ... -Dfluxtion.apiKey=YOUR_KEY` (overrides the file for that invocation)
3. Verify the key: `./check-fluxtion-key.sh` (reports valid / invalid / not-subscribed / offline).


## What's here

- `node/RootNode` — the event-handler node, one `@OnEventHandler` per event type (`PriceUpdate`); stores the latest event.
- `node/Child` — an `@OnTrigger` node referencing RootNode, fired after it updates.
- `src/main/fluxtion/designer/application-context.xml` — Spring XML topology plus `FluxtionSpringConfig` semantic contract: explicit `nodeBeans`, declared `eventTypes`, and handler expectations. Open it in the IntelliJ Fluxtion visualiser; the pom maps this folder as the resources dir so it's also on the classpath (`ClassPathResource`). (The referenced `RootNode` + event classes are generated in `src/main/java`.)
- `FluxtionMain` — **AOT**: `MyProcessor` is generated at build time by the fluxtion-maven-plugin; Main just `new`s it and runs it (no compiler at runtime).
- `event/*` — shell event classes.
- Audit logging is on: the node extends `EventLogNode` and each handler calls `auditLog.info(...)`; the builder enables `addEventAudit(INFO)`.
- `MyProcessorTest` — a JUnit 5 smoke test.

## Generation mode — AOT

`./mvnw package` runs the `fluxtion-maven-plugin` (`1.3.0`) at
`process-classes` to emit `com.example.myapp.generated.MyProcessor` into
`src/main/java` (git-ignored), which a second compiler pass builds; `FluxtionMain` loads it
reflectively. `fluxtion-builder` is `provided` (build-time only). The plugin generates the
processor via the Fluxtion source-gen API, so a key is needed **once at build time** (see below).
