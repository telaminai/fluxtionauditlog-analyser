# Session report: from starter template to a validated risk limit

**Date:** 2026-09-21 (all times local, BST)
**Author:** Claude (Claude Code session), working with the project owner
**Project:** `fluxtion-spring-mongoose-1`

This report covers where the project started, what was done, what was found, and what was easy or hard when using Fluxtion, the Mongoose audit log and the Fluxtion Audit Log Analyser together to add behaviour and check it against facts.

---

## 1. Summary

- Starting from the unmodified **Fluxtion project starter** template (Spring XML design, hosted in Mongoose), I added a **notional risk limit** to the `RiskCheck` node. The feature publishes breaches to the Mongoose file sink.
- Every result was **predicted before it was measured**, then checked four ways: a unit test, the Mongoose audit log, the sink file, and the analyser's own calculations.
- **Verdict: the feature behaves exactly as predicted.** All 15 checks and all 6 sink lines match the predictions, including the boundary case (a trade exactly at the limit does not breach).
- **Round 2:** added two new nodes, **trade recording** (`tradeRecorder`) and **mark-to-market by book** (`markToMarket`), plus a new `TradeEvent`, all declared in Spring XML. All 6 live mtm and P&L values match the predictions exactly. One prediction was mine and wrong (I miscounted the trades); the system was right.
- **Easy:** using the audit log and analyser to check behaviour once the evidence was loaded.
- **Missing tool:** the starter's stub generator is not reachable from the project, so round 2's classes were written by hand. In **round 3** an unreleased starter build found in the local Maven cache was run against a copy: it generated usable stubs, but it could not reconcile the round-1 `RiskCheck`, and its output needs hand-finishing (see 3.6 and Appendix B).
- **Hard:** getting live audit evidence out of Mongoose and into the analyser. The runbooks don't document this path. One advertised mechanism (the audit WebSocket tail) didn't work, and there were several small format and build-order problems.

## 2. Starting point: the template

### 2.1 Where it came from

The project was generated by the **Fluxtion project starter** (`https://fluxtion-playground.dev/start`). All template files carry the same timestamp, **06:57:19**. The comment contract manifest identifies the generator:

| Item | Value |
|---|---|
| Starter coordinate | `com.telamin.fluxtion:fluxtion-starter-core:1.0.72:jar:all` |
| Fluxtion BOM / runtime | 1.0.72 / 1.0.16 |
| fluxtion-maven-plugin | 1.3.0 |
| Mongoose / plugins | 1.0.29 / 1.0.43 |
| Java | 21 (Maven wrapper included) |
| Compile mode | AOT: the processor is generated at build time by the Maven plugin's `scan` goal, using a remote source-generation API that needs a Fluxtion API key |

### 2.2 What the template contained

- **Design:** `src/main/fluxtion/designer/application-context.xml`, a Spring XML topology with two nodes (`rootNode`, then `riskCheck`), one event type (`PriceEvent`), and a `PerformanceMonitorAudit` auditor at log level INFO.
- **Nodes:** `RootNode` (handles `PriceEvent`, extends `EventLogNode`, logs the event, price and volume) and `RiskCheck` (an `@OnTrigger` node). **Both handlers were `// TODO` stubs** that stored the latest event and returned `true`.
- **Hosting:** `config/server-config.yml` sets up a file feed (`data/input.txt`, `readStrategy: EARLIEST`, CSV mapped to `PriceEvent`), a file sink (`data/output.txt`), Chronicle audit capture to `./audit` with auto-start for `marketProcessor`, and the web admin console on `127.0.0.1:8181`. `MongooseProgrammaticMain` is the same setup in code.
- **Scripts:** `run-server.sh` (build if needed, then run with the required `--add-opens` flags) and `check-fluxtion-key.sh` (checks the API key without printing it).
- **Agent guidance:** `CLAUDE.md` and `AGENTS.md` point to `PROJECT.md`, which names three runbooks:
  - `runbooks/build.md`: build and verify; write expected results before running.
  - `runbooks/hosting.md`: start and stop, input ordering, what a reset does, audit availability.
  - `runbooks/analyser.md`: the "shared evidence canvas"; connect the analyser, open the design and evidence, build reports.
  - It also includes a comment contract (`runbooks/comment-contract.json`) with its provenance manifest.
- **Analyser profile:** `.analyser/project.fluxtion-settings`, with project-relative paths and no keys.
- **Tests:** one test, `MarketProcessorGraphTest`, which only checks that the supplier returns a non-null graph.

### 2.3 Gaps in the template as shipped

| Gap | Effect |
|---|---|
| Handlers are TODO stubs | A passing build and run only show events passing through unchanged. There's nothing to check yet. |
| The sink is configured but nothing publishes to it | `data/output.txt` is always empty, even though the README says "file feed → MarketProcessor → file sink". |
| `RootNode` logs the whole `PriceEvent` | Its `toString()` (`PriceEvent{symbol=…, …}`) is written inside a YAML `{…}` block, so a strict YAML parser rejects the line. |
| The README mentions `ServerSmokeTest` | That test doesn't exist in the template. |
| The runbooks don't describe the web-admin audit endpoints | They warn that capture storage and analyser-readable exports are different, but not how to get an export. |

### 3.2 Getting live audit evidence into the analyser (08:18 to 08:26)

1. Backed up the existing audit queue, then started the server with `./run-server.sh` (hosting runbook).
2. Tried the **`/ws/audit-tail/{processor}` WebSocket.** It accepts a connection but sent **no records**, even when new events were captured. Inspecting the plugin shows it starts at the end of the queue (`toEnd()`), and the bundled web UI never uses it.
3. Found that **`/api/audit/file/{id}/export` is current** while the server runs (it returns the whole queue as YAML), while `/api/audit/files` reported **out-of-date** record counts and times.
4. Wrote a small follower script (Node, in the session scratchpad) that polls the export every second and appends only the new bytes to a growing YAML file. The analyser opens that file and follows it.
5. **Fixed a one-record lag:** the export separates records with `\n---\n` but leaves the last record unterminated, so the analyser held the newest record back until the next one arrived. The follower now moves the separator so every record is closed as soon as it's written.
6. Checked the loop by appending rows to `data/input.txt` while the server ran. Each record reached the analyser within about 1 second and was highlighted as it arrived.

### 3.3 Designing, predicting, building and deploying the risk limit (08:26 to 08:33)

**Requirement (agreed before any code):**
- `notional = price × volume`
- breach when `notional > limit`, strictly greater
- limit = 1,000,000, set in the Spring XML
- audit-log `symbol`, `notional`, `limit` and `breach` on every check
- publish `BREACH,<symbol>,<notional>` to the `output` sink on a breach
- side fix: `RootNode` logs `event.symbol()` instead of the whole event

**Predictions (agreed before the build, checked in Java doubles to rule out floating-point surprises):**

| Row | Notional | Breach |
|---|---|---|
| AAPL 195.30 × 1200 | 234,360.0 | no |
| MSFT 410.10 × 800 | 328,080.0 | no |
| GOOG 155.75 × 1500 | 233,625.0 | no |
| AMZN 178.22 × 640 | 114,060.8 | no |
| NVDA 905.60 × 2100 | 1,901,760.0 | **yes** |
| EDGE 1000.00 × 1000 (sent live) | 1,000,000.0 | no (at the limit) |
| OVER 1000.01 × 1000 (sent live) | 1,000,010.0 | **yes** |

**How the sink is declared.** The bundled Spring contract (read from `fluxtion-builder-1.0.72`) supports a `sinks` list of `SinkBinding(name, valueType, nodeBeans)`. Its verifier requires each listed node to hold a `SinkPublisher` field whose name matches the binding. The generator builds nodes through their constructors, so the publisher and the limit are passed as constructor arguments.

**Changes:**

| File | Change |
|---|---|
| `application-context.xml` | `riskCheck` constructor gets `outputSink` and `1000000`. New `outputSink` bean (`SinkPublisher("output")`). New `sinks` binding (`output`, `java.lang.String`, `riskCheck`). |
| `RiskCheck.java` | Extends `EventLogNode`. Computes notional and breach, writes them to the audit log, publishes on breach. |
| `RootNode.java` | Logs `symbol` instead of the whole event. |
| `RiskCheckLimitTest.java` (new) | Drives the generated processor directly. Tests the arithmetic and the at-limit case without the server. |

**Deploy:** stopped the old server with SIGINT (the shutdown hook ran), archived the audit folder, restored `input.txt` to its original 5 rows, rebuilt, started the server, and followed the new audit log into the analyser.

### 3.5 Round 2: trade recording and mark-to-market by book (08:51 to 09:06)

**Before writing any code**, I read the published Spring authoring contract (`fluxtion-playground.dev/spring-authoring/contract.md`) and checked it against the binding classes in the pinned `fluxtion-builder-1.0.72`. The two agreed on every property this round needed.

**Design (agreed before building):**
- New event `TradeEvent(book, symbol, qty, price)`, with `qty` signed.
- **One ordered feed.** A new mapper, `CsvToMarketEvent`, turns `TRADE,book,symbol,qty,price` into a `TradeEvent` and passes other lines to the existing price mapper. The hosting runbook warns that separate feeds don't guarantee order, and the predictions depend on it. The mapper is set in both `server-config.yml` and `MongooseProgrammaticMain`.
- `tradeRecorder` handles `TradeEvent`. It keeps position per book and symbol, and cash per book (−qty × price).
- `markToMarket` has constructor references to `tradeRecorder` and `rootNode` (both default `TRIGGER`). For each book it computes `mtm = Σ position × mark` and `pnl = mtm + cash`, and logs `mtm_<book>` and `pnl_<book>`.
- Spring changes:
  - two `nodeBeans`
  - `TradeEvent` added to `eventTypes`
  - one new `EventHandlerBinding` (`TradeEvent` → `tradeRecorder`)
- Kept audit-only: no new sink, and no `filterString` routing by book.

**Predictions (Java doubles, agreed before building):**

| # | Row | EQ1 mtm / pnl | EQ2 mtm / pnl |
|---|---|---|---|
| 1 | `TRADE,EQ1,AAPL,100,195.00` | 19,530 / 30 | none |
| 2 | `TRADE,EQ1,MSFT,-50,410.00` | −975 / 25 | none |
| 3 | `TRADE,EQ2,NVDA,10,900.00` | −975 / 25 | 9,056 / 56 |
| 4 | `AAPL,197.30,500` | −775 / 225 | 9,056 / 56 |
| 5 | `NVDA,880.00,100` | −775 / 225 | 8,800 / −200 |
| 6 | `TRADE,EQ1,AAPL,-100,197.50` | −20,505 / 245 | 8,800 / −200 |

**Build:** the first build failed with **FLX-1009**. By default Fluxtion expects every `final`, non-`transient` field to be set through a constructor, and my working maps were `final`. The diagnostic named the fields, explained the rule and gave the fix: mark them `transient`. After that change the build passed. 3/3 tests pass, including `MarkToMarketTest`, which runs the same six steps against the generated processor.

**Measured, in the live Mongoose run followed into the analyser:**
- All 6 live records match the table exactly for mtm and pnl in both books. Position and cash on each trade record match too (for example, after row 6 `position: 0`, `cash: 20750.0`).
- On the 5 startup price rows, `markToMarket` ran and logged no books, as predicted.
- The two live price rows produced `riskCheck` notionals of 98,650 and 88,000, with no breach.
- `output.txt` gained nothing from the live rows; its only line is the startup NVDA breach.
- **One prediction was wrong, and the error was mine:** I wrote "3 `tradeRecorder` records", but the scenario has 4 trades (rows 1, 2, 3 and 6). The log correctly shows 4.

**Evidence kept in the analyser:** flags on records 23 to 28, and a "P&L by book" stairs chart with EQ1 and EQ2 lines, trade and price markers, and a note on each step.

### 3.6 Round 3: end-of-day report, using the starter's stub generator (09:10 to 09:20)

This round deliberately tested the stub generator described in Appendix B, after finding a runnable (unreleased) starter build in the local Maven cache. Predictions were written for the **generator** as well as for the runtime.

**Design:** a new `MarketCloseEvent`, a node `eodReportPublisher` reading `markToMarket` through a **`DATA`** reference binding (so intraday re-marks do not trigger it), and a new `eodReport` sink publishing one `EodReportLine` per book to `data/eod-report.txt`. Only the XML, the `CLOSE,<date>` mapper branch and the sink config were written by hand.

**Method:** copy the project to a scratch directory, run the starter there, then bring the new stubs into the real project. The commands were `validate` and `regenerate --reconcile --project . --xml src/main/fluxtion/designer/application-context.xml`.

**Generator predictions vs results:**

| # | Predicted | Result |
|---|---|---|
| G1 | `validate` passes on the unchanged project | PASS, but for a different reason: it validates the **XML only** ("XML: valid; 4 nodes, 3 edges") and never inspects the Java |
| G2 | `validate` fails or warns when the declared classes are missing | **WRONG.** It passed ("5 nodes, 4 edges") with all three classes absent |
| G3 | `MarketCloseEvent` shell, no fields | Partly: no fields, but emitted as `public record MarketCloseEvent() {}`, not a class like the template's `PriceEvent` |
| G4 | `EodReportPublisher` with constructor, `@NoTriggerReference`, handler, sink field, standard comments | Mostly: constructor, `@NoTriggerReference` and `@OnEventHandler onMarketCloseEvent` are right. Differences: the sink field is `sinkEodReport` (public, non-final, inline initializer), **plus an extra `@OnTrigger onEodReportPublisher()`**, **no comment-contract comments**, no `EventLogNode` base (so no `auditLog`), fully-qualified names and broken indentation |
| G5 | empty `EodReportLine` record | CORRECT |
| G6 | existing classes untouched | `RootNode`, `TradeRecorder`, `MarkToMarket` untouched. `RiskCheck` **could not be reconciled** (see below); the tool refused and wrote nothing |

**The round-1 `RiskCheck` cannot be reconciled.** Three conflicts, in order:
1. `SPRING_RECONCILE_CONFLICT … field:outputSink` — the reconciler expects a reference field **named after the referenced bean**; my field was `output` while the bean was `outputSink`.
2. After renaming: "Reference/publisher type contradicts the declaration" — the XML implies a raw `SinkPublisher`, my field is `SinkPublisher<String>`.
3. After deleting the class to force a fresh stub: "Cannot infer source constructor types from literal/inline bean arguments" — the literal `<constructor-arg value="1000000"/>` is not supported.

Each time it refused and wrote nothing, which is the right behaviour. It does mean the round-1 design (a separate `SinkPublisher` bean plus a literal constructor argument) is **outside what the generator supports**, even though it builds and runs. The fresh `RiskCheck` stub shows the intended sink pattern instead: a `public SinkPublisher<String> sinkOutput = new SinkPublisher<>("output")` field, with no bean and no constructor argument.

**Runtime predictions vs results (live Mongoose run):**

| # | Row | Predicted | Result |
|---|---|---|---|
| R1 | `CLOSE,2026-09-21` | 2 lines: EQ1 mtm −20,505 pnl 245; EQ2 8,800 / −200 | Exact, including the record's text form |
| R2 | `NVDA,890.00,100` | EQ2 re-marked to 8,900 / −100; **no** EOD lines | Exact: `markToMarket` ran, `eodReportPublisher` did not |
| R3 | `CLOSE,2026-09-22` | 2 more lines, EQ2 now −100 | Exact |

Also as predicted: on a close only `eodReportPublisher` ran (no `markToMarket`, `riskCheck` or `tradeRecorder`), `output.txt` gained nothing beyond the startup breach, and `EodReportTest` passes (4/4 tests). The generated extra `@OnTrigger onEodReportPublisher()` never fires, because its only parent is a no-trigger reference.

**Verdict on the generator:** it does the useful part (correct skeletons for new nodes, events and sinks, a `fluxtion-authoring.json` ownership record with per-member hashes, and a safe refusal when it cannot reconcile). The output still needs hand-finishing: no comment-contract comments, no imports or formatting, no `EventLogNode` for audit logging, and an extra trigger method.

## 4. What was easy

1. **Checking behaviour against the audit log.** Each record showed exactly what each node computed (`notional: 1000000.0, limit: 1000000.0, breach: false`). The boundary case was a fact in the log, not an inference from code.
2. **Predicting first.** Writing expected values before building turned validation into a yes/no comparison, and made "behaves as predicted" an honest claim.
3. **The analyser's query tools.** `series` with crossings found every breach and flip in one call. `read` with `fields` returned only the values needed. `flag`, `graph` and `report` kept the findings tied to specific records. `spotlight` made it easy to point the person at what I meant.
4. **Built-in cautions.** The runbooks and tool descriptions warn against overclaiming ("did not log is not did not run", "a path is not proof", "producing a file is not a correctness check"). They caught at least one weak conclusion early.
5. **The Spring XML design and code generation.** Once the contract rule for sinks was known, the design change was small, and the generated processor was easy to read.
6. **Quick live testing.** Appending a row to the feed and seeing its record about a second later made each new question cheap to test.
7. **Server start and stop.** `run-server.sh`, a clean SIGINT shutdown, and the admin API (`/healthz`, `/api/version`) all behaved as documented.

## 5. What was hard

1. **Finding how to get audit evidence out.** The runbooks don't cover it. I found the web-admin audit endpoints by listing and disassembling the plugin jar.
2. **The audit WebSocket tail didn't work.** `/ws/audit-tail` accepted connections and sent nothing. I switched to polling the export.
3. **An out-of-date listing endpoint.** `/api/audit/files` kept reporting the startup record count and time while the queue grew.
4. **The export leaves its last record open.** This put the live view one record behind. It took reading raw bytes to find.
5. **Build order with AOT generation.** A leftover generated `MarketProcessor.java` in `src/main/java` (gitignored, left over from an earlier build) compiles before the plugin regenerates it, so a constructor change breaks the build until you delete it. Also, `target/classes` and the jar receive the previous `.graphml`, because resources are copied before generation runs.
6. **Wrong or awkward analyser output:**
   - Graph pairing claimed the graphml was "probably from a different build", even though it declares the `output` node. The cause seems to be how the framework's `SinkPublisher` node is classified.
   - Finding boxes are always labelled "WHAT IS WRONG" / "LIKELY CAUSE", even when a finding confirms correct behaviour.
   - Chart formulas can't compare a logged boolean to `true`, so breach had to be recomputed as `notional > limit`.
   - The explanation box covers part of the chart and can't be moved.
7. **Things I couldn't do myself.** I couldn't switch the analyser's Follow mode on (the person had to click it) or reposition chart elements.
8. **A small contract mismatch.** The generated processor declares the sink's value type as `java.lang.Object`, although the XML says `java.lang.String`.

## 6. Spring XML authoring: what was easy and what was hard

**Easy**
- **The declarations are small and readable.** The whole of round 2 took two `<bean>`s, one `eventTypes` entry and one `EventHandlerBinding`. Links between nodes are ordinary `constructor-arg ref`s, and the generated processor mirrors them directly (`new MarkToMarket(tradeRecorder, rootNode)`, guard `isDirty_rootNode | isDirty_tradeRecorder`).
- **Good diagnostics.** FLX-1009 named the offending fields, explained the rule, and gave a fix that worked first time. It also stated that the fix was complete.
- **Clear separation of concepts.** The contract separates graph links (constructor references), services (never beans) and events (class-name strings). That made the design questions easy to answer.

**Hard**
1. **Finding a spec that matches the pinned version.** There's no written contract inside the project or the pinned jars. The published page states no version, and it says local authoring "publication is pending". I had to check the page against the 1.0.72 builder classes (`javap`) to be confident the two matched.
2. **Stub generation was missing, so I wrote the classes by hand.** The contract says the starter generates skeleton classes (with the standard comments) for new nodes, events and sinks. Nothing in the project gives a way to run it, so I hand-wrote `TradeEvent`, `TradeRecorder` and `MarkToMarket`. The project owner pointed out that the starter would have generated these. See **Appendix B** for what I searched, what I found, and what it cost.
3. **The rule that `final` means constructor-supplied isn't in the authoring contract.** It's normal Java to make a node's working collections `final`. Fluxtion then expects them to be set through the constructor and fails the build (FLX-1009). The fix is easy once you've seen the diagnostic, but the contract page should mention `transient` or `@FluxtionIgnore` for a node's own working state.
4. **How sinks are declared was only discoverable from the verifier.** In round 1, the rule that a `SinkBinding` node needs a `SinkPublisher` field with the same name came from disassembling `SpringDeclarationVerifier`. The contract page does say that sinks "generate `SinkPublisher<T>` fields", but that assumes you're using the stub generator (see point 2).
5. **Stale generated source, twice.** Each constructor change needed the leftover generated `MarketProcessor.java` deleted before the build would pass.
6. **Some behaviour isn't specified.** The contract doesn't say how several event types on one node, or several handlers per node, are matched. It also doesn't say how the value type is carried from `SinkBinding.valueType` into the generated processor, which declares `java.lang.Object` rather than the configured `java.lang.String`.
7. **Routing more than one event type through one ordered feed isn't covered.** Keeping trades and prices in order needed a custom mapper that dispatches on the line's first field. That's reasonable, but a template example or runbook note would help, since the hosting runbook warns that separate feeds lose ordering.

## 7. Recommendations

**For the template and runbooks:**
- Add an "Audit evidence" section to `runbooks/hosting.md` or `runbooks/analyser.md`: use `/api/audit/file/{id}/export`, note that `/ws/audit-tail` doesn't deliver records in plugins 1.0.43, and give a supported way to follow the export.
- Log `event.symbol()` (or other plain fields) in the template's `RootNode`, not the whole event.
- Remove `ServerSmokeTest` from the README, or add the test.
- **Ship local stub generation with the project** (see Appendix B): pin a released starter-core coordinate in the POM or wrapper, add a script such as `./author.sh regenerate`, and add an "Authoring new nodes" step to `PROJECT.md` and the build runbook.
- Mention in the Spring authoring contract that a node's own working state (maps, counters) must be `transient` or `@FluxtionIgnore` when `final`.
- Add a template example of one ordered feed carrying more than one event type.
- Note in `runbooks/build.md` that constructor changes need the stale generated source removed first (or make the build clean it automatically), and that the jar's `.graphml` is one build behind.

**For Mongoose plugins (1.0.43):**
- `/ws/audit-tail`: make it deliver records, or remove it.
- `/api/audit/files`: report live record counts and last-write times.
- Export: close the final record with a separator, or document that it's left open.

**For the analyser:**
- Recognise framework nodes such as `SinkPublisher` in graph pairing.
- Offer neutral finding labels for confirmations.
- Allow boolean comparisons in chart formulas.
- Let the assistant turn Follow on.

## Appendix A: Analyser issues with reproduction details

These are for the analyser's author. Each entry gives the call, what came back, and what I expected. The calls went over the MCP action socket, with a log grown live by appending to a YAML file.

| # | Call | Observed | Expected / suggestion |
|---|---|---|---|
| A1 | `open {graphml: …/MarketProcessor.graphml}` with a log whose records include `- output: { registeredMessageSink: output}` | `"the graph declares 2 of the 3 node(s) this log writes"`. `coverage` → `loggedButNotInTopology: ["output"]` plus the warning *"the graphml is probably from a different build"* | The graphml has `<node id="output">` (class `SinkPublisher`, label `<<EventHandle>>`). Match framework or event-handle nodes by id; don't warn about a different build. |
| A2 | `graph {markers: [{when: "riskCheck.breach == true", …}]}` | Warning: `'true' is not a key reference (expected instanceId.key)` | Support boolean and string literals (`== true`, `== "true"`). Workaround used: `riskCheck.notional > riskCheck.limit`. |
| A3 | `spotlight {target: "graph:Breach state:series:flip to breach"}` | `'…' is not on graph 'Breach state'`, although the legend shows "flip to breach (6)" | Allow marker series as spotlight targets, or say in the error that markers aren't targetable. |
| A4 | `spotlight {target: "project:log"}` | `the Project panel is hidden or has no such section — its rail toggle shows it` | Fine as an error. Consider revealing the panel automatically, as other targets are revealed. |
| A5 | `open {design: src/main/fluxtion/designer/application-context.xml}` on the project profile | `file unavailable or outside authorised roots … roots: [src/main/java]` | The project's own runbook names this XML path. The starter's `.analyser` profile should include `src/main/fluxtion` as a source root (I added it by hand with `source_root`). |
| A6 | Follow mode | No verb can switch it on; the person had to click the toolbar button | Add a `follow` option (for example on `open`, or a `follow` verb). |
| A7 | Follow on a log whose producer leaves the last record unterminated (no trailing `---`) | The newest record is held back until the next one arrives, so the view is always one record behind | Reasonable parsing, but worth a status hint ("1 trailing record pending"), or a timeout that accepts a complete-looking last record. |
| A8 | `series {expr: "delta(…)", filter: {from, to}}` | The first in-window record has no delta (it doesn't look back before `from`), so the flip at record 27 was missing from the windowed answer but present in the whole-log answer | Either look back one record for rolling functions, or say in the result that window edges have no history. |
| A9 | `report` finding sections | Always labelled **"WHAT IS WRONG"** / **"LIKELY CAUSE / SUGGESTED FIX"**, even when the flag confirms correct behaviour | Let a flag carry a kind (for example `confirmation`) with neutral labels ("Observation" / "Assessment"). |
| A10 | `report` → PDF, marker tables | Flag rows render as `? flags` (the glyph seems missing from the PDF font) | Embed the glyph or fall back to text ("flag"). |
| A11 | `graph {explanation: …}` | The explanation box covers the lower-left of the plot and can't be moved. In the PDF it hides steps. | A position option, or draw it below the plot. |
| A12 | `graph {notes: […]}` for records seconds apart on a multi-minute axis; a note near the right edge | Notes stack on top of each other; a right-edge note sits under the legend | Collision avoidance, or place the legend outside the plot. |

**What worked especially well and should be kept:**
- `series` with `crossings` (one call answers "where does X cross Y").
- `read` with `fields` (compact values, including `traceLikeOnly`).
- `flag` → `report` building on live evidence, with the log fingerprint recorded.
- Numbered spotlights.
- `context` returning pointers and pairing verdicts.
- The cautions built into the tool descriptions.

## Appendix B: Missing stub generation (for developers)

### What should have happened

The Spring authoring contract says that when a node, event or sink is declared in the XML, the **starter generates the Java skeletons**:
- node classes under `src/main/java/<basePackage>/node/`
- handler and trigger methods for each declared binding
- `SinkPublisher<T>` fields for sinks, plus a record stub when `valueType` is absent
- the standard comment-contract comments

The intended workflow is: edit the XML, then generate or reconcile the stubs, then fill in the logic, then build.

### What happened

In round 2 (trade recording and mark-to-market), I declared a new event (`TradeEvent`) and two new nodes (`tradeRecorder`, `markToMarket`). **I found no way to run stub generation from the project, so I wrote all three classes by hand.** I copied the comment-contract comments from the existing stubs to keep them consistent.

### What I searched

| Place | Result |
|---|---|
| `PROJECT.md`, `README.md`, `runbooks/*.md` | No mention of generating stubs locally. |
| Project scripts (`run-server.sh`, `check-fluxtion-key.sh`, `mvnw`) | Build, run and key check only. |
| `fluxtion-maven-plugin:1.3.0` goals | `scan`, `springToFluxtion`, `yamlToFluxtion`. They generate the **processor**, not node or event stubs. |
| POM dependencies | No `fluxtion-starter-core` dependency. |
| Published contract page | Describes stub generation, but says local authoring "publication is pending". |
| Local Maven cache | The released `fluxtion-starter-core:1.0.72` (the coordinate in `runbooks/comment-contract-manifest.json`) **is not present**. Only unreleased `1.0.70` and `1.0.72` test and demo builds are cached. |

### What exists, but isn't connected to the project

The cached unreleased build `fluxtion-starter-core-1.0.72-demo-52efd42e2ddb-all.jar` (manifest `Implementation-Version: 1.0.72-SNAPSHOT`) has a runnable main class, `com.telamin.fluxtion.starter.Starter`, and a `Reconciler`. Its usage text reads:

```
Fluxtion authoring: validate | regenerate | link [--project DIR] [--xml FILE] [--src-root DIR]
                    [--reconcile|--no-reconcile] [--generate-deregistration=true|false]
```

This looks like exactly the missing tool: validate the XML, regenerate stubs, and reconcile existing sources. **I did not run it.** It's an unreleased snapshot, it isn't pinned by the project, and the project's rules say to use the contract bundled with the pinned starter.

### What its absence cost

- **Time and risk:** I had to work out the class shapes the generator would have produced (constructor order, handler signatures, comment text) from the contract, the existing stubs and the builder's verifier.
- **A build failure:** my working maps were `final`, which caused FLX-1009. Generated stubs would probably have used the expected pattern from the start.
- **Unverified agreement with the contract:** there's no check that the hand-written classes match what the generator would emit. The build and the verifier passed, but that isn't the same as a reconcile.

### What the tool actually does (tested in round 3)

Run against a **copy** of the project:

```
java -jar fluxtion-starter-core-1.0.72-demo-…-all.jar validate   --project . --xml src/main/fluxtion/designer/application-context.xml
java -jar fluxtion-starter-core-1.0.72-demo-…-all.jar regenerate --project . --xml … --reconcile
```

- `validate` checks the **XML only** (bean graph, cross-references). It reports, for example, "XML: valid; 5 nodes, 4 edges" and prints a playground link with the XML encoded in it. It passes even when every declared class is missing, so it is not a check that the code matches the design.
- `regenerate` without `--reconcile` does nothing: "Reconciliation disabled: source and record unchanged; the build checks existing classes."
- `regenerate --reconcile` writes the missing classes and a `fluxtion-authoring.json` ownership record (per-member signatures, owned annotations and stub-body hashes), and leaves conforming existing classes untouched.
- It **refuses as a whole** when any class conflicts, and writes nothing at all, naming the member and the rule.

**What it generated well:** constructors matching the XML edges, `@NoTriggerReference` from `mode=DATA`, `@OnEventHandler` per binding, `SinkPublisher<T>` fields from sink bindings, and record stubs for missing value types.

**What still needed hand-finishing:** comment-contract comments, imports and formatting (it emits fully-qualified names and broken indentation), an `EventLogNode` base where audit logging is wanted, event and record fields, and removing or keeping an extra `@OnTrigger` method it adds to a handler node.

**Conventions it enforces, which are not in the published contract:**
- A reference field must be **named after the referenced bean**.
- A sink is a field on the node (`sink<Name>`), **not** a separate `SinkPublisher` bean passed through the constructor.
- **Literal constructor arguments** (`<constructor-arg value="1000000"/>`) cannot be reconciled: "Cannot infer source constructor types from literal/inline bean arguments".

### What to fix

1. **Publish** a released `fluxtion-starter-core` matching the pinned coordinate, and make it reachable from the project (a POM dependency or plugin goal, or a downloaded tool jar with a pinned checksum, like the comment-contract manifest).
2. **Add a project script**, for example `./author.sh validate|regenerate|link`, that runs it with `--project .` and `--xml src/main/fluxtion/designer/application-context.xml`.
3. **Document the workflow** in `PROJECT.md` and `runbooks/build.md`: edit the XML, run `validate`, run `regenerate` (reconcile), implement the TODOs, then build.
4. **Document the conventions above** in the authoring contract: reference-field naming, the sink-as-field pattern, and the limits on literal constructor arguments. They are only discoverable today by hitting a reconcile conflict.
5. **Make the generated stubs match the template's own style**: comment-contract comments, imports, formatting, and `EventLogNode` where audit logging is expected.
6. **Tell agents:** add a line to `CLAUDE.md`/`AGENTS.md` saying that new nodes and events get their stubs from the starter and aren't hand-written. If the tool is unavailable, the agent should stop and report that, as it would for any provisioning failure.
