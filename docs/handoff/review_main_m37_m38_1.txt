1. M38.1 — THE SECURITY SLICE, PROBED RATHER THAN READ
================================================================================
D-C2's gate (`Runbooks.refuse`) is built the right way round: an **allowlist**, where a path segment
must match `[A-Za-z0-9._-]+`. That refuses shell metacharacters, spaces, quotes, `$`, backticks,
encoded traversal and null bytes *by construction* rather than by a blocklist someone has to keep
ahead of. I fired seventeen shapes at it:

  ACCEPTED   ops/deploy.md · ./ops/deploy.md · ops/...md        (all plainly harmless)
  refused    ops/../../etc/passwd · ../ops.md · /etc/passwd · C:\win\x.md · ~/x.md ·
             https://evil/x.md · ops/%2e%2e/x.md · "ops/deploy.md; rm -rf /" · ops/$(whoami).md ·
             a path with an embedded newline · ops//deploy.md · a NUL byte · a trailing space ·
             \\server\share\x.md

Nothing got through. The refusals also carry reasons, which is what makes a hostile or hand-edited
file degrade to "that entry was dropped, and here is why" instead of to a pointer someone acts on.

R1 · **`resolve()` had no containment check — fixed here.**
     `Runbooks.resolve(/tmp/proj, "../../etc/passwd")` returned **`/etc/passwd`**. Not exploitable
     through the product: `refuse()` gates the verb path, the import path and the config loader, so no
     such value can be stored. But `resolve()` is public, does not know whether the gate ran, and is
     the other half of the same boundary — and the two halves of a security boundary should each hold
     alone. It now returns null when the normalised target falls outside the project root, which every
     caller already treats as "no such runbook". Pinned by a test that fails on the old behaviour.

     This is the only finding, and it is defence in depth rather than a hole.
