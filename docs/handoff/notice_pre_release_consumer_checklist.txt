NOTICE — what to settle BEFORE the builder release, from the consumer side
From: the audit-log analyser session (M45) · Date: 2026-08-31
Context: owner is completing the compiler work and releasing, then deciding what needs to change on
         either side and whether a re-release follows.

NOTHING FROM US BLOCKS THE RELEASE. M45.2/.3/.5 are shipped and green against the branch tip; we consume
a `metaVersion 1.0` PARALLEL file today and fall back cleanly for everything else. This note is only
about the few things that are **cheap now and expensive after**, because they are the ones a release
makes permanent.

================================================================================
THE ASYMMETRY THAT DECIDES THE LIST
================================================================================
The GraphML is emitted **client-side by whichever builder an author pinned**. So the moment a builder
is released, every file it ever emits exists somewhere, forever, and we must read it forever. There is
no upgrade moment and no deprecation that reaches those files.

That splits the work cleanly:

  · **key NAMES and SEMANTICS published under `metaVersion 1.0` are permanent.** Getting one wrong is
    not a bug you fix in the next release — it is a shape you support in perpetuity;
  · **missing keys, and the DEFAULT, are cheap.** They change in any later release with no legacy
    burden at all, because absence stays absence.

So the pre-release question is not "is it finished" — it is "is anything published that we would not
want to be stuck with".

================================================================================
1 · THE ONE DECISION WE WOULD MAKE BEFORE RELEASING — AGGREGATED
================================================================================
`AGGREGATED` was designed as the compatible shape for a consumer that wants the facts without the
parallel-edge shape. **We are that consumer, and we have permanently refused it** (D-V1), for the reason
your own javadoc gives: *"the lists are sets, not index-aligned tuples"*. Since propagation became
per-relationship it is worse than when we assessed it — two relationships on a pair can now legitimately
disagree, so aggregation loses a fact rather than blurring one.

Release it under `metaVersion 1.0` and you own it under the 1.x compatibility promise indefinitely, for
a shape with no known reader.

DECIDED — **publish it, and document the scope precisely.** The owner asked us to call it, and
measuring it changed our answer, so the reasoning matters more than the verdict.

We emitted this repo's own graph both ways and compared:

  · **node facts are BIT-FOR-BIT IDENTICAL.** Aggregation merges EDGE facts onto one edge per vertex
    pair and does not touch nodes at all. `auditCapable`, `auditCapableVia`, `kind`, `class`,
    `callbackKinds` and `topologicalRank` are exact in either shape;
  · **only a MERGED edge loses anything, and it announces itself.** An aggregated edge carries
    `fluxtion.relationshipCount`; where that is 1, nothing was collapsed onto it and its facts are
    exact too. The lossy case is visible in the data — one edge in our graph reads
    `referenceField="dirtyStateMonitor,eventDispatcher"`, `relationshipCount=2`, with a single
    `propagates` that cannot be attributed to either field.

**So AGGREGATED is not a shape with no reader — it is a shape whose losses we had overstated.** Our own
D-V1 refused the whole file, and that was wrong: it threw away an exact answer because it shared a
document with an inexact one, and it cost the entire audit-capability win on any aggregated graph. We
have corrected it. **The analyser now reads node facts from an aggregated file, and edge facts from any
edge whose `relationshipCount` is absent or 1.** So it has a consumer, and that consumer is us.

What we would ask of the release, and it is documentation rather than code:

  **state in the key registry that aggregation affects EDGE facts only, and that
  `relationshipCount == 1` means an edge's facts are exact.** Both are true of the emitter today and
  neither is written down. Without them the shape reads as uniformly lossy — which is what we
  concluded, wrongly, from the javadoc alone.

That turns AGGREGATED from a bridge nobody crosses into the correct choice for any reader that draws
one arrow per pair, which is most of them.

================================================================================
2 · KEEP THE DEFAULT AT OFF FOR THIS RELEASE — WHICH WE THINK IS ALREADY THE PLAN
================================================================================
Restating so it is not lost in the release rush: the analyser fix that renders parallel edges correctly
is on our `main` and **not in v1.11.0**, our current release. Ship the builder with the default at
`PARALLEL` and every analyser install in the field draws a doubled pair as one heavy arrow and reports
an inflated edge count — quietly, since nothing tells the user.

Default `OFF` costs nothing and removes that entirely. The flip is a separate, later, cheap decision,
and by then we will have shipped.

================================================================================
3 · WHAT WE DO NOT NEED FROM THIS RELEASE
================================================================================
Stated so it does not get pulled forward and delay you:

  · **`fluxtion.framework`** — planned and withheld, needs the `builder-api` change. Our M45.4 is parked
    and we are not blocked. Withholding it rather than publishing a package-prefix guess was the right
    call and we would not reverse it to make a date;
  · **`fluxtion.eventAudit`** — planned. We take the audit regime from the log header meanwhile;
  · **the sidecar being on by default** — opt-in is right. We measured the ceiling with it enabled and
    both predicted rows moved (2–3 build attempts to 1; `final` named as the mapping trigger 0 of 2 to
    2 of 2), so the value is proven without needing it defaulted on.

All three are additive. A later release adds them with no legacy shape to carry.

================================================================================
4 · WHAT WE HAVE PINNED, SO A RE-RELEASE CAN BE CHECKED CHEAPLY
================================================================================
When you decide what needs to change after release, these run in seconds on our side and will tell you
whether a builder change reached a consumer or broke one:

  · `GraphMlExporterCompatibilityTest` — `OFF` output against pre-vocabulary output: ids, kinds, class
    names, adjacency both directions, edge count, audit verdict. Both sides committed, so it cannot go
    stale the way the `dd36bc5` check did;
  · `GraphVocabularyTest` — mode detection, the 1.x version promise, `auditCapable`, and the fingerprint
    being **model-scoped rather than file-scoped** (identical across PARALLEL and AGGREGATED);
  · `ParallelEdgeRenderingTest` — one line per pair, relationships still distinguishable,
    `topologicalRank` **pinned against the dispatch order we know** rather than trusted;
  · `DeclaredAuditCapabilityTest` — the declared fact reaching the coverage denominator, and the
    fallback still honest without it.

Regenerating our three fixtures against a new builder and running those four is the whole check. If you
want it run against a release candidate before you tag, say so and we will.

================================================================================
5 · THE ONE ITEM WE WOULD STILL GATE ON, AND THEN LET GO
================================================================================
The old-client/new-server DTO round trip. `DtoWireCompatibilityTest` pins Kryo registration ids, which
is necessary and not sufficient. Under the cloud model the server is always latest and every client is
pinned, so *old client + new server* is the default state of every user who has not bumped, and a server
upgrade exercises it for all of them at once with no rollback available to them.

Raised three times now, and the owner has asked for a concrete instruction rather than another flag. So:

**DO THIS — two golden files and one test, before you tag.**

  1. Using the **last released builder** (1.0.64 — a real pinned client, not a constructed one), build
     any small graph and **capture the serialised DTO to a file**. Check it into the compiler repo as a
     test resource, named for the version that produced it.
  2. Capture the **`EventProcessorModel` the current server returns** for that DTO, and check that in
     the same way.
  3. Add one test at HEAD that (a) **deserialises the 1.0.64 DTO** — this is the server accepting an old
     client, the case every un-bumped user is in — and (b) **deserialises the model response with the
     1.0.64 reader**, which is that same user's build reading the reply. Assert the node set, the
     annotated methods and the dispatch order survive both ways.
  4. Run it in the release job, and **add a new golden pair on each release** rather than replacing the
     old one. The matrix you want is "every released client against today's server", and it builds
     itself one file at a time.

**Why this shape.** It needs no version matrix, no dual-classpath harness and no second Maven module —
two binaries and a test. It is exactly what "old client, new server" means in bytes, which is the thing
`DtoWireCompatibilityTest` cannot reach: pinning Kryo registration ids proves the ids did not move,
not that a payload written by last month's client still reads.

**And the cheap insurance if that is more than you want before this release:** capture the two goldens
now and check them in **without** the test. Capturing them is only possible while 1.0.64 is still the
last release; writing the test can wait. Losing the ability to capture them cannot.

**DONE — step 1 is captured and is waiting for you.** `docs/handoff/artefacts/dto-wire-golden-builder-1.0.64.bin`,
27,027 bytes: the exact payload a real `mvn -Pregen process-classes` on builder 1.0.64 puts on the wire,
recorded by pointing `fluxtion.remote.host`/`port` at a forwarding proxy. Not constructed — recorded. It
is parked in this repo because the compiler tree was mid-merge; **please move it.** Provenance and hygiene
notes are beside it.

**Capturing it changed the recommendation, which is the argument for capturing rather than reasoning.**
The payload begins `ac ed 00 05` — `ObjectOutputStream` stream magic. **A default AOT Maven build takes
the Java-serialization path, not Kryo.** `DtoWireCompatibilityTest` gates a Kryo registration-id shift and
says in its own words that a `serialVersionUID` change is not the failure mode it worries about. That gate
is correct, and its append-don't-insert rule is right — but it covers the format the default path does not
use. Both are real; one has a golden, and this is the other.

The Java path is not unguarded: `TopologicallySortedDependencyGraphDto` and `NodeDto` both pin
`serialVersionUID`, which is the right mechanism. What a pinned UID does not cover is a changed field
*type* or class hierarchy — which throws at the receiver just the same, and is what deserialising this
file at HEAD would catch.

So the four steps stand, with step 1 done and one correction: **the test to write first reads this file
with Java serialization**, because that is the path a released client actually takes.

If after that the answer is still "accepted risk", say it once and we will stop raising it.
