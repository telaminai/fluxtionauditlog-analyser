Verdict: CHANGES REQUIRED

The archive boundary, origin validation, v4 handoff evidence, tutorial correction and the new
template-reference-guide path are generally strong. The blocking defect is narrower: the new REST
discovery route assumes exact-path dispatch, but the JDK HttpServer uses longest-prefix dispatch.
Consequently a misspelled action URL can execute a real action instead of returning the discovery 404.

The review started at 39d8ba4. Commits 674bdc1 and 1a1e49a arrived on main while it was in progress;
they are included in the range and in the conclusions below.


F1 — HIGH — /action and /manifest are prefix routes, so malformed paths reach real handlers

ActionServer registers contexts at `/action`, `/manifest` and `/` (ActionServer.java:67-74), then
describes the last one as handling anything that is not exactly the first two (lines 144-148). That is
not how com.sun.net.httpserver.HttpServer routes: it chooses the longest matching path prefix.

I added a review-only test in a detached worktree and ran:

  mvn -q -Dtest=ActionServerTest#probePrefixAndMethodSemantics test

It failed with these actual results:

  request                                      expected       actual
  GET  /manifest/not-a-route                   404            200 + full manifest
  POST /manifest                              405            200 + full manifest
  POST /action/not-a-route + valid token       404            200 + aggregate executed

This is not a token bypass: the action-child request still needs a valid token. It is nevertheless a
real dispatch defect. A client can address a path the server says is wrong and still mutate analyser
view state or write an authorised output, depending on the action in its body. The three shipped tests
only exercise a non-overlapping path (`/api/context`), a root child (`/nope`) and the exact manifest;
none challenges HttpServer's prefix rule.

Required correction: make the two real handlers reject any path other than their exact path before
dispatch, and make `/manifest` enforce GET. Pin `/action/extra`, `/manifest/extra`, GET `/action` and
POST `/manifest`. Wrong paths should reach the useful discovery response; wrong methods on exact paths
should be 405.


F2 — REQUIRED SECURITY-CONTRACT CORRECTION — the any-Origin refusal is not applied to every request

The class contract says **any request carrying Origin is rejected** (ActionServer.java:20-29), and that
is the deliberately simple DNS-rebinding posture. The new `handleUnknownPath` has no Origin check. A
second review-only assertion proved:

  GET /not-a-route + Origin: http://evil.example    expected 403, actual 404 discovery body

There is a pre-existing order variant too: handleAction checks the HTTP method before Origin, so:

  GET /action + Origin: http://evil.example         expected 403, actual 405

Neither response exposes analyser data and a normal tokened POST action is still protected, so I do not
classify this as a demonstrated exploit. It does, however, contradict the hard security invariant at the
new browser-addressable surface. Put the Origin refusal ahead of method/path-specific replies on every
route and retain tests for the unknown-path and wrong-method cases.


F3 — REQUIRED — the discovery response gives the wrong token contract

ActionServer.java:158 says:

  X-Analyser-Token (required by /action and /manifest, not by this reply)

But `handleManifest` performs no token check, and the established test deliberately calls GET
`/manifest` without one and expects 200 (ActionServerTest.java:55-63). The public manifest is the useful
bootstrap design; the new text should therefore say the token is required by `/action` only. Pin that
fact by calling the manifest without a token and asserting the discovery wording, rather than merely
checking that the header name occurs somewhere.
