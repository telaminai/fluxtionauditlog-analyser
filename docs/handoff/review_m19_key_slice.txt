3. FINDINGS
================================================================================

F1 (LOW, code — the entry's wipe challenge, answered): saveProfileAndActivate validates the
profile NAME before entering the try/finally that wipes the key:

    name = requireProfileName(name);   // throws for e.g. "../outside" — key untouched
    requireKey(key);                   // wipes on blank itself
    try { ... } finally { Arrays.fill(key, '\0'); }

An invalid name therefore returns the caller's char[] unwiped — and the store's own test suite
exercises exactly that path (profileNamesCannotEscapeTheProfilesDirectory) without asserting a
wipe. The dialog clears the JPasswordField in its catch, but the char[] it obtained from
getPassword() survives until GC. Fix is one move: hoist requireProfileName inside the try (or wipe
in the dialog's catch). save() is correct: its only pre-try throw is the blank-key case, which
wipes internally.

F2 (NOTE, no change requested): buffer wiping is a hygiene gesture, not heap erasure —
new String(key) inside the save paths necessarily creates immutable copies (the Properties value,
the store buffer). Nothing in the code or docs overclaims this today; recorded so the CHANGELOG's
"wipes caller buffers" is never later upgraded to a heap-secrecy claim it cannot honour.

F3 (LOW, cross-repo compatibility note): Properties.store escapes '=', ':', spaces and non-ASCII
in the stored VALUE. The builder reads the file back through Properties.load, so round-trip is
correct — but the starter's check-fluxtion-key.sh reads the raw line
(grep '^apiKey=' | cut -d= -f2-) and would see the ESCAPED form of a key containing those
characters. Real keys are UUID-shaped, so practical risk is low; worth one line wherever the
shell contract is next touched (starter-side; recorded in my repo's queue, not this slice's).

F4 (ENDORSED — the entry's second challenge): preserving unrelated canonical-file properties on
rewrite is the right decision. ~/.fluxtion/fluxtion.apiKeyFile is shared with the Maven plugin and
the visualiser lineage; only apiKey is this dialog's to write, and clobbering the rest would break
tools that own them. The accepted casualty is Properties semantics: comments and ordering of a
hand-authored file are lost on rewrite. Acceptable, now recorded as intended.

F5 (BEHAVIOURAL NOTE, intended-as-built): deleting the ACTIVE profile clears the active-profile
marker but leaves the canonical key configured — so the row/card still say "present" with no named
profile active. Defensible (deleting a profile should not break builds); recorded so the state is
known-intended rather than rediscovered as a bug.
