===============================================================================
F1 — BLOCKER: replacing a framework auditor leaves an authored node marked framework
===============================================================================

This is now reproduced through the production GraphML emitter, not inferred from source.

An EventProcessorConfig starts with its framework clock registered under the name `clock`.
`addFrameworkAuditor` records that name in `frameworkAuditorNames`. If an author subsequently does:

    config.addAuditor(new AuthorClock(), "clock");

the auditor map contains the author's instance, but `addAuditor` does not remove `clock` from the
framework-name set. The compiler consumes that stale set and emits the author's class as:

    id=clock, class=...AuthorClock, fluxtion.framework=true

That makes M45's authored-node coverage denominator wrong: a real authored node is excluded. The
public API javadoc makes the opposite promise, saying an author-registered auditor is absent from the
set even if it shares a framework name.

The fix belongs at the single authority in the public API, not in the exporter. Plain `addAuditor`
must make the resulting binding authored; `addFrameworkAuditor` must make it framework. Because the
latter currently delegates to the former, change their ordering or use one internal registration
method rather than adding a compiler-side exception. Pin both replacement directions in the public
repository, then add a compiler test that overrides `clock` and inspects emitted GraphML. The present
FrameworkProvenanceTest protects against package inference but does not exercise name replacement.

===============================================================================
F2 — RELEASE GATE: the documented BOM/base lockstep is not enforced
===============================================================================

The compiler parent uses `fluxtion.base.version=1.0.14-SNAPSHOT`, while fluxtion-bom deliberately
still pins 1.0.13 during development. That asymmetry is reasonable. The design note and tracker,
however, say parent and BOM were bumped together and say BomBaseVersionGateTest enforces lockstep.
Neither statement matches the tree. The test checks that BOM pins are non-SNAPSHOT and that builder
uses the compiler version property; it does not require the release BOM to select the same base line
as the released compiler.

Correct the documents to describe the intentional development asymmetry and add an executable
release-time assertion. Otherwise a release can pair a compiler requiring public 1.0.14 with a BOM
that continues to select public 1.0.13. The release order is now public 1.0.14 first, compiler/builder
second, with the BOM aligned for release. Record `fc8d776` as the source revision paired with the
current snapshot so another clean machine can reproduce the build.

===============================================================================
N1 — consolidate the manifest gate instead of creating a second parser
===============================================================================

GraphMlManifestGateTest adds a useful check: emitted `<data>` keys are reachable in PARALLEL and
AGGREGATED output. Keep that assertion. Its regex/substring manifest parsing is order-sensitive and
duplicates the parsed manifest authority already in GraphMlMetadataTest, which reads the JSON and
checks declared/emitted status plus value types and enums. Fold the reachability assertion into that
parsed authority so field reordering cannot break the gate and the vocabulary has one source of
truth. The statement that the manifest was previously ungated should be narrowed accordingly.
