R11-1 — exact click identity

The old guard checked whether a word from the displayed line existed somewhere among a node's keys.
It selected price when the click was inside "price: adjusted", desk.price, or a string value containing
price: 42. Reproduced before changing production code.

NodeLogTokenizer now produces NodeLogData: entries and complete key spans in one parse. RecordParser
maps block-relative spans back to raw-record offsets, accounting for CRLF and skipped comments.
LogRecord memoises that one result. DetailPanel consumes it and adjusts for the displayed record's
start; it does not tokenize the displayed line to decide an exact key.

Limits are deliberate: multiline node items parse as before but publish no exact-click spans, because
the tokenizer folds their continuation whitespace. Their node-level menu remains available where the
clicked line identifies the node. Hand-built records without position data likewise make no exact claim.
The text evidence itself is unchanged. The wire format and reader's grammar declaration are unchanged.

R11-2 — evidence formatting

EvidenceText is shared by LogicalLogView, StepCursor and both MainFrame report-evidence paths.
Absence is bare @unkeyed; named keys outside the plain-name vocabulary are quoted and escaped, so a
business key named @unkeyed cannot look like absence. Quoted values retain their string identity.
This is an inspection format, not a new reloadable export. The Copy tooltip states that limitation.

R11-3 and specification corrections

M61 is labelled as the six-node quote engine with sparse logging, not a 30-node dense graph.
The older JFR explanation is explicitly separate from that measurement. format-spec §3a describes
complete spans and distinguishes an exact click from the node fallback, which may offer a genuine
named unkeyed property. ReportBinaryEvidenceTest's historical explanation is corrected: the old
named null field survived, while the string retained encoding quotes.
