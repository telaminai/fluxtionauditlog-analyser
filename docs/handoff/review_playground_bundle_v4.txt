Accepted conclusions
--------------------

1. **The report's §3 argument is sound.** `referenceBlock` renders the agreed resource's `why` text
   at playground `web/src/lib/starter/bundle.ts:599-611`; the brief's worked target deliberately does
   the same. The string `source-gen triage` is therefore a link description inside the generated
   reference block, not a local re-statement of the triage rule. The present whole-file scan in
   `tools/bench/bundle-bench.py:210-213` asks the producer to choose between the specified target and
   a green result. Scope the scan to the guide content after the stable "Everything below" boundary;
   make a missing boundary fail closed, and add a fixture which proves the token is allowed in the
   reference block but refused below it.

2. **The skill SHA resolution is a worthwhile scope addition, and the implementation does pin the
   skills.** `resolveRevision` resolves a raw GitHub branch to a SHA
   (`web/scripts/vendor-skills.mjs:273-290`) before the index and each skill are fetched through the
   resulting root (`:316-350`). One GitHub API call in a build-time vendoring step is a reasonable
   trade for reproducible snapshots and for removing the mid-vendor branch race. It needs the tests
   described in F4, and it must be extended to the other input before this claim can cover the bundle.

3. **The v1 suite was not weakened.** Its existing refusal and validation fixtures now explicitly pass
   `SKILLS_CONTRACT_V1` (for example `web/src/lib/starter/vendor-skills.test.ts:51,118-312`), so they
   continue to exercise the published v1 contract rather than accidentally invoking v2.

4. **The generated guide remains useful.** It gives real run/export/stop commands, explains the
   keyless run versus key-required regeneration boundary, gives the design and GraphML paths, and
   points the reader to the selected procedures. The deleted hand-written canon list has been replaced
   by a concise applicable-reference block, not by an empty guide.

Findings requiring correction
-----------------------------

F1 — BLOCKING: the reference-set snapshot is mutable, unpinned, and its override can record unsafe
provenance. The new skills path correctly resolves `main` before reading, but
`vendorReferenceSet` separately fetches `REFERENCE_SET_URL`, which still names `main`
(`web/scripts/vendor-skills.mjs:421-459,496-507`). The committed snapshot therefore records that
mutable URL as `source`, contains no resolved revision, and may describe references from a later commit
than the skills. `--reference-set` / `REFERENCE_SET_SOURCE` also bypass the source parser and its
credential/query/fragment refusal; a file URL or credential-shaped URL can enter the committed
snapshot's `source`. Finally, `--reference-set none` skips writing but does not remove an old snapshot.

For the canonical default, resolve the analyser repository once and fetch both the skills index and
`src/main/resources/reference-set.json` at that same SHA. Record a safe revision-bearing identity,
not the caller's raw URL. If a separate reference override remains supported, give it the same parsing,
pinning, refusal and provenance rules; make `none` remove/refuse a stale `reference-set.json`. Add
network-free tests for all of those cases. Until then, the report's "every byte comes from one commit"
claim is true only for skills, not for the v4 bundle inputs that generate `CLAUDE.md`.

F2 — BLOCKING: the analyser's own benchmark test suite regressed. The product check was renamed to
`agent guide declares exactly one supported contract`
(`tools/bench/bundle-bench.py:257-260`), while the unit fixture still expects the old name
`agent guide declares exactly the supported contract` (`tools/bench/test_bundle_bench.py:115-124`).
Update the expectation and rerun the suite. The normal generated-bundle run cannot substitute for a
red test of the gate itself.

F3 — HIGH: D-B2's important negative half remains unproved, and the advertised download seam cannot
currently exercise it. The implementation appears correct — it filters `appliesTo` at
`bundle.ts:599-601` — but `analyser-bundle.test.ts:403-420` asserts only that the Spring fixture has
the Spring resource. The imperative fixture does not assert its absence. Moreover its real ZIP test
always requires Spring's `application-context.xml`
(`web/src/lib/repl/maven-download-bundle.test.ts:87-98`), so setting `BUNDLE_TEMPLATE` to a non-Spring
template fails before the guide can be checked. Add the direct imperative-guide absence assertion and
make the ZIP inventory conditional on the model's Spring definition (or deliberately narrow the seam
and remove its claim to test any bundle template).

F4 — HIGH: the new v2 retrieval behaviour has no direct adversarial tests. No test imports or calls
`resolveRevision` or `vendorReferenceSet`; the old v1 tests cannot prove that a SHA is used for every
v2 request, that an API failure returns the declared transport outcome, or that malformed v2 indices
and specialisation selections refuse for the intended reason. Add deterministic `fetchImpl` tests that
record every URL and prove index, skills and reference set are all read at one SHA. Retain the v1
fixtures unchanged as the compatibility coverage.

F5 — MEDIUM: the profile assertion is partly self-referential. The generator compares `runbook.count`
with `SKILLS_MANIFEST.skills.length` (`analyser-bundle.test.ts:293`), so it detects an emitter mismatch
but cannot detect a wrong manifest selection. The named checks cover load, Mongoose and no replay, but
not the complete expected v4 set. Assert the literal four names for the acceptance Spring+Mongoose
template, separately from asserting that profile emission follows the manifest.

F6 — MEDIUM: successful bench output says an identical AGENTS.md "differs". The predicate is correct,
but `check_v4` always supplies that detail whenever the file exists
(`tools/bench/bundle-bench.py:215-218`). Emit no detail when the bytes match. A PASS line which says
"differs" weakens the evidence the hand-back is meant to provide.
