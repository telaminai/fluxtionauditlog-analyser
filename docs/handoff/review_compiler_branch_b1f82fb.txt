VERDICT: CHANGES REQUIRED BEFORE THE DIAGNOSTICS BRANCH IS RELEASED

The GraphML anchor/manifest repairs, event-walk regression, envelope repairs and released 1.0.14
pin all hold up. The author-precedence rule is coherent after tracing its registration routes. The
diagnostics closure does not: two known user-path failures are characterised but deliberately left
wrong, the new FLX-1002 producer violates the structured element contract, and the newest tracker
marks public error documentation Done while every emitted per-code URL tested returns 404.

This review started at 64909a1. b1f82fb arrived during the clean build and is included; it changes
only TRACKER.md, so the clean reactor at 64909a1 is code-equivalent evidence for the reviewed head.
The compiler worktree was not edited and its pre-existing untracked tmp/ was preserved.

===============================================================================
F1 — BLOCKER: the two “pinned defects” are defects to fix, not policy choices
===============================================================================

The handoff asks whether FLX-1005 should become reachable through Fluxtion.compile and whether an
interpreted cycle should be checked before the name map. Yes to both. Neither changes which graph is
accepted; both replace the wrong failure with the diagnostic this branch already declares as the
contract. There is no compatibility trade-off that justifies shipping the wrong answer.

Duplicate names
---------------

Both public paths reject a duplicate explicit name as an uncoded Guava BiMap failure:

    IllegalArgumentException: value already present

The coded FLX-1005 producer exists in TopologicallySortedDependencyGraph.registerNode but the public
path bypasses it: config public nodes are merged with inst2Name.putAll(...), and the duplicate value
fails inside HashBiMap before registerNode or the DTO diagnostic stage can run. The new test asserts
"UNCODED" as current behaviour while the registry/current-state table says Java hard failures are
Done and FLX-1005 names both colliding nodes. Those cannot both be release truth.

Route the public-node merge through the same validation/diagnostic authority as registerNode, then
assert FLX-1005 through Fluxtion.compile and FluxtionInterpreter. Preserve the raw failure only as a
historical regression explanation, not as the expected result of an acceptance test.

Interpreted cycles
------------------

The interpreted path rejects the cycle but reports a duplicate framework node named nodeNameLookup;
the AOT path reports FLX-1007 for the same topology. A framework name the author never supplied is
not an alternative policy—it is false attribution. Run cycle validation before the merge that masks
it, or fix the merge collision, and require the exact FLX-1007 code through both public paths.

The point of structured diagnostics is that an author can act on the first failure. Freezing two
known wrong first failures would release the compiler in the state this project was created to remove.

===============================================================================
F2 — BLOCKER: FLX-1002 emits the wrong structured element
===============================================================================

BuilderDiagnostics.exportedServiceMethodReturnTypeNotGeneratable emits:

    element(DiagnosticElement.node(nodeName, serviceInterface))

That says kind=NODE and stores the SERVICE INTERFACE in the nodeClass property. The real node class
is absent. The promised serviceInterface and method properties are absent too; method exists only as
a RelatedRef. This violates the registry's minimum structured fields for FLX-1002 and gives a consumer
a semantically false NODE element.

The model already has exactly the right authority:

    DiagnosticElement.service(serviceInterface, method, nodeName, serviceName)

Use the SERVICE element. If the concrete node class is also useful, carry it as a correctly-labelled
related reference rather than overloading nodeClass. Add FLX-1002 to SchemaConformanceTest's
producer-generated fixture set and assert the JSON fields, kind and schema. The new tests check only
message text and suggested-fix substrings, so this wire defect is invisible to all 3,718 green tests.

===============================================================================
F3 — BLOCKER: “Public error docs Done” points users at live 404s
===============================================================================

b1f82fb changes the current-state table to:

    Public error docs | Done | error-scope.md is the per-code scope reference for
    fluxtion.com/errors/, backed by DiagnosticScopeTest

error-scope.md is source/reference content in this repository. It is not a deployed per-code page.
Every BuilderDiagnostics entry emits a URL of the form https://fluxtion.com/errors/<CODE>. A live
request to https://fluxtion.com/errors/FLX-1002 at review time returned HTTP 404. Search found no
indexed FLX-1002 or FLX-1005 page on that host.

Do not mark public docs Done until each emitted URL resolves to content for that code. Either deploy
the pages before the compiler release, point DOCS at the actual owned documentation host, or keep the
status open and omit/redirect documentationUrl until it is real. A diagnostic's repair link taking a
new author to a dead domain is worse than no link because it advertises an unavailable support path.

===============================================================================
F5 — HIGH: FLX-1002's boolean exemption is asserted, not behaviour-tested
===============================================================================

The policy direction is sound: void and primitive boolean are the two signatures the generator can
honour; other return types already fail and now deserve a coded pre-generation rejection. The test
does not establish its load-bearing justification.

aBooleanExportedMethodIsAcceptedBecauseItControlsPropagation asserts only that compilation succeeds.
It never returns false, invokes the generated service, or observes whether a dependent fires. The
class javadoc still says the node's boolean value is discarded, yet the production generator uses it
in processor.setDirty(node, node.method(...)) when ExportService.propagate=true; only the wrapper's
outward return is hardcoded true. The prose and behaviour remain conflated in the very fixture meant
to settle them.

There is also an unreconciled second rule: ValidateExportServiceVoidReturn and
SubstrateLintExportServiceVoidTest still warn on every non-void @ExportService method and say exported
services are command surfaces. The new diagnostic says boolean is a supported propagation idiom. One
compiler must not teach both rules depending on which validation surface runs.

Add runtime cases for boolean true/false with propagate=true and propagate=false, assert dependent
invocation separately from the wrapper's outward return, and add a primitive non-boolean producer
case. Then change the substrate lint to share the same void-or-boolean predicate and wording. Keep
one authority for the rule.

===============================================================================
N1 — provenance precedence is accepted; add the inverse controls
===============================================================================

“Explicit author registration wins over the same identity arriving through GenerationContext” is a
coherent ownership rule, and the Anchor fixture proves the collision that required it. Source audit
found no reason to reverse the decision. The two constructor loops apply the same identity rule and
markCompilerInfrastructure stops at an authored identity, which is internally consistent.

The blast-radius evidence is narrower than the rule. The framework control in
FrameworkProvenanceTest is the clock auditor, whose provenance comes from the separate
frameworkAuditorNames channel. Add plain context-only and context-public-only nodes and assert they
remain framework=true, beside the overlap case that becomes authored=false. That pins both sides of
the precedence rule without relying on the auditor exception. This is additional hardening, not a
finding that the current Anchor output is wrong.

===============================================================================

===============================================================================
