1 · WHAT THE COLLISION WAS, AND HOW IT RESOLVED  (historical)
================================================================================

Two sessions implemented GraphML edge metadata within an hour of each other, in the same file,
neither able to see the other: `9402fe7` ("Slice 4") on the feature branch, `dd36bc5` on the handoff
branch. They agreed on the diagnosis and disagreed on key name, edge shape, whether the emission was
toggleable, and where the facts came from.

Resolved, per the compiler's own tracker (finding F6): `9402fe7` reverted, `dd36bc5` cherry-picked as
`7e63cbc`. One exporter path, one key name (`refKind`), one relationship model, one toggle governing
all of it, default OFF. Two follow-up commits then fixed the spike's concrete value defects and made
model ownership the documented gate for flipping that default.

The remaining architecture item — relationships re-derived by reflection rather than captured where
the compiler decides them — is recorded in that tracker as an owner-confirmed gate, and is specified
in the compiler repo at `design/model-rationalisation/README.md`. Nothing further is needed here.

================================================================================
2 · STILL OPEN: the build fingerprint is published but not emitted
================================================================================

Measured at `3091862`: the key manifest carries 26 keys, **19 emitted and 7 planned**.
`fluxtion.toolchainVersion` and `fluxtion.generatedAt` are emitted. **`fluxtion.sourceFingerprint`
is one of the seven planned** — specified in `docs/specs/meta-data-improvements/README.md`, declared
in the manifest with `status: planned`, and produced by nothing.

This was assumed to have been covered by the combining work. It was not: the integration settled the
edge model and the toggle, and the fingerprint was never in scope for either branch.

WHY IT IS WORTH MORE THAN ITS SIZE

It is the only artefact that answers "is this graph the build that produced this log?" from two files
and no running processor — which is the normal forensic case, and the normal LLM case. Today that
question is answered by counting unmatched instance ids, a heuristic that cannot distinguish "wrong
build" from "this cycle simply did not touch those nodes".

In a loop where a model regenerates repeatedly, the most likely silent failure is not a bad
diagnostic — it is the model reading the PREVIOUS build's graph and reasoning confidently about code
that has since changed. Every other artefact in the loop is checkable; without the fingerprint, the
pairing between them is not. It is the loop's integrity check rather than bookkeeping.

It also has two other consumers already waiting, which is the argument for doing it once:

* `ProcessorDescriptor.sourceFingerprint()` exists and returns null. Two fingerprints that can
  disagree would be worse than one, so the GraphML value and the descriptor value must be the same
  computation.
* `FLX-1021` (stale checked-in generated source) is marked *Design needed*. With a fingerprint
  stamped in the generated source header it becomes decidable: recompute, compare, and name the
  class whose signature moved. That is the difference between a diagnostic that can exist and one
  that cannot.

WHAT STILL NEEDS DECIDING BEFORE IT CAN BE EMITTED

The spec proposes SHA-256 over a canonical serialisation of the generation inputs — node names,
classes, callback kinds, ranks, edges with their relationship facts, service contracts, audit regime,
generator identity — sorted, and explicitly EXCLUDING timestamps, absolute paths and the generated
source text.

Two owner decisions remain, both recorded as open questions in the spec:

1. the exact input set — in particular whether the audit regime belongs in it, since a traced and an
   untraced build of one graph are arguably the same graph and definitely different artefacts;
2. whether the AOT path must be reproducible under `SOURCE_DATE_EPOCH`, and whether a build wanting
   byte-identical output can suppress `generatedAt`.

The property that makes it useful is that two builds of unchanged input produce the same value. If it
moves every rebuild, every comparison is a false negative and the key is worse than absent — the same
failure mode as the reflection-ordering instability already found and fixed in this vocabulary.

SEQUENCING

Independent of the model-rationalisation work: the fingerprint is computed from the model, not from
the relationship carrier, so it does not wait on that gate. It can be emitted while the vocabulary
default is still OFF, and it is arguably the one key that should be emitted regardless of the
toggle — a document that does not say which build wrote it is a document nothing can trust, whatever
else it carries.
