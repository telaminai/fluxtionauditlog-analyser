WHY THIS EXISTS, IN THE OWNER'S WORDS
  "I thought we would be able to choose a template from the swing app to make it seamless to get
  started" … "this is the missing low friction onboarding step".

  Today a first-time reader changes tool three times before seeing one record: browser (pick and
  download a template) → terminal (build, run, export) → analyser. The browser hop is the one that
  can be removed, and removing it makes the analyser the place onboarding STARTS.

WHAT IS DONE — the playground half, live in production now

  GET https://fluxtion-playground.dev/start/scaffold?template=<id>
      [&artifact=<a>][&group=<g>][&basePackage=<p>]
      -> 200 application/zip, content-disposition attachment; filename="<artifact>.zip"

  · <id> is the `file` value from https://fluxtion-playground.dev/starter-templates/index.json,
    with or without the ".starter.json" suffix. All 14 catalogue entries are fetchable; a test
    asserts that, so a new template cannot be added and be unreachable.
  · The three overrides are optional; an unset field keeps the template's own default. They exist
    because the template is a SHAPE and the project is generated to the user's names
    (spec-agent-brokered-dev-loop §C2) — without them this would be a fixed zip.
  · Errors: 404 unknown id (the body NAMES the catalogue URL and lists the available ids, so a
    client can recover without documentation); 404 for a path-shaped id; 400 if both ?s= and
    ?template= are given (they are alternatives, and silently preferring one teaches the wrong
    model); 422 if an override makes the spec invalid — never a zip that will not build.

  Verified against PRODUCTION after the deploy, not only in test:
      ?template=analyser-bundle            -> 200, 38,564-byte zip, unzips to audit-analyser-bundle/
                                              with CLAUDE.md, AGENTS.md, config/, run + export + stop
      ?template=analyser-bundle&artifact=risk-engine -> 200, project rooted at risk-engine/
      ?template=nope                       -> 404
      ?template=analyser-bundle&s=x        -> 400
      ?template=..%2Fetc                   -> 404
      /starter-templates/index.json        -> catalogue 1, both onboarding entries, keyNeed "none"

A LIVE BUG THIS FOUND, WORTH KNOWING BEFORE YOU COPY THE PATTERN
  The gallery derived its key badge from `mode` alone, and KEY_BADGE.none ("No key") was
  unreachable because no mode maps to it. So the site showed "Key once at build" on analyser-bundle
  — which commits its generated processor and builds with NO key. The one template the tutorial
  recommends carried a false warning as the first thing a new user saw. `mode: aot` means "the
  cloud compiler generated this", which USED to imply "you need a key at build"; M19 broke that
  equivalence and nothing had noticed. Fixed by an entry-level keyNeed override.

  Note the shape of it, because your picker can reproduce it: keyless-to-BUILD and keyless-to-
  REGENERATE are different claims, and only the first is true of the bundle. It ships
  check-fluxtion-key.sh deliberately, as a preflight for the regeneration build.

THE ONE DECISION THAT IS NOT MINE TO MAKE (spec §D-3)
  Whether the analyser may ever RUN the downloaded project. I recommend NO for this slice and the
  spec is written that way. Runbooks.java deliberately stores POINTERS, never commands, so that
  opening a colleague's project with an agent attached cannot execute text they wrote; and the
  analyser executes nothing derived from file content today (only S3 fetches and MCP client
  launches, both user-initiated). Downloading an archive and running a script out of it is a
  different act. If the owner wants it, it should be its own slice with its own review, and the rule
  should be that the analyser runs a FIXED, KNOWN command for a template it fetched itself — never a
  string read out of a downloaded file.

  Until that is decided, element 8 is "show and copy". The reader still uses a terminal for
  build/run/export; three tools become two.
