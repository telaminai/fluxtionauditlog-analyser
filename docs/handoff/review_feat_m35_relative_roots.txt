2. WHAT I TRIED TO BREAK, AND COULD NOT
The obvious way to get project-relative paths wrong is a path that is not under the project. I
expected `../../elsewhere/lib/src` — fragile, and it leaks one machine's layout into a committed
file. It is handled: `toPortable(path, projectRoot)` falls back to the `~` rule when
`!abs.startsWith(root)`, so an outside root is written as itself.

  · a root OUTSIDE the project → round-trips unchanged                        [test added]
  · a root that IS the project root → written ".", resolves back to the root  [test added]
  · the `Properties.store` date line is genuinely stripped — and if the regex ever stopped
    matching, their own `writingWhatTheFileAlreadySaysIsNotAWrite` would fail, because two writes
    would then differ. Transitively covered; I wrote an explicit test, then deleted it as redundant.

Also verified by reading: `baseDirFor` requires BOTH the `.analyser` directory name and the
canonical file name, so `.analyser/other.fluxtion-settings` correctly anchors at `.analyser` (they
test this); project-relative is tried BEFORE the `~` rule, which is the point — a project inside
the home directory must not come out `~/work/proj/src` on a teammate's clone; forward slashes are
forced, which is right for a committed file.
