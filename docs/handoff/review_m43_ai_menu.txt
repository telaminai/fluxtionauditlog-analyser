1. THE ATTACK LIST, ITEM BY ITEM
================================================================================
The model change (Map<String,String> → Map<String,Runbooks.Pointer>) — HOLDS. One map, not a
  parallel description map, is the right shape (two maps disagree about which runbooks exist). The
  old-profile path was verified independently as asked: readRunbooks reads `runbook.N.description`
  which a pre-M43 file lacks → null → Pointer(path, null); pinned by
  RunbookDescriptionTest.aRunbookWrittenBeforeThisSliceStillLoads. SettingsShare import re-gates
  both halves; the share label names the description as cargo and a test asserts it (D-AI8).

A refused description costs the description, not the pointer — ENDORSED. The pointer is
  load-bearing and the description a convenience on top; the refusal is NAMED in the refused list
  (readRunbooks adds the reason), so nothing degrades silently. Consistent with the house rule
  everywhere else: degrade loudly, keep what still works.

Discovery's bounds — HOLD, with one asymmetry (F1). Depth 7 / 50 results with the cap named,
  SKIP list covers the big offenders (.git, target, node_modules, venvs, dist…), symlinked
  DIRECTORIES are skipped so the walk cannot leave the project, unreadable files are skipped
  without abandoning the scan, and the walk never throws. Scanning this repo returns empty
  quickly (re-verified). Candidates the gate would refuse are filtered before offering — the
  offer/store invariant from the other side.

The offer/store invariant (usableName) — HOLDS. Reduction only removes what is unusable, never
  invents; the final check is `Runbooks.refuse(cleaned, "ok.md")` itself, so the invariant is
  enforced by the real gate rather than a parallel rule that could drift.

AiMenuTest's source-text checks — ACCEPTABLE AS A TRIPWIRE, and should be understood as one.
  Two honest limits: `indexOf("\n    }")` finds the first 4-space-indented brace after the method
  start, so an inner construct formatted at that indent would silently truncate the checked
  region; and the check only covers buildAiMenu()'s body — a forbidden call in PointerDialog is
  outside its sight (PointerDialog's own gate usage is what covers that). Both limits match the
  ProjectPanelIsRevealOnlyTest precedent this follows. The renamed-method guard (assert with a
  message naming the fix) is the right way to keep a source-text test from rotting into a no-op.

================================================================================
2. THE THREE DECISIONS
================================================================================
D-AI5 (declared, never read at serve time) — ENDORSED, and it is stronger than the spec argues.
  The spec's argument is drift (context changing when a file changes, with nobody declaring it).
  There is a second: serve-time frontmatter reads would make `context` a function of repository
  FILES rather than the gated profile — anyone or anything with repo write could alter what the
  analyser asserts about the project without ever touching the profile the gates guard. Declared
  severs that path. The cost (a description that rots when the file evolves) is real but visible:
  the Project panel shows the declared text next to an Open that shows the file, so drift is
  inspectable by a human. If it ever bites, the cheap remedy is a VIEW-time drift hint in the
  dialog (a human-initiated read is already D-AI5-legal — prefill proves it); do not revisit
  serve-time reads.

D-AI9 (no red, no "tested") — ENDORSED. Red-unspent matches the house pattern (the coverage caveat
  stays off a perfect score for the same reason), and "MCP ready"-never-"connected" is enforced by
  test against the exact trap McpSetupState's javadoc names. OTHER_INSTANCE earning the light its
  place is correct — it is the state this review itself proved real in M42 (the endpoint file is
  last-writer-wins). The light rendering live is now VISIBLE in the committed ai-menu.png
  ("MCP starting", amber, bottom-right).

D-AI1 (panel states, menu acts) — ENDORSED without qualification; it preserves M37's D-L3 instead
  of eroding it for convenience, and AiMenuModel extracting the decisions from the listener is
  what made D-AI2/3/4 testable at all.

Also verified beyond the list: `context.runbooks[]` gains the description INSIDE the pre-existing
above-the-early-return block (the ONBOARDING trap explicitly avoided); KnownKeys owns the family
and the M38.7 preserve-unknown test was updated; the D-AI4 no-execute rule holds in PointerDialog
(refusals rendered in-dialog with the reason, per D-AI6).

================================================================================
3. FINDINGS
================================================================================
F1 (minor) — SkillDiscovery skips symlinked DIRECTORIES but not a symlinked SKILL.MD FILE:
  visitFile does not check Files.isSymbolicLink, and SkillFrontmatter.read follows links, so a
  crafted in-project symlink causes a read OUTSIDE the project during discovery. Contained — what
  escapes is two inert strings shown to a human in a dialog, and the STORED pointer is the
  in-project symlink path — but the walk's "cannot leave the project" claim deserves the one-line
  symmetry fix (`if (Files.isSymbolicLink(file)) return CONTINUE;`).
F2 (nit, no action) — the truncation flag can over-claim: at exactly MAX_RESULTS the next file
  visit sets truncated even when no further skill exists. Honest in the safe direction.
F3 (note) — SkillFrontmatter reads only single-line frontmatter values; a YAML folded/multi-line
  description yields no suggestion. Correct for a prefill (it is a suggestion, not a parser), noted
  so nobody files it as a bug.
F4 (process) — the push race: M43 was pushed to origin while this clone held unpushed M33.7 work,
  so reconciling required a rebase that REWROTE the M33.7 SHAs — rotting the very SHA references
  the M33.7 review had just fixed in its report (they are re-fixed in the commit carrying this
  review, and frozen by pushing it). Lesson for the two-session workflow: a handoff report that
  cites SHAs should be pushed promptly after it is written, and a session that pushes to a shared
  main should say so where the other session will look.
