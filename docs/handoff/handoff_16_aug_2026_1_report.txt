1. WHAT SHIPPED
================================================================================
S1  topology/StepCursor — the model, no Swing
    One cursor at two depths: record → nodeLogs row → next record. Arrival at a record is its own stop
    (ENTRY), which is where the entry point is marked before any node highlights. prev() from an entry
    lands on the PREVIOUS record's last row, not its entry — the log is complete both ways and stepping
    should read the same in either direction.
    16 tests, driven by BOTH real fixtures so the regime difference is asserted rather than assumed
    (the traced fixture has more rows for the same cycle — that assertion is the brief's thesis).

S2  cursor overlay on the canvas
    Current position is a halo drawn OUTSIDE the box; the trail of already-stepped rows a weaker halo;
    the entry a dashed one. The node keeps its own execution border and fill underneath.
    Deliberate: recolouring the current node's border is the obvious implementation and would trade the
    epistemic state (what the log establishes) for the navigational one (where you are). Stepping is
    precisely when both are wanted.

S3  wiring
    RecordSource reads the table's visible rows, so "next record" means next in the FILTERED view.
    Rolling into another record re-shades the canvas and moves the table selection; a guard flag stops
    the table ⇄ cursor sync looping. Detail viewer highlights the cursor's nodeLogs line BY OCCURRENCE.
    Keys: [ and ]. F3/Shift+F3 untouched.

S4  docs
    topology.md "Step through a cycle" rewritten; spec-graph-replay §4 records the finalised
    granularity, replacing its looser "step node-by-node" wording.

2. SEMANTICS CONSTRAINTS — HOW EACH IS HONOURED
================================================================================
The brief called these non-negotiable; each is enforced somewhere a change would break a test or a
visible label, not just by intention:

  "row order IS the dispatch sequence; layers say nothing"
      The cursor walks nodeLogs order. The ordinal badges already painted come from the same list, so
      cursor and numbers cannot disagree — they read the same source.

  "untraced records: the label must say rows are only the logged nodes"
      StepCursor.positionLabel() emits "row 3 / 8 (logged nodes)" untraced and "invocation 3 / 16"
      traced; both spellings are asserted in StepCursorTest. Silent nodes keep their RAN_SILENTLY /
      MAY_HAVE_RUN shading at every step because the cursor overlay never touches the border.

  "traced records: stepping is exact, absent nodes stay DID_NOT_RUN"
      AuditTrace decides; the shading comes from classifyCycle, which the cursor does not modify.

  "the same instanceId in several rows — each row is its own step, do not dedupe"
      steppedSoFar() keeps repeats; two tests cover it, one fixture-driven and one explicit. The detail
      highlight resolves BY OCCURRENCE for the same reason — first-match would highlight the wrong line
      and quietly claim the cursor is somewhere it is not.

  "record sequence respects the shared filter"
      RecordSource is the table's visible rows.
