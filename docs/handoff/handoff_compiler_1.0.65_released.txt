===============================================================================
THE BACKEND IS DEPLOYED, AND THE ENVELOPE CROSSES THE GATEWAY
===============================================================================

This is new since your last review and it changes what a remote build gives you.

The wire envelope carries side-band facts beside the payload — the model
fingerprint out, the server's diagnostic report back — because Kryo's default
FieldSerializer is positional and the payload's shape is frozen. Until today it
was inert in production: the deployed compiler predated it and answered 415, so
every remote build fell back to a plain call.

1.0.65 is deployed. Measured, not assumed:

  * A production build now stamps a descriptor fingerprint. That is the ONLY
    artefact that proves the envelope crossed — GraphML and client-side
    diagnostics appear IDENTICALLY in a fallback run, so neither is evidence.
    The fingerprint is computed client-side, its field is transient so it cannot
    ride the payload in either format, and the only code that sets it server-side
    reads it out of the envelope metadata.

  * The response leg too: a deliberately broken graph returned FLX-1001 in the
    sidecar as a structured wire-contract document, beside the client's own
    FLX-1008. FLX-1001 is raised during SOURCE generation, which runs
    server-side.

  * A local server was listening on 8080 throughout and would have produced the
    same fingerprint. Excluded three ways: the client logged the production
    endpoint; the run was repeated with the local server killed, same digest; and
    the service's own network log shows three POST /generate-source -> 200, ONE
    PER BUILD. One request per build is itself proof of no fallback — a 415
    produces two.

NOT established, and the compiler tracker says so: whether the gateway PRESERVED
the content type or whether byte-level magic detection rescued a REWRITTEN one.
The magic and the envelope shipped together, so there is no envelope-aware client
without it to test against. Both work; the measurement cannot separate them.

WHAT THIS MEANS FOR YOU: a remote AOT build now returns the server's diagnostic
report as a structured document, not just prose in an exception. If you have code
that parses compiler failures out of message text, it can stop.

===============================================================================
THE DTO WIRE ROUND-TRIP YOU ASKED TO BE MADE A RELEASE GATE
===============================================================================

You wrote: "Ask upstream to make that round-trip a release gate: it is the only
change on the branch whose failure mode is simultaneous." Reasonable, and it is
now the case, though arrived at from the Kryo side rather than yours.

Three gates run in the reactor on every build:
  RemoteResponseCompatibilityTest  — the response's serialised shape is identical
                                     to released 1.0.64, field names and order
  DtoWireCompatibilityTest         — the DTO wire shape
  ReleasedDtoWireGoldenTest        — pinned against the released 1.0.64 payload

And the constraint behind them is measured rather than argued: KryoFieldEvolutionTest
asserts that adding a field to a wire class BREAKS a pinned Kryo reader. That is
why nothing new is ever added as a field, and why the envelope exists at all.

Your backwards-compatibility assessment ("the DTO wire is the high-risk surface,
because the server is always latest and every client is pinned") was the correct
read, and it is the reason the wire shape is frozen rather than versioned.
