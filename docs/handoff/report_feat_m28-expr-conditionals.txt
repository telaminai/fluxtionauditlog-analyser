2. DECISIONS BEYOND THE SPEC'S LETTER (flag these in review)
================================================================================
D1  NON-CONTRIBUTING RECORDS ON A FULL WINDOW — the spec says an empty/under-filled window is NaN
    and a NaN sample leaves the window unchanged, but not what a FULL window ANSWERS on a record
    that contributes nothing. Implemented as an anchor split, stated in Evaluator's javadoc:
      - AGGREGATES (mean/sum/rollingMin/rollingMax) describe the WINDOW, which exists independently
        of the current record → a full window answers. This is what makes mean(if(c,x),10) a
        CONTINUOUS "mean of the last 10 breaching samples" (holds between breaches) — pinned by
        the gateTheOutputVersusGateTheInput test.
      - lag/delta are anchored to the CURRENT sample ("N samples ago" needs a now) → no finite
        sample this record, no point this record.
    I believe this is the only reading that makes the review's own composition argument work, but
    it is the one place I chose semantics the spec did not dictate.
D2  lag needs N+1 samples before it speaks (the spec's "NaN until N have been seen" is off by one —
    the value 1 sample ago requires 2 seen). Implemented correctly; test names it.
D3  delta on a gap: prev is KEPT through a NaN sample (D-W2), so the next delta measures ACROSS the
    gap (1, NaN, 3 → deltas NaN, NaN, 2). The alternative (reset on gap) would erase a real past.
D4  rate is (newest − oldest) over the pruned window — the spec's "(last − first)/window — change
    per T" formula read literally would double-normalise; for a "1m" window, newest − oldest over
    that minute IS the change per minute.
D5  MAX_WINDOW = 1_000_000 samples (parse error above): beyond that a "window" is a whole-series
    statistic, which is a spec non-goal. Durations are uncapped — memory is bounded by samples
    actually inside the window.
D6  Time-windowed rollingMin/Max: the monotonic deque discards dominated samples at insert; this is
    the standard sliding-window-minimum structure and correct under time pruning (a dominated
    sample is strictly older than its dominator, so it can never outlive it into being the answer).
    Stated here because it looks lossy on first read.
D7  (M28.6) Band unknown-handling: the condition is extracted as a series, so NaN samples are OMITTED
    before the interval walk — an unknowable stretch neither opens nor closes a band, meaning a band
    runs from the first held sample to the next measurably-false one, BRIDGING unknown gaps. The
    alternative (unknown breaks the band) would claim the condition stopped holding on no evidence.
    Pinned by ConditionBandsTest.unknownSamplesNeitherOpenNorCloseABand.
D8  (M28.6) Band conditions evaluate under LOCF, not the graph's per-series resolve choice — a band
    has no resolve knob. Cross-node conditions are the whole point of bands and STRICT would blank
    them; a per-band resolve can be added if anyone ever asks.
D9  (M28.5) No manual UI for authoring guides/bands was added — the spec's P1/P2 shapes are verb-
    first, and the UI READS them (paint, persistence, share). If hand-authoring is wanted it is a
    dialog on the existing setGuides/setBands seams.
