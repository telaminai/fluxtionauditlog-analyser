### N1 — Medium: showAll escapes R5's pre-check; a refused save has already removed the focus

**RUN + READ.** `src/main/java/telamin/fluxtion/audit/analyser/analyser/ui/ActionExecutor.java:1280`, `:1390`; `ui/TopologyPanel.java:413` (same package prefix).

Concrete sequence on the committed round-three graph:

1. Select `rootNode`, then apply its node focus. Context depth is **1**, visible nodes **1**.
2. Submit `topology {showAll:true, saveFocusAs:"review-focus"}`.
3. The reply is `ok:false`, `nothing to save — the full graph is not a focus; apply one first`.
4. Context depth is now **0**, visible nodes **11**. The prior focus has gone.

The predictor receives `select`, `pop` and `focus`, but not `showAll`. It sees the existing focus and allows the request. The apply path then calls `showAll()` before the save, clearing precisely the state that made the save acceptable. This is the same whole-or-refused defect R5 was meant to close, through another supported combination. The new R5 tests and mutation all pass while this happens.

**Required:** account for the entire preceding topology transition when validating a save, including `showAll` and its selection-clearing effect. Refuse before applying anything, or establish a valid replacement focus before saving. Add a regression on a nonempty existing focus, checking the complete before/after state, and a mutation that omits this transition from preparation. Keep the existing pop and focus-then-save cases. The changelog's whole-or-refused claim depends on this correction.

Reproducer: [RereviewProbe.java](evidence/m44-4-single-state-2026-09-24/rereview-probe/RereviewProbe.java), `ATOMIC_*` in [output.txt](evidence/m44-4-single-state-2026-09-24/rereview-probe/output.txt). No production edit or test double of the transition was used.

### N2 — High: a report series silently substitutes resolution and scope

**RUN + READ, including the exported PDF.** `src/main/java/telamin/fluxtion/audit/analyser/analyser/ui/ReportSeriesPicture.java:42`, `:43`, `:46`; `ui/MainFrame.java:1407`.

`ReportSpec.SectionSpec.call` is documented as the parameters that produce the series data (`report/ReportSpec.java:77`). The new renderer reads only `expr`/`key`, forces **LOCF**, and uses the current UI filter. It does not honour the call's `resolve` or `filter`, and does not report either as ignored.

Two concrete counterexamples:

- Records alternate `nodeA.x=1`, `nodeB.y=2`, `nodeA.x=4`, at three times. `series {expr:"nodeA.x + nodeB.y", resolve:"STRICT"}` returns **0 points**. A report series with that same call draws **2 points** by carrying values across records.
- Three `rootNode.v` values occur at 1000, 2000 and 3000. `series {expr:"rootNode.v", filter:{from:2000,to:2000}}` returns **1 point**. A report containing that exact call exports **3 points**, with an axis spanning 1000–3000.

I exported the second case through the built jar's real report action and rendered both PDF pages to images. Page 1 correctly draws the saved one-node focus. Page 2 visibly draws the three-point series and captions it `rootNode.v · 3 points · under the current filter`. The caption describes the substituted scope, but never discloses that the requested scope was ignored. `report` returned success without a warning. This is not an exit-status-only observation.

**Required:** honour the stored series call's data-selection/evaluation semantics, or refuse unsupported semantics explicitly with NOT RENDERED and a reason. Share the parameter interpretation with the series path rather than maintaining a second interpretation. Pin both counterexamples through the report adapter and exported artifact; a mutation that forces LOCF or drops the call filter must fail. Do not treat `ChartSeriesAgreementTest` as covering this: it bypasses this adapter and supplies matching filters and resolution manually.

Evidence: [direct probe](evidence/m44-4-single-state-2026-09-24/rereview-probe/output.txt), [PDF probe](evidence/m44-4-single-state-2026-09-24/rereview-probe/PdfProbe.py), [actual replies](evidence/m44-4-single-state-2026-09-24/rereview-probe/pdf-output.txt), [two-page exported PDF](evidence/m44-4-single-state-2026-09-24/rereview-probe/focus-and-series.pdf). ### 1. R1 — capture, identity, filter and supersession

**RUN + READ: the reported race is corrected.** `ActionExecutor.captureCoverageInputs` captures the store, snapshot, topology input, filter copy and scan bound inside the single `onEdt` task. The scan itself is outside that task. `FilterState.copy()` copies time bounds, dimensions, grouping, text and its source function; the frame binds that function to the loaded store. Capturing the row bound prevents Follow growth from extending that scan unnoticed.

I traced the load callback, graph-change notification, filter action/listener and Follow timer: the frame's store replacement and `LogOpened` submission occur in one EDT turn, as do these graph/filter/append transitions. `LogOpened` is submitted before the store assignment inside that turn; this is not an externally interleavable pair of tasks. A pending request retains the old generation until the completion; it cannot give an old capture the completed open's new generation. Membership facts still go through the pair-identity gate.

`CoverageCaptureTest` queues a competing change from inside the suppliers. An EDT task cannot execute that queued task halfway through capture; on the defective off-EDT path the competing EDT change runs between suppliers. That is deterministic ordering, not a sleep-based race. Both capture and live-filter mutations failed their named assertions in my run. I did **not** rerun the original blocking `CoverageRaceProbe`: its supplier waits for the EDT while capture now runs on the EDT, so its timeout would test the probe's deadlock. The deterministic test is the appropriate replacement.

The P64 graph miss is correctly explained: the old code took the snapshot before the graph input. A graph switch in that gap stamped the old revision, which the session rejected as stale, rather than laundering old inputs under a new revision. I checked that order in the prior source; I did not reconstruct the author's pre-fix graph-test run.

The superseded reply checks generation/revision after the qualification attempt. Follow growth is instead handled by the captured bound and stale qualification scope; it is not a new generation. I found no new-identity route in the paths inspected. This is not a proof against every future callback or filesystem race.
