  W2  `Deque<Supplier<Boolean>> myStack` -> `ArrayDeque<BooleanSupplier> myStack`.
      The field was declared as the INTERFACE. A JIT profiles it to one concrete type and folds
      the call; closed-world AOT without profiles leaves a real invokeinterface standing on a path
      that runs on EVERY event.

  W2  Early return when the queue is empty, replacing an unconditional `dispatching = false` store.
      dispatchQueuedCallbacks() is called on every event and the queue is almost always empty.

  W3  `Supplier<Boolean>` -> `BooleanSupplier`. Every wrapper's dispatch() already returns primitive
      boolean, so the generic queue boxed a Boolean on every callback. This is a CORRECTNESS item,
      not a performance one: it means the re-entrant path allocated, which contradicts the
      zero-steady-state-allocation claim the project makes elsewhere.

W8 IS DEFERRED, DELIBERATELY, AND THE REASON IS RECORDED
  W8 was to give Clock a concrete ClockStrategy field. It cannot be done without an API break —
  ClockStrategy is the published extension point. Measured in situ it is +0.25 ns on JIT and on
  native+PGO, and +1.33 ns only on native-WITHOUT-PGO, a configuration §1 of the spec already rules
  out. So the deployable cost is +0.25 ns and the price is a breaking change. Not taken. If a
  reviewer disagrees, the argument to attack is "third-order, do it only if the field is being
  touched anyway" in spec §3.3.

TESTS ADDED — 12, in CallbackDispatcherEmptyPathTest (new file, 174+ lines)
  They pin BEHAVIOUR, not speed. Throughput is the conformance bench's job (W10), which asserts
  output equivalence before it believes any timing.

  Two of the twelve were added late, after review of the diff found the claim underpinned:

    theInFlightItemStaysOnTheQueueDuringItsOwnDispatch
    fireIteratorCallbackDuringDispatchGoesToTheFrontOfTheQueue

  Here is why they exist, and this is THE THING TO ATTACK ON THIS BRANCH:

  `dispatching` is not a debug flag. fireIteratorCallback() reads it to decide whether an iterator
  goes to the FRONT of the queue (a dispatch is in progress, so this must run before queued work) or
  the BACK. The old code executed `dispatching = false` unconditionally, including on the empty path;
  the new code returns before it. That is only safe if a NESTED call cannot reach the early return
  while an outer dispatch is running — otherwise the inner call clears the outer's flag and a
  subsequent iterator is queued to the wrong end. Silent reordering, not a crash.

  It cannot happen, because the in-flight item is removed only AFTER its dispatch() returns false, so
  the queue is never empty when observed from inside a callback. That premise is now a test rather
  than a paragraph: if a future change removes the item first, the test fails instead of the ordering
  drifting unnoticed.

  This reasoning is MINE and has not been independently checked. If it is wrong, the change is a
  latent reordering bug in the re-entrant path. Attack it first.

  The other reachability question, stated for completeness: the early return also skips the store when
  `eventProcessor == null`. Reaching that with `dispatching == true` requires nulling a public field
  from inside a callback. Judged pathological, not defended.
