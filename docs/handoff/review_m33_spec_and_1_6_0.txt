NaturalOrder — CONFIRMED CORRECT, including the parts that usually go wrong in natural sorts.
  I walked the transitivity traps: equal-value digit runs with differing zero-padding, case ties,
  digit-vs-letter boundaries. The comparator is a lexicographic order over a per-string token key
  (lowercased chars; maximal digit runs as values), with `a.compareTo(b)` breaking ties ONLY inside
  full key-equality classes — a genuine total order. Digit-vs-letter cross-comparisons are consistent

3. THE M33 SPEC — ADOPT, WITH TWO AMENDMENTS
================================================================================
The principle (references + connective prose, never a document) is right, D-I1/D-I2/D-I7/D-I8 are
the strongest decisions in it, and the effort claim is honest (PdfDoc 354 / FindingReport 329 lines,
verified exact). The findings:

F1 (SUBSTANTIVE) — a wrong log RESOLVES; it does not dangle. The non-goals say "opening it on a
  different log is the D-I3 unresolved-anchor path". That is factually unsound: recordIndex 42
  resolves on ANY log with 43 records, a chart name resolves against project state, a series call
  re-runs anywhere. Against the wrong log, every section renders confidently — fresh, plausible,
  WRONG evidence under narrative written about different data. D-I3 only catches absence; this
  failure arrives present.
  AMENDMENT: a report stores a small LOG FINGERPRINT at authoring — log name/root, record count,
  first/last logTime (identity data, not evidence; references-only survives) — and the renderer
  compares and announces: "written against demo-quote-series.yaml · 726 records · 09:00→09:18; the
  loaded log differs". Without this, the spec's own principle sentence is unenforceable. With it,
  the cross-log non-goal gains teeth and the "re-runnable claim" use case (D-I3's best feature)
  becomes explicit rather than accidental: same log lineage, moved on = re-verification; different
  log = misapplication, and the page says which.

F2 (SUBSTANTIVE) — the filter context is part of the claim. Evidence sections re-run "against the
  live log" — meaning under the CURRENT FilterState. D-I7 celebrates the numbers moving with the
  filter, rightly, for a table viewed as a query. But an investigation's narrative was written
  against a specific extraction context; render the same prose over silently different-but-resolved
  evidence and the report carries two accounts of itself — D-I1's drift class, arriving inside one
  document. M27 built the exact tool for this: a named filter context.
  AMENDMENT: a report stores the FilterState (or a named-focus reference) it was authored under.
  On open, OFFER to apply it (offer-never-act, M20.5/D-R5's pattern); declining renders under the
  current filter with a standing line naming the difference. At minimum the rendered page must say
  which filter produced what the reader is looking at.

F3 (minor) — D-I8's rowWhen has no stated evaluation model. Bands evaluate conditions over the
  record walk with LOCF carry; a table row is one record. Two implementers will choose differently.
  Write one sentence: rowWhen evaluates against the row's record with the same carry semantics as
  bands (or STRICT within-record — either is defensible; pick).

F4 (minor, optional) — D-I2's standing label could carry authorship (agent narrative vs user note).
  The chart explanation/notes don't attribute either, so consistency argues against; mentioned only
  because a REPORT is the artifact most likely to leave the building.

Acceptance additions if F1/F2 adopt: (9) opening a report against a different log names the
fingerprint mismatch before rendering any section; (10) opening under a different filter offers the
stored context and labels the render if declined.
