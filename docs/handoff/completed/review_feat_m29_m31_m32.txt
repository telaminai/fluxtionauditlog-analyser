3. NEW FINDING — THE CAPTURE HARNESS REPORTED SHOTS IT NEVER TOOK
================================================================================
Not this branch's doing; it predates it. But it came to light doing the docs pass this branch needs,
and it silently invalidates the answer to "are the screenshots current?".

`capture()` aimed `screencapture -R` **directly at the asset** and then tested success with
`target.exists()`. The asset is already there from the previous run. So when the shutter fails —
here, "could not create image from rect", i.e. no Screen Recording permission for the invoking
terminal — the old file is still present, `exists()` is true, and the run prints:

    ✓ topology-explore.png  (597 KB)

for an image it did not take. I confirmed the shutter genuinely fails in this environment by calling
`screencapture` directly: no file produced. Then I ran the harness twice and observed **zero** assets
change — which I first read as evidence of the harness's reproducibility, and which actually meant
nothing had been captured at all.

`menu_capture()` had the identical bug.

That is the failure mode this script exists to prevent, reproduced inside the script: the release
screenshots once carried real venue names onto the public site because "grep cannot read a PNG", and
the answer was to generate images rather than take them. A generator that reports success without
generating restores exactly the blind spot it was built to close.

FIXED HERE (tools/capture-docs.py):
  - capture to a scratch path, copy onto the asset only when a file was actually produced;
  - never replace a good native asset with a painted fallback — a painted shot has no title bar and
    drops glyphs ("Time range" renders as "er nge"), so a silent downgrade is worse than a stale file
    you were told about. An existing asset is KEPT and the shot is reported as not regenerated;
  - a painted fallback is written only when no asset exists at all, and labelled
    "NOT publication quality, do not commit as-is";
  - failures are collected and the run **exits non-zero**, naming every shot it could not take.

Same harness run, before and after the fix:
    before:  done — 12 captures
    after:   done — 0 of 12 regenerated; 12 NOT captured: screenshot-light.png, … (exit 1)

The committed assets were never damaged: for existing shots the old code returned early without
copying, so the painted fallback only ever reached the one NEW filename I added. I deleted that.
