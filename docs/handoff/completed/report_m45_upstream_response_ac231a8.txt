1. THE RELEASE GATE — DONE, AND THE SPEC WAS RIGHT ABOUT THE SHAPE OF THE RISK
================================================================================

"Old client + new server is not an edge case, it is the default state of every user who has not
bumped, and a server upgrade exercises it for all of them at once with no rollback available to them."
That is exactly right and it is why this was worth blocking on.

`DtoWireCompatibilityTest` (fluxtion-builder) now covers the mechanism:

  · a NEW-client node — carrying the @ServiceRegistered/@ServiceDeregistered descriptors — round-trips
    in both Java and Kryo;
  · an OLD-client node, with those descriptors simply absent, reads on current code;
  · a descriptor naming an annotation the reader has never heard of survives as DATA. Annotation
    identity on the wire is a String, which is why this addition needed no new class and why the next
    one will not either;
  · KRYO REGISTRATION IDS ARE PINNED. This is the gate that matters. The change added instances of an
    already-registered type, so the failure mode that would actually bite is an id SHIFT — ids are
    positional and both ends must agree. Verified by inserting a registration and watching NodeDto
    move from id 10 to 11, so the test fails for the real reason rather than passing by luck.

STATED PLAINLY, because the review's own standard demands it: this is NOT the cross-jar test you asked
for. It covers the mechanism, not the artefact. Loading the last released builder on an isolated
classloader and round-tripping between two versions of one class would cover the artefact; that stays
open, and it is the right thing to add if a future change touches a FIELD rather than a list's contents.

2. REACHABILITY — RESOLVED, AND IT WAS THE RIGHT QUESTION
================================================================================

M45 asks whether `-Dfluxtion.graphml.metadata` reaches the exporter under `fluxtion-maven-plugin`, on
the grounds that a mechanism that exists but cannot be reached from the path users take is the same
failure as the sidecar. Checked in the plugin source rather than reasoned:

  · `AbstractFluxtionMojo.buildFluxtionClassLoader` builds a URLClassLoader over the project classpath;
  · the mojos load the generator class through it and invoke it REFLECTIVELY, in the Maven JVM;
  · there is no fork — no ProcessBuilder, no exec, no forked-JVM configuration anywhere in the plugin;
  · the mojo already sets system properties itself (output and resources directories), so the pattern
    is one the plugin relies on.

**So `mvn -Dfluxtion.graphml.metadata=PARALLEL` reaches the exporter, and so does
`-Dfluxtion.diagnostics.sidecar`. M45.1 can proceed as written.**

3. THE SIDECAR — YOUR HEADLINE FINDING, NOW CLOSED
================================================================================

`writeSidecar` had two referents in the tree: its own class and a unit test. You were right that this
was the ask rather than a scope note, and right that it made two rows of your pinned comparison
unrunnable.

`EventProcessorGenerator` now writes it, opt-in with `-Dfluxtion.diagnostics.sidecar=<path>|true`.
Errors arrive through the catch around model building; warnings through a collector wired to the graph.
A write failure is logged and swallowed — a build must not fail because its diagnostics file could not
be written. `DiagnosticSidecarProductionTest` drives `Fluxtion.compile`, not the writer, because a unit
test on the writer cannot fail the way the product was failing.

**Its first real output is itself a finding, and it is one of yours.** On a CLEAN build the sidecar
contains FLX-1008 naming `serviceRegistry` — a framework node. The framework-noise policy was already
open upstream; it is now visible in a file rather than buried in a log, which is an argument for
settling it before you start consuming warnings.

5. BYTE STABILITY — COULD NOT REPRODUCE, FIXED ANYWAY
================================================================================

Honest result: five separate JVM runs across two graph shapes were byte-identical. Your graph is larger
and yours is the measurement that matters, so not reproducing is not disproving — and the mechanism you
describe is real: `vertexSet()`/`edgeSet()` order traces back through the dependency walk to maps keyed
by node objects, whose identity hashes differ between runs.

Fixed defensively, because it is cheap and independently required by the fingerprint: vertices sort by
emitted id, simple-graph edges by (source, target), and the relationship list by endpoints then the
relationship's own discriminator. Verified after the change — three separate JVM runs identical at OFF
and at PARALLEL.

If you still see drift after taking this build, please send the artefact; that would mean a second
source of order I have not found.

7. WHERE M45 AND THE UPSTREAM SPEC DISAGREE, AND WHO IS RIGHT
================================================================================

7a. D-V0 — dual-path is permanent. ACCEPTED, and upstream should adopt the framing. The metadata spec
    describes `fluxtion.framework` as replacing a maintained name list. Your correction is better: it
    demotes it to a fallback that still has to be maintained. Upstream's own tracker already says the
    key is not emitted at all yet (see 7b), so the honest statement is weaker still.

7b. `fluxtion.framework` IS NOT EMITTED, and M45.4 depends on it. This is the one place M45 plans
    against something that does not exist. Node creation is now RECORDED — factory, generation context,
    @Inject, transitive reference from those — but the framework registers the clock, node-name lookup
    and service registry as AUDITORS, and `EventProcessorConfig.getAuditorMap()` lives in the open
    `builder-api` artefact and mixes those with any auditor the author added. Rather than publish
    `false` for a node the compiler created, the key and `fluxtion.authoredNodeCount` are `planned` in
    the manifest and withheld. The metadata spec's "Ready" marker describes the ask, not the output.
    **M45.4 is blocked upstream, and closing it needs a builder-api change.** M45.3 and M45.5 are not
    affected — auditCapable, propagates, filters, handlerMethod and topologicalRank are all emitted.
    **But read §8 before building M45.5: topologicalRank was emitting the wrong order until dbcbe17.**

7c. D-V1 — refuse AGGREGATED. Agreed, and upstream's own javadoc is the evidence you quote. Worth
    adding: with propagation now answered per RELATIONSHIP rather than per vertex pair, two edges on one
    pair can legitimately disagree, so AGGREGATED's merge is lossier than when you assessed it, not less.

7d. Release footprint — confirmed. Only `fluxtion-builder` needs releasing. `fluxtion-runtime` is
    untouched, so your 1.0.13 pin stands, and the metadata switch is a system property rather than a
    `FluxtionCompilerConfig` method, so `fluxtion-builder-api` gains nothing.

8. AMENDMENT — topologicalRank was the WRONG ORDER, and I had reported it fixed
================================================================================

TAKE dbcbe17 OR LATER BEFORE M45.5, AND REGENERATE ANY FIXTURE MADE WITH AN EARLIER BUILD.

WHAT WAS WRONG. `topologicalRank` was an index into `getObjectSortedDependents()` — the OBJECT
sorted order, which is field/construction order — not `getSortedDependents()`, the dispatch order.
Those two lists part company exactly where push is involved, because push edges are inserted
reversed. Measured on a graph with one push reference:

    generated dispatch : ... joiner, sink
    published rank     : sink=7, joiner=8        <- the opposite

and against the implementation before the fix the gap is wider: pusher=10, target=3.

WHY THIS MATTERS TO M45 SPECIFICALLY, which is the reason it is worth a whole section:

  · M45.4's blocker (fluxtion.framework, §7b) is a MISSING key — you plan around it and lose a
    feature. This is different in kind: the key was PRESENT, plausible, and reversed. D-V4 item 2
    makes it "a column"; a column of integers reads as authoritative, and nothing downstream would
    have told you the two numbers were the wrong way round.
  · your own baseline is why it matters most here. Sibling dispatch order is the question three of
    three agents could not answer from the artefacts, and four of six previously concluded
    declaration order. Shipping a rank that inverts across push edges would have replaced "cannot
    tell" with "confidently wrong", which is a worse position than the one you measured.
  · it is the same defect class as the two we already fixed on this branch — per-pair propagation
    and the @TriggerEventOverride demotion. A value that is wrong rather than missing, and readable
    without any signal that it should not be trusted.

HOW IT GOT INTO A REPORT, because the process point is the transferable part. The call site was
renamed to `model.dispatchRank(...)` and the local variable to `dispatchOrder`, while the method
behind them still returned the object order. The rename made the claim LOOK true, I wrote it into
the integration report, and it survived your review and mine — because both of us were reading the
report's prose against the diff, and no test asserted the ordering at all.

It was found because the owner asked whether the rank was relied on anywhere or was "an arbitrary
observed index after generation". That question, not a test, is what exposed it. The lesson I am
taking: on this branch every CODE change has been mutation-checked, and the REPORTS have not been
held to the same standard. A claim in a handoff is an assertion like any other.

NOW COVERED, each mutation-checked against the implementation it replaces:

  · topologicalRank follows dispatch order, asserted across a push edge;
  · nodes and edges are emitted in SORTED order — the stability fix from §5 had no direct test, and
    without the sort the emitted order is visibly walk order;
  · a method-reference capture is a labelled relationship. The compiler follows
    `MethodReferenceReflection.captured()[0]`; the field holds the lambda WRAPPER, so the old
    emitter matched nothing and left the edge bare. This was on your unproven-routes list.

Anchors and exported callbacks remain uncovered, and I am not claiming otherwise.
