8. WHAT TO ATTACK — YOUR THREE
===============================================================================

ATTACK 1 — THE GATEWAY CONCLUSION. IT HOLDS, and the strongest counter-route is closed by
absence rather than by argument.

The route that would have collapsed it is not the payload — it is the SERVER RECOMPUTING the
digest from the DTO it already holds. The fingerprint is a hash of the model, and the server
has the model, so a recomputed value would be identical and indistinguishable.

It cannot. fluxtion-generator-http's main source contains ZERO references to ModelFingerprint.
The server has no code that can produce the digest. The only server-side write is
Main.java:302 — WireEnvelope.metaValue(requestMeta, "sourceFingerprint") — and the field it
writes into is transient on SourceGenConfig, so it arrives null under any serialisation
format. JavaSourceGenerator then stamps sourceGenConfig.getSourceFingerprint() verbatim, null
when absent.

So a non-null descriptor fingerprint in a remotely generated processor can ONLY have arrived
through envelope metadata. Independently instanced here: our production regeneration today
stamped 7a01dd06…346e, and it equals the client-computed GraphML digest for the same model.

ONE LIMIT, which your handoff already states and which this evidence does not remove: this
proves the envelope metadata REACHED THE SERVER. It does not separate "the gateway preserved
the content type" from "byte-magic detection rescued a rewritten one". Your conclusion is
correctly scoped as the former not being established.

ATTACK 2 — THE M45.4 FIX. THE WINDOWS ARE STILL THERE, AND YOUR REASON FOR THEIR
UNREACHABILITY IS WRONG.

You say they are "unreachable now that framework nodes never enter the set". That is not what
closes them, because the windows are not about framework nodes at all.

Both guards read authoredNodes BEFORE the matching addAll populates it:

    guard at ~285   then   authoredNodes.addAll(rootNodes)            at ~294
    guard at ~305   then   authoredNodes.addAll(publicNodes.keySet()) at ~319

The node at risk is an AUTHOR'S node that arrives through the generation context AND appears
in rootNodeConfig.getNodes() or publicNodes. It is marked compiler-created by the guard, then
authored by the addAll, and export reads compilerCreatedNodes — so the author's own root node
is published as framework plumbing. Excluding framework auditors from authoredNodes does not
touch that path. Anchor.anchor, the route that produced F1, is exactly how an author's node
gets into context.getNodeList().

NodeClassificationInvariantTest's five shapes are plain, author-auditor, event-audit, anchored
and referencing. NONE uses rootNodeConfig, and none puts one instance into both a context
collection and publicNodes. So the honest status is UNREACHABLE-IN-THE-TESTED-SHAPES, REASON
UNVERIFIED — not unreachable by construction.

The fix is smaller than the test: hoist both addAll calls above their guard loops, or register
all author nodes before any context merge. Then the windows close structurally and nobody has
to write the shape that would have found them.

ATTACK 3 — ONE THING IN THE HANDOFF IS INCOMPLETE.

"At OFF the only unconditional GraphML change is still edgedefault=directed, which your parser
does not read."

The CONCLUSION is right — the parser reads neither, and we verified that in item 5. The
STATEMENT is incomplete: the OFF-mode diff between 1.0.64 and 1.0.65 is 154 insertions and 154
deletions, and the bulk of it is the DOCUMENT ORDER of the nodes, not edgedefault. Content is
equivalent; serialisation order is not.

Worth correcting because of who it misleads: anyone diffing committed GraphML, or holding a

node document order and edgedefault both moved" and the next reader spends no time on it.
