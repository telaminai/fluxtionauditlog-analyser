F-A (MEDIUM, LATENT) — the F1 precedence blast radius. Your attack point 1.
===============================================================================

METHOD: rather than hunt one route, the invariant was asserted directly. A temporary probe
in the TopologicallySortedDependencyGraph constructor recorded every case of
authoredNodes ∩ compilerCreatedNodes != {}, and the full 3496-test corpus was swept.

The probe was PROVEN LIVE first, by making it unconditional and confirming it fired (3319
records from a single test class). Without that step a null result is indistinguishable from
a probe that never ran — the same hollow-assertion failure this branch has been fixing, and
the first run of it was in fact checking the wrong tmpdir and reported a false clean.

RESULT: 3315 violations, every one the same node — serviceRegistry.

CAUSE, and it is not GenerationContext. EventProcessorConfig's own constructor:

    addFrameworkAuditor(serviceRegistryNode, ServiceRegistryNode.NODE_NAME);
    addNode(serviceRegistryNode, ServiceRegistryNode.NODE_NAME);      <-- author-facing API

That addNode puts the registry into inst2Name, so the constructor's
`authoredNodes.addAll(inst2Name.keySet())` marks the framework's own node as AUTHORED. The
auditor loop later adds it to compilerCreatedNodes because it is a framework auditor. Export
consults only compilerCreatedNodes (GraphMlFacts.isCompilerCreated), so the emitted answer is
right. The two sets disagree and nothing notices.

THE ANSWER TO THE QUESTION AS ASKED: yes, there is an identity where the opposite precedence
is correct, and it is serviceRegistry. But the sharper statement is:

    authoredNodes does not mean "the author registered this".
    It means "this reached addNode" — and the framework calls addNode itself.

So the F1 guard `!authoredNodes.contains(contextNode)` has a live false-positive today. It is
rescued only because the auditor loop runs afterwards and re-marks the node. Any future
framework node that goes through addNode and is NOT also a framework auditor would be
silently misclassified as authored: wrong fluxtion.framework, inflated authoredNodeCount, and
no test would fail.

TWO ORDERING WINDOWS COMPOUND IT — in both, authoredNodes.addAll runs AFTER the guard loop
that reads authoredNodes:

    rootNodes    addAll at ~269, guard loop at ~261
    publicNodes  addAll at ~294, guard loop at ~281

A node arriving through both routes is marked compiler-created and then marked authored, and
compilerCreatedNodes wins. Not reachable in the current corpus; the shape is the same as the
defect F1 fixed.

SUGGESTED FIX, cheapest first: assert the invariant in the constructor. Better: collapse to a
single classification function returning one answer, so the two sets cannot disagree.

SEVERITY: latent, not live. The emitted GraphML is correct today on every graph tested,
including the analyser's. This does not block the release.

outside reviewer to run it lost a full matrix to this.

YOUR ATTACK POINT 3 — are the two behaviour fixes RIGHT?
===============================================================================

FLX-1005 routed through the diagnostic path: RIGHT, and complete.
  requireUnusedName returns early when existing == node, so idempotent re-registration still
  works. requireUnusedNames force-puts provisionally, so a duplicate WITHIN one map collides
  instead of reaching the BiMap. Both colliding class names are in the diagnostic.

Failed dependency-tree build made sticky and replayed: RIGHT.
  dependencyTreeFailure is an INSTANCE field and the graph is constructed per build, so a
  cached failure cannot poison an unrelated build — the obvious objection, checked and
  dismissed. It also makes failure symmetric with the existing `processed` success guard: the
  method is build-once in both outcomes, which is principled rather than a patch.

  ONE CAVEAT WORTH RECORDING: it masks rather than fixes the non-idempotence of
  buildDependencyTree — re-running still re-registers node factories and builds a second
  NodeNameAuditor. That is acceptable under build-once semantics, but the path is now
  unreachable and therefore untested. Anyone who later wants retry semantics must fix the
  non-idempotence first, and nothing will remind them.
