F1 · BLOCKING — FLX-1009 still wins a mixed failure and hides the graph reference
================================================================================

The mapper classification is now preserved, which fixes the collection and equals/identity
re-derivation defects. The code that SELECTS the diagnostic is still wrong:

  LiveGraphSourceGenExtractor.java:300-312
    stateOnly = valueOnlyFields(unmatched, mappedFieldKind)
    stateOnly.isEmpty() ? FLX-1001 : FLX-1009

Any VALUE field therefore selects FLX-1009, even when another unmatched field is a genuine
REFERENCE requiring a constructor. FLX-1009 names only the value field and recommends
@FluxtionIgnore/transient, while the reference that makes that remedy insufficient vanishes
from the structured result.

I drove the real extractor with a node holding:

  final Parent parent;       // REFERENCE
  final String counter;      // renderable VALUE
  MixedNode(Parent parent);  // no constructor for both mapped fields

  expected: FLX-1001
  actual:   FLX-1009

The branch's mixed test does not exercise this choice. ConstructorFieldForkTest:84-91 calls
valueOnlyFields directly, observes [counter], and never asserts which diagnostic production
selects. Its method name says the mixture is not reported as pure state while the production
call does exactly that.

Required correction: use FLX-1009 only when every unmatched field is classified VALUE.
Any REFERENCE or unclassified member makes the general FLX-1001 the honest result. Pin the
decision through TopologicallySortedDependencyGraphDtoBuilder, not the helper. Update the
stale direct-parent explanation at LiveGraphSourceGenExtractor:298-299 and README's fork
description at the same time.

F2 · BLOCKING — SPRING_BEAN_NOT_SELECTED still makes both false-positive decisions
================================================================================

Two independent production probes fail.

1. A supplier-wired child is reported as omitted.

   context.registerBean("child", Child.class, () -> child)
   context.registerBean("parent", Parent.class, () -> new Parent(child))
   nodeBeans = [parent]

   actual diagnostic: ... not part of the graph: [child]

The live Parent object holds Child and Fluxtion discovers that reference. The new traversal
does not inspect the live object graph; referencesOf at FluxtionSpring.java:397-428 reads only
RuntimeBeanReference values stored in BeanDefinition constructor/property metadata. Supplier,
@Bean and autowired wiring need not leave that representation, so the rule still implements
"explicit BeanDefinition reference", not issue #20's "unreferenced" condition.

2. An unrelated Auditor-typed bean is suppressed even though it is not added.

   context bean: unlistedAuditor = EventLogManager instance A
   config.auditors: [EventLogManager instance B]
   nodeBeans = [handler]

   expected: unlistedAuditor is omitted
   actual:   no warning

auditorBeans at FluxtionSpring.java:346-358 removes every Auditor-typed bean whenever any
auditor is configured. But addNodes at :213-219 adds an auditor only when
springConfig.auditors.contains(the exact context bean). The committed test at
SpringBeanNotSelectedContextTest:104-115 itself uses two different EventLogManager instances
and then states the context bean is in the graph. It is not; the test pins the false result.

There is a third fail-open/fail-noisy mismatch in the comments: beansReachableFromSelected
says an unreadable definition suppresses the whole report (:368-371), but it returns an empty
set and reportBeansNotSelected removes nothing (:277-290), so it reports more beans instead.

Required correction: derive omission from the objects actually selected as nodes/auditors and
the same live-reference walk the compiler uses, after selection has resolved. If that cannot be
done in this slice, narrow the rule/message to explicit selection facts; do not claim "not part
of the graph" from BeanDefinition metadata. Add real-context cases for supplier/@Bean wiring,
the exact configured auditor instance, and an unconfigured Auditor-typed bean.

F3 · BLOCKING — SchemaConformanceTest is a partial schema reimplementation, not validation
================================================================================

The prior review explicitly required a strict JSON parser and Draft 2020-12 validator. The
replacement reads the schema with SnakeYAML and manually implements only top-level required,
pattern, enum and minLength (SchemaConformanceTest.java:107-145). It ignores $ref, type,
allOf, if/then, const, items, minItems, minimum and format. Calling those four checks "the
schema, executed" overstates what the test proves.

Executable counterexample: I invoked that committed harness on this invalid element:

  { "kind": "NODE" }

The published schema's allOf/then requires nodeName and nodeClass, but assertConformsTo
returned normally. The independent probe failed only on its final assertion that the harness
must reject it. The committed self-test catches one lowercase code because pattern is one of
the four rules copied into Java; it says nothing about the rest of the schema.

The schema itself still contains two defects named by the prior review:

  - diagnosticsVersion's pattern accepts 2.0 even though this file is normative for 1.x
    (schema lines 13-16);
  - nodeName, nodeClass, mappedFields, stateFields and collidingNodes are conditionally
    required but are not declared/typed properties. A real validator therefore accepts a
    numeric nodeName and arbitrary list contents.

Its top description still says consumers tolerate unknown enum members while severity is the
only enum and is now deliberately closed; wire-contract.md's acceptance checklist still asks
for an unknown enum member to parse. The evolution decision was corrected in one paragraph,
not through the whole contract.

Required correction: use an actual Draft 2020-12 validator in test scope, parse as strict JSON,
validate producer-generated output for every implemented code, and add negative mutations for
the conditional element requirements and known property types. Pin the major version and make
the schema description/checklist agree with the closed severity decision.

F5 · REQUIRED BEFORE SIDECAR USE — writeSidecar still is not atomic replacement
================================================================================

DiagnosticJsonWriter.java:68-74 and wire-contract.md call replacement atomic. The implementation
does this at :89-93:

  delete existing target
  rename temp to target

There is an absent-file window, and a failed rename loses the last valid report. The test at
DiagnosticWireContractTest:222-241 verifies only the final state of successful create/replace;
it cannot distinguish atomic replacement from delete-then-create.

Required correction: same-directory Files.move with REPLACE_EXISTING + ATOMIC_MOVE, with a
documented REPLACE_EXISTING fallback where atomic moves are unsupported, preserving the old
target on failure and cleaning the temp on every path. This was N2 in the previous review and
was not disposed in the response.

F6 · INTEGRATION BLOCKER — do not merge Slice 4's unconditional GraphML emitter
================================================================================

Revision e1b31a0 unconditionally declares and emits fluxtion.referenceKind,
fluxtion.referenceField and fluxtion.propagates (JgraphGraphMLExporter.java:239-253,
:391-440). It therefore changes default GraphML bytes and exposes a vocabulary before a
consumer is ready. It also aggregates TRIGGER,DATA into positionally joined kinds/fields but
reduces propagation to one OR boolean. That cannot express propagation per relationship — the
distinction EdgeReference.java:59-68 says consumers need.

The acceptance evidence is narrower than the text: EdgeReferenceGraphMLTest imports
PushReference but has no push fixture; it has no mixed trigger/data pair, multiple same-pair
fields, callback-kind fixture or consumer test. The newer metadata work has already corrected
the central premise: GraphML output can expand one internal graph edge into multiple document
edges without changing the compiler graph, and its metadata modes are explicitly staged behind
fluxtion.graphml.metadata with default OFF.

Required integration decision: remove 9402fe7's Slice 4 from this branch or replace it with the
separately reviewed, default-OFF metadata implementation. Do not merge two competing key names,
relationship models and exporter paths. This review does not accept or reject that newer
uncommitted implementation; it is being reviewed separately.
