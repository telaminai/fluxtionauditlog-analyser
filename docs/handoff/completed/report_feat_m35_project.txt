================================================================================
1. WHAT SHIPPED (one paragraph, for the reviewer in a hurry)
================================================================================
`open {project}` is a route to machinery that existed (ProjectSession.open → LoadResult that never
throws; afterProjectChange(…, endsSession=true) that already closes the log and graph). What is NEW
is the echo, and the echo is the entire safety story, because the verb APPLIES and does not ask
(tracker M35.8, the settled decision). It names every project-owned category with before/after counts,
what it closed WITH PATHS, the previously active project, and the one call that puts it back.
`context` now names the project in force. `open {close: "project"}` exists because the decision's
promise — "the agent can put it back in one call" — was unfulfillable when the previous state was
"your own settings": there is no path to name for that, so it needed a verb (deviation D1).

================================================================================
2. THE ECHO — as built (differs from the brief's sketch; §3 says where and why)
================================================================================
  open {project: "<dir or .analyser/project.fluxtion-settings>"} →
  { "project": "<name>", "settings": "<file>",
    "replaced": { "sourceRoots": {"before": n, "after": m}, "mavenRepos": {…},
                  "eventProcessors": {…}, "selectedEventProcessor": {"before": fqn|null, "after": …},
                  "namedGraphs": {…}, "namedFocuses": {…}, "reports": {…}, "hiddenColumns": {…} },
    "closed": { "log": "<path>", "graph": "<path>" },          // absent members were not open
    "closedWhy": "a project is a session boundary (M35.5) … reopen them inside the new project"
                 | "nothing was open",
    "previous": "<name>" | "your own settings",
    "reversible": "open {project: \"<previous file>\"} puts it back"
                | "open {close: \"project\"} puts your own settings back",
    "ignored": [...], "ignoredWhy": "…"                        // only when other params rode along
  }
  Re-opening the ACTIVE project: { project, settings, "alreadyActive": true, "note": … } — nothing
  replaced, nothing closed. Reloading would flush live state over the file and read it back (M20
  auto-persist), so the session would end for no change; saying so is the honest answer.
  Failure (missing/unreadable/unparseable): ActionResult.error(<LoadResult.message>) — the reason
  IS the answer. applyProjectResult() is deliberately NOT used on this path: its failure is a dialog.

  open {close: "project"} →
  { "closed": "project", "project": "<name>", "now": "your own settings — …",
    "replaced": {…same shape…}, "closed": {…}/"closedWhy", "reversible": "open {project: \"<file>\"} …" }
  Its echo is its own: the `kept` sentence the other close cases carry ("profile state survives") is
  FALSE for leaving a project — that act is exactly the one that swaps the profile-state categories.

================================================================================
3. DEVIATIONS FROM THE BRIEF — each with the reason, none silent
================================================================================
D1 · `close: "project"` ADDED (the brief did not ask for it). The decision says the echo names the
    previous project "so the agent can put it back in one call". When the previous state is "your own
    settings" there is no path to name, and File ▸ Close project has no socket route — the promise
    could not be kept without this. It also makes E8 ("close project with both loaded") drivable,
    which the brief lists as an item to drive. Smallest fulfilment: one enum value, one switch case,
    reusing project.close() + afterProjectChange(…, true) exactly as the menu does.
D2 · `replaced` names EIGHT categories, not the brief's five. ProjectProfile.PROJECT_SCOPED owns
    Maven repos, reports and the selected event processor as well; a switch that replaced them and
    did not say so would violate the very rule the echo exists for. selectedEventProcessor is
    reported as before/after VALUES (a class name is what the caller needs to notice, not a count).
D3 · `closed` carries PATHS, not the brief's ["log","graph"] list. "Reversible from the answer you
    were given" has to include reopening what the boundary closed, and a bare word cannot be reopened.
D4 · Accepting the offer via the verb ENDS the session; the human's dialog accept KEEPS the log
    (E9's exception). This asymmetry is deliberate and stated in the schema: the brief's E7 requires
    "open log + graph, then open a project → both close", and a verb that sometimes closes and
    sometimes keeps, depending on where the log happens to sit, is a rule with a hidden branch — the
    kind an agent cannot reason about from the manifest. The echo's `closed.log` path makes the reopen
    one call, so the cost is one call and the rule stays flat. Reviewer may overrule; the change is
    one boolean at the applyProjectResult call and a schema sentence.
D5 · `context.project` ADDED ({active, name, settings} | {active:false, note}). E7–E10 are scripted
    checks only if the script can assert which project is in force afterwards; and an agent deciding
    whether to accept `projectOffer` needs to know what it would be leaving.

================================================================================
7. THE TRAP, AND HOW IT WAS AVOIDED
================================================================================
E7.3 is the proof: `context.projectOffer` names projA's settings file BEFORE E7.4 accepts it. The
fixture was built to make the offer fire — a log copied INSIDE the project directory, with
.analyser/project.fluxtion-settings two levels up — and the transcript shows it did. E9's KEEP half
is not asserted here at all, for the reason §6 gives; it is left as the eyeball item it is.

================================================================================
8. FOUND ON THE WAY — one fixed here, two recorded for their owners
================================================================================
F1 · FIXED (this branch) — `context` threw on a FRESH start. Before any log has ever been loaded,
    MainFrame.filter is null and context() dereferenced it: "Cannot invoke FilterState.fromMillis()
    because filter is null". The first call any agent makes against a just-launched analyser failed,
    which no test caught because every test loads a log first. E7.0 caught it because the isolated
    home had never seen one. Guarded: context answers with an empty filter and everything else it
    knows. CHANGELOG Fixed line added; a headless test would need a MainFrame, so it is verified by
    E7.0 here and stated as such.
O1 · RECORDED (M19.2) — relative source roots in a profile resolve against the PROFILE'S directory
    (.analyser/), not the project root. ProjectProfile.load passes file.getParent() as the base;
    SettingsShare.resolveAgainstBase's own doc says "a bundle that ships sourceRoot.0=src/main/java
    lands at <bundle>/src/main/java" — for the canonical profile it lands at
    <bundle>/.analyser/src/main/java. The first fixture used project-relative roots and every
    resolved root pointed at a directory that does not exist (visible in a discarded first run's
    context.source.roots). Nothing shipped depends on it yet — the writer never emits relative
    roots — but the M19 bundle contract does, so it must be fixed before M19.2 is called done:
    one line (base = file.getParent().getParent() when the file is the canonical profile).
O2 · RECORDED (M20) — opening a project and doing nothing REWRITES its profile. The fixture was
    hand-written with relative roots; after the run it held absolute ones (transcript tail). Auto-
    persist (ProjectSession.flush on the next switch) wrote the in-memory config back, and the
    writer emits ~-relative or absolute paths only. For a COMMITTED profile that is a diff nobody
    asked for on every teammate's machine — the very legibility ProjectSession's javadoc promises.
    Fix belongs with the writer (preserve the relative form the file had) — not this slice.
