2. THE GRAMMAR CHECK — answered BY the generator side (the entry's check #1)
================================================================================

skillsProvenance accepts: `none` · `canonical@<rev>` · `local@<rev>` ·
`mirror:<http(s), host, no userinfo/query/fragment>@<rev>`, rev ∈ [A-Za-z0-9._-]{1,120},
≤300 chars, no control characters, split at the LAST '@' (so an '@' inside a mirror path cannot
confuse the parse — verified by reading, and the userinfo case is pinned by test).

GENERATOR COMMITMENT (playground P2, recorded here so both sides hold the same contract):
  · default vendoring emits          canonical@<analyser-repo git SHA or tag>
  · corporate mirror emits           mirror:<https base URL, no userinfo/query/fragment>@<rev>
  · air-gapped local emits           local@<rev or date-stamp>  (the local PATH never enters it)
  · skills.source=none emits         none
  · revisions are git SHAs or tags; anything else (e.g. a semver with '+') is slugified to
    [A-Za-z0-9._-] before emission, so the grammar's rejection of '+' is a non-issue.
All four forms fall inside the accepted grammar; the credential-bearing and file:-URL shapes the
test rejects are shapes the generator will never emit. P3's bundle acceptance should add a
cross-repo conformance check: generate each mode, assert skillsProvenance() accepts the emitted
string verbatim — that turns this prose commitment into a fixture.
