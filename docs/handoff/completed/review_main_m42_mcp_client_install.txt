================================================================================
1. THE TWO DECISIONS THAT MATTERED, AND BOTH ARE RIGHT
================================================================================
**It never edits the client's config file.** `ClaudeMcpClient` and `CodexMcpClient` shell out to the
client's own CLI (`claude mcp add`, `codex`) and say so in the javadoc — *"Claude Code owns
~/.claude.json; this class never parses or edits it."* That is the correct call and not the obvious one:
parsing another tool's config is easy to do and impossible to keep right across their releases. The
analyser writes nothing it does not own.

**No shell anywhere.** Every launch goes through `ProcessBuilder(List<String>)` — probe, both clients,
the bridge. A jar path with a space or a quote is an argument, never a token to be re-split. The generic
JSON keeps the same property explicitly (*"every later argument remains a separate JSON string, never a
shell split"*), which is exactly where a copy-paste config would otherwise get it wrong.

`runningJar()` is properly conservative: multi-entry classpath refused, non-jar refused, missing files
refused, and it fails to `Optional.empty()` rather than guessing a launcher. The earlier review's F1 (debug
flags inherited) is closed, and the amendment from the M42.1 review — re-checking endpoint ownership AFTER
the probe, so a TOCTOU window returns OTHER_INSTANCE — is implemented at `McpConnectionProbe:118`.

================================================================================
2. F1 — A SECRET ON THIS APP'S COMMAND LINE REACHED THE CLIENT'S CONFIG FILE (fixed here)
================================================================================
`fromRunningJar` copies **every** JVM option before `-jar` into the bridge vector, checked only against a
denylist of debug agents. That vector does not stay local:

    ClaudeMcpClient.add(bridge)  → `claude mcp add …` → written into ~/.claude.json
    CodexMcpClient.add(bridge)   → written into the Codex config
    GenericMcpConfiguration.render(bridge) → JSON shown for the user to paste into a client config

So an analyser started with `-Dhttp.proxyPassword=…`, `-Dmy.token=…` or `-Dauthorization=…` put that
value into a file the user may sync, commit, or paste into a chat while asking for setup help. Nothing in
the path redacts it, and the setup dialog's whole purpose is to get that command in front of the user.

What makes this a finding rather than a nitpick is that **this codebase already refuses exactly this**.
D-C6 gates report destinations with `ReportDestination.CREDENTIAL` — AKIA keys, `token=`, `secret=`,
`password=`, `api_key=`, `authorization`, `bearer` — and the M38.5 review even hardened it to OFF by
default because "a webhook URL is a credential in path form". The rule existed; this entrance was missed.

**Fix.** The gate is now ONE definition (`ReportDestination.looksLikeCredential`) used at both entrances,
rather than a second copy that would drift — the copy that stops being updated is always the one still in
use. `unsafeForClientBridge` consults it, so a credential-shaped option refuses the whole command, keeping
the resolver's existing fail-closed behaviour rather than half-reconstructing a launch. Two tests: five
credential shapes refused, and a counter-test that an ordinary launch (`-Xmx2g`, `-Dfile.encoding=UTF-8`)
still produces a command — a gate that refuses everything would silently delete the fallback, which is the
failure nobody notices because it looks like the feature simply not applying.

The JBang path is unaffected and remains the documented route.
