THE DESIGN (owner-specified):
  One step cursor walks the log at two depths with a single Next/Prev:
      eventLogRecord → each nodeLog row within it → next eventLogRecord → its rows → …
  The topology follows the cursor: entering a record marks the ENTRY POINT (event or exported-service
  call — EntryPointResolver already resolves it); each step highlights that row's node as the current
  dispatch position, with already-stepped rows of the SAME cycle staying lit (accumulate within the
  cycle); rolling into the next record clears the accumulation and marks the new entry.

SEMANTICS CONSTRAINTS (from the merged fix branch — violating these re-introduces the bugs it fixed):
  - The row order IS the dispatch sequence; the layout's layers are a partial order and say nothing.
    The numbers already painted on nodes come from the log — the cursor and those numbers must agree.
  - UNTRACED records: rows are the nodes that LOGGED, nothing more. The step label must say so —
    "row 3/8 (logged nodes)" — and silent nodes keep their RAN_SILENTLY / MAY_HAVE_RUN shading at
    every step. Stepping must never imply "these were the only nodes that ran".
  - TRACED records (AuditTrace detects them): rows are every invocation; stepping is exact; absent
    nodes stay DID_NOT_RUN and the label can say "invocation 3/16".
  - The SAME instanceId can appear in several rows of one record — each row is its own step; the node
    re-highlights as current again. Do not dedupe.
  - Record sequence respects the SHARED FILTER (next record = next in the filtered view, like F3).

UX WIRING (all two-way, reusing what exists):
  - Next/Prev buttons on the Topology tab + keyboard (suggest [ and ] — F3/Shift+F3 stay
    anomaly-jump; do not overload them). Stepping past the last row advances the record; before the
    first row, retreats to the previous record's last row (bidirectional — the log is complete).
  - Record table selection ⇄ cursor: selecting a record puts the cursor at its entry (step 0);
    stepping into a new record moves the table selection.
  - Detail viewer sync: the cursor's current row is highlighted in the record detail's nodeLogs text —
    step in the graph, see the row; the two views narrate each other.
  - Status line: record timestamp · row k/n (+regime wording above) · instanceId · the row's key/values
    summarised.
