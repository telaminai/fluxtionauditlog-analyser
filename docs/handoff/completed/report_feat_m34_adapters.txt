================================================================================
1. graph(Path) ON THE SPI
================================================================================
    default Optional<SourceGraph> graph(Path source) throws IOException   // empty
    record SourceGraph(List<Node> nodes, List<Edge> edges, Provenance provenance)
    enum Provenance { DECLARED, INFERRED }

DEFAULT, deliberately — Capabilities' lesson from M34.1's first slice: this is a published surface
since 1.5.0 and every reader written against it must keep compiling. Pinned by a test that
implements the bare interface and asserts graph() is empty.

PROVENANCE RIDES THE RETURNED GRAPH, not the reader (spec review F4): availability is per SOURCE,
so a fixed graphSupport() on the adapter would be wrong for half its users — one estate has a
registry export where another has none. Returning EMPTY is the honest answer for a source that
cannot say, and it is a DIFFERENT statement from returning an INFERRED graph. The record REFUSES to
be built without a provenance, because an unmarked graph is the one thing coverage cannot safely
consume.

The core's own vocabulary (D-A4) — ProcessorTopology.Node/Edge, already engine-neutral. A richer
engine-specific model would force every consumer above to know which engine it was looking at,
which is the coupling this SPI exists to remove.

================================================================================
2. THE RECONCILIATION RULE — GraphSource
================================================================================
Two things can now supply a graph: a reader, and a person or agent via open {graphml}. Quietly
preferring either is how the analyser ends up confidently describing a system it is not looking at.

THE RULE IS M35.3's ASYMMETRY, ONE LEVEL OUT. That milestone settled it for logs and graphs: a
thing someone OPENED is intent and is respected; a thing that merely arrived is residue or
convenience and yields.

    NONE            -> anything may fill it
    OPENED          -> a reader NEVER displaces it
    READER_DECLARED -> replaced only by OPENED
    READER_INFERRED -> replaced only by OPENED

and the view always says WHICH, because D-A2 is not satisfied by loading the right graph — only by
saying which one was loaded and where it came from.

supportsCoverage() carries the finding the M34.0 spike paid for: coverage is "declared minus
observed", so against an INFERRED graph the subtraction is always 100% and the feature that found
the POC's 54 dead nodes becomes a tautology that still prints a number. INFERRED therefore returns
false, and the consumer must say so rather than show a ratio.

3. NOT DONE — and why it is a good place to stop
================================================================================
Slice 3 is the app wiring: SpiLogStore surfacing the reader's graph, MainFrame honouring
GraphSource precedence, the Topology panel naming the source beside M35.6's pairing note, and
coverage refusing a ratio on an inferred graph.

The two slices done here are PURE and fully tested. The wiring is Swing-side, sits on top of M35's
judgeOpenedGraph()/clearGraph(), and would be rewritten if M35 changes in review. Stopping at the
seam means this branch is reviewable on its own terms — the SPI shape and the precedence rule are
the decisions worth arguing about, and neither needs the wiring to be judged.

REVIEW FOCUS
R1  Is the precedence right? The alternative — a reader graph winning because it "came from the
    source itself" — is defensible and I rejected it: someone naming a file is a stronger signal
    than a default, and M35.3 already settled that shape for the same reason.
R2  supportsCoverage() returns a boolean; should it instead return the SENTENCE to show? The
    boolean puts the wording at each call site, which is how the coverage warning drifted apart
    from the panel before (M35.6 §13). Deliberate for now, worth challenging.
R3  SourceGraph throws on a null provenance rather than defaulting to INFERRED. Defaulting would be
    friendlier and would let a careless adapter ship a graph nobody can trust; throwing makes the
    author choose. Same call as Capabilities' non-null ordering, opposite conclusion — Capabilities
    DEFAULTS because every pre-existing container really was totally ordered, whereas no such
    default is true of provenance.

4. SLICE 3 — the wiring (added 2026-08-25, after M35 merged)
================================================================================
Done now that the branch sits on a merged main rather than a stack.

  LogStore.sourceGraph()          default empty — a text container is a stream of records and knows
                                  nothing about structure, which is why the GraphML has always been
                                  a separate file. Only an SPI reader answers differently.
  SpiLogStore                     asks the reader ONCE at open (a reader that scans a registry must
                                  not be re-invoked per query) and, if it THROWS, keeps the log and
                                  records why: an unreadable graph is a missing graph, and the log
                                  is still evidence. graphNote() carries the reason so the source
                                  does not look like one that simply had no graph.
  ProcessorTopology.of(list,list) the SPI speaks LISTS because that is the shape a foreign engine's
                                  API returns; forcing every adapter to build the id-keyed map would
                                  push a core implementation detail across the boundary. A duplicate
                                  id keeps the FIRST — the id is the join key to nodeLogs, and two
                                  nodes claiming one would make step-through ambiguous with nothing
                                  downstream able to detect it.
  TopologyPanel.loadFromSource    honours GraphSource precedence and returns whether it took the
                                  slot. loadedFrom stays null — it came from the log, not a file the
                                  user can point at — and the status names the source, adding the
                                  coverage caveat when the graph was inferred.
  MainFrame.offerSourceGraph      runs AFTER repairLoadedGraph, so a stale graph is closed before
                                  the new source is offered its slot. Order matters here: the other
                                  way round, the source's graph would be judged against the old log.
  coverage                        REFUSES on an inferred graph, naming why, instead of returning a
                                  ratio that is 100% by construction. This is the M34.0 spike's §4
                                  finding turned into a guard.

5 new tests (791 total): a declared graph reaches the store; no graph is not a failure; a THROWING
reader loses its graph and keeps its log, with the reason recorded; a native store offers nothing;
duplicate ids keep the first.

5. M34.2 (first half) — the ordering claim reaches the VIEW
================================================================================
M34.1's ordering slice plumbed `ordering: TOTAL | PARTIAL` to LogIndex and reported it in `context`
— and NOTHING CONSUMED IT. The topology went on painting ordinal badges over a source that never
decided an order, which is the M34.0 spike's §3 finding still live in the shipped code. This closes
it.

  · the ordinal badge is NOT PAINTED when the source declares PARTIAL. The node keeps its "logged"
    ring — that it ran is true — and stops claiming when. A number that asserts a position the
    source never decided is worse than no number.
  · step-through says "logged 3 / 5" instead of "step 3 / 5". "Step" implies a sequence.
  · the Topology status carries a STANDING warning ("⚠ ARRIVAL ORDER, NOT DISPATCH ORDER"), composed
    as a persistent part exactly as M35.6's pairing note is, so it survives every other status write.
  · the `topology` echo carries `orderMeaningful` + `orderCaveat`. An agent reads the ECHO, not the
    canvas — a suppressed badge is invisible to it, so the qualification has to travel in the data.

VERIFIED AGAINST A REAL PARTIAL SOURCE, which needed building: no such source exists in-tree, so a
throwaway reader PLUGIN (declaring Ordering.PARTIAL and a DECLARED SourceGraph) was compiled against
the shipped jar and installed in ~/.fluxtion-analyser/plugins/. That also exercised M31's
ServiceLoader path end to end for the first time since it shipped.
    context.dispatchOrder      "PARTIAL — this source could not supply an order within a cycle…"
    topology.orderMeaningful   false, with the caveat
    coverage                   4 declared / 4 covered — still works, because the source graph is
                               DECLARED; the guard is on INFERRED, not on foreign
    screenshot                 the four nodes carry "logged" rings and NO ordinal badges. Compare
                               the M34.0 spike shot, where concurrent nodes wore badges 2 and 3.

D1 · A DEFECT THIS SLICE EXPOSED, and it was mine
--------------------------------------------------------------------------------
`context.graphPairing` reported "graph": null while a graph WAS loaded. Every caller asked
`loadedGraphFile() != null` to mean "is there a graph", and a source-supplied graph deliberately has
no file. That is the mirror of the defect M35 spent itself on: not claiming a graph it lacks, but
DISOWNING one it has.

Fixed with `hasGraph()` and `graphLabel()` — ask whether a graph exists, not whether a FILE does —
and migrating all nine call sites. Migrating them uncovered a live NPE on the way:
judgeOpenedGraph() passed the guard and then dereferenced loadedGraphFile(), which is null for
exactly the graphs M34.1 had just made possible. It would have thrown on the first source-supplied
graph anyone opened. Found by changing the question, not by a test.

6. M34.2 COMPLETE — the shading half, and what it turned out NOT to include
================================================================================
On a graph INFERRED from its own run, every node logged by construction, so "did not run" and "not
on this path" can never appear. Their absence then reads as "nothing was missed" — coverage's 100%
wearing a different hat, on a surface where nobody thinks to be suspicious. The Topology status now
says so as a persistent part (the M35.6 mechanism), and the `topology` echo carries the same words
plus `graphSource`, because an agent reads the data and never sees the picture.

REPLAY-DIFF: NOTHING TO DEGRADE. The slice names it, but the feature does not exist — the spec
itself observes that Temporal's native replay fits it better than Fluxtion's does. Recorded rather
than invented: M34.2 is complete against what is built, and the tracker says to revisit when
replay-diff lands. Writing a degradation path for an absent feature would be a guess dressed as work.

VERIFIED, both directions, against real sources:
    INFERRED   graphSource READER_INFERRED · executionCaveat present · coverage REFUSED (HTTP 400)
    DECLARED   graphSource READER_DECLARED · no caveat               · coverage answers (ratio 1.0)
The contrast is the test: a caveat that fires on everything is not a caveat.

THE PROBES ARE NOW IN THE TREE — tools/spikes/m34-probe/. They had to be built because NO SOURCE IN
THIS REPO CAN EXERCISE M34.2: the native reader is TOTAL-ordered and has no graph, so every
degradation path had nothing to degrade against and would have shipped read-verified only. Two
readers, one PARTIAL+DECLARED and one PARTIAL+INFERRED, with build-and-install steps in the README
and a note to delete the jar afterwards — a probe claiming capabilities nothing else claims is not
something to leave in a real profile.

  A DEBUGGING NOTE worth keeping, because it cost a cycle: the first inferred run reported
  graphSource "None" and I began hunting the precedence logic. The jar was stale — `mvn test`
  compiles but does not repackage, so the running app predated the change and "None" was Python's
  missing key, not the enum. Rebuild before driving.

All five findings verified by re-derivation and all five are right. F1 is the one I should have
found: I designed GraphSource to answer "who wins the slot WHILE a log is open" and never asked what
happens to a reader's graph when the log goes. It is the log's DERIVED state — M35's own rule,
applied to a thing I had just created, and I missed it in the milestone that exists to enforce it.
The reviewer found it the way M35's findings were found: drive it, close it, look.

F2 is worse in a specific way and worth naming. I wrote `graphNote()` with a javadoc saying "so the
source does not look like one that simply had no graph" — and nothing ever called it. Loud
degradation promised in the comment, silent in the code, in the same commit. That is the defect
class this branch is about, committed while describing the intent.

F3, F4, F5 all correct. F4's self-correction in the review ("I first wrote NPE on first paint —
WRONG, checked and corrected") is the right instinct: the finding stands on the adjacency maps
without the crash claim.
