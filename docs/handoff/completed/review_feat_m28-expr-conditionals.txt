R3 — STRAY DURATION REJECTION IS AIRTIGHT. I tried fifteen ways to smuggle a Dur into a
non-window position: "5m"+1, abs("5m"), -"5m", min(a.x,"5m"), both if() branches, the condition
side of if(), and("5m",1), not("5m"), mean("5m",3) (first-arg), nested max(abs("5m"),1),
rate("5m","1m") (first-arg), and a trailing + "1s" after a valid window. All fifteen rejected, each
message teaching the fix. lag(x,"5m") and rate(x,3) get bespoke explanations of why counts and
durations are not interchangeable. I could not find a hole.

R2 — WINDOW ARITHMETIC IS SOUND. The running sums (count and time forms) never recompute, so FP
error accumulates monotonically across a scan — but only finite values are ever added or subtracted
(so NaN/Inf cannot poison the accumulator, which would be unrecoverable), and the drift is ~1e-10
relative over 1e6 records at realistic magnitudes. Not a defect. The monotonic deques are correct
under both index pruning and time pruning; a dominated sample is strictly older than its dominator,
so it can never outlive it into being the answer (D6's reasoning checks out).

Also verified: the count-window ring's (count % n) indexing returns the value from exactly n
accepted samples ago and needs n+1 samples to speak (D2 correct); delta keeps prev across a gap so
the next step measures across it (D3); time pruning for aggregates runs OUTSIDE the finite guard so
old samples age out on non-contributing records, while count pruning correctly runs inside it.

2. F1 — rate() WAS SYSTEMATICALLY BIASED LOW  [FOUND, FIXED ON THIS BRANCH]
================================================================================
Not an edge case and not confined to startup. Probe: x rising exactly 1.0/s, sampled every 10s, so
the true rate is 60 per minute at every point.

    t=10s  rate=10.0     6x low  (window filling)
    t=20s  rate=20.0
    t=50s  rate=50.0
    t=60s  rate=50.0     steady state, 17% low
    t=90s  rate=50.0     never converges on 60

Two compounding causes:
  (a) No normalisation at all. D4 correctly rejected the spec's "(last − first)/window" as
      double-normalising, but overcorrected to raw (newest − oldest). Combined with time windows
      having no fill requirement, rate then reports the change over however much data happens to
      exist.
  (b) The window is open at the old end — pruning drops the sample sitting exactly at now − T — so
      the retained span is short by one sampling interval even once the window is nominally full.

The reported value is therefore low by (T − Δ)/T where Δ is the sampling interval, for ever. With
30-second sampling on a "1m" window that is HALF the true rate, silently. This matters more than a
normal off-by-a-bit because D-W3's steer deliberately sends rate-sensitive users to the time-windowed
forms, and rate was the one function that is wrong there.

FIX (Evaluator, rate node): normalise by the span actually covered, then scale to T.

    double span = samples.peekLast()[0] - samples.peekFirst()[0];
    if (span <= 0) return Double.NaN;   // no elapsed time — unknown, not infinite
    return (samples.peekLast()[1] - samples.peekFirst()[1]) * windowMillis / span;

Reads 60.0 at t=10s and at t=60s — correct while filling AND when full. Three tests pin it:
rateIsChangePerWindow_normalisedByTheSpanActuallyCovered (the existing test, whose old expectation
of 30.0 was the bug made visible — its data rises 1.0/s, so 60.0 was always the right answer),
rateDoesNotUnderstateOnAPartlyCoveredWindow (constant 1.0/s must read 60 at every point, filling or
full), and rateNeedsElapsedTime (samples sharing a timestamp → NaN).

Spec, graphs.md and CHANGELOG updated in the same commit; the spec records why BOTH earlier formulas
were wrong so this is not re-litigated later.

================================================================================
3. F2 — COUNT-WINDOW AGGREGATES HAVE NO STALENESS BOUND  [owner decision, not fixed]
================================================================================
This sharpens R1/D1 rather than contradicting it. Probe: mean(if(x > 100, x), 3) where the condition
holds only for records 0–3.

    rec=3  x=104.0  mean=103.00
    rec=4  x=  1.0  mean=103.00     condition no longer holds
    rec=9  x=  1.0  mean=103.00     ... and for every record to the end of the log

The identical TIME-windowed form goes NaN once its window empties (verified side by side). So the two
families disagree about staleness, and the count family has no bound at all.

D1's justification — an aggregate describes the window, which exists independently of the current
record — is the reading that makes the composition argument work, and I still endorse it. But the
docs say the mean "holds between breaches", and what it actually does is hold INDEFINITELY: a point
plotted hours after the last breach is indistinguishable from live data. These charts become PDF
evidence, so that is the same honesty concern that decided D-W2 and M29's D-F2.

Options, in the order I would consider them:
  1. Say it plainly in the docs — "holds indefinitely after the last contributing sample" — and rely
     on D-W3's existing steer toward time windows. Cheapest, and probably sufficient.
  2. Give count aggregates a staleness rule (e.g. go NaN after N non-contributing records).
     Principled, but invents a second policy the spec deliberately does not have.
  3. Leave as is. Defensible, but the docs currently understate it.
I did not change this — it is a semantics decision, and the spec is the owner's.
