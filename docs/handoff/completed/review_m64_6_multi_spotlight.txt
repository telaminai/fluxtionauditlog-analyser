F1 — P2, required: retain a numbering high-water mark until replacement or empty.
  src/main/java/telamin/fluxtion/audit/analyser/analyser/ui/SpotlightOverlay.java:87
  add derives the next number from the CURRENT maximum. Clearing the highest-numbered spotlight lets
  that number be reused for a different target while the rest of the set remains lit. Reproduced both
  directly on SpotlightOverlay and through the built jar:
    spotlight {targets:["status","detail"]}       -> status=1, detail=2
    spotlight {clear:true,target:"detail"}         -> status=1
    spotlight {add:true,target:"records"}          -> records=2 (must be 3)
  The existing unit test removes the MIDDLE member, which cannot expose this error. The chat's earlier
  "2" now refers to a different thing, exactly the failure D-SP6 prohibits. Keep a next-number counter;
  reset only on replace/empty and preserve it when remove/remeasure retires the highest member. Add both
  removal and remeasure regression cases. Fix the code, not the spec's stable-number rule; the tracker
  assertion that numbers are never reused is currently false.

  names and checks the add-union bound. resolveAll's parse-before-reveal guarantee therefore holds only

  Reproduced on the jar with demo-quote-series.yaml:

  The second call refuses the unknown target, but context.filter changes from that text predicate to {}
  and context.selection changes from [] to record 15 (byteOffset 6347). A rejected request erased the
  investigation scope. Separately, with six valid targets already lit, add records:row:10 refuses the
  seventh target but still clears the text filter and selects record 10 (byteOffset 4235).

  Fix: share full validation across the action/frame boundary, including all names and union capacity,
  before any goto/reveal; then perform the permitted reveal phase and its remeasurement. Assert that
  filter AND selection AND standing spotlights remain unchanged for these syntactically/capacity-invalid
  calls. D-SP6 deliberately permits visibility side effects for a valid request that later cannot be
  displayed; it explicitly does not permit a misspelled member to touch the surface. Preserve that
  distinction in code and docs. The current all-or-nothing tracker claim overstates the implementation.
