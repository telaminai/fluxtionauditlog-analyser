FOUND LIVE, FIXED BEFORE COMMIT (both would have been invisible to the unit tests)
  1 `open {log}` is ASYNCHRONOUS. The first live run reported 1/3 — step 2 (`filter`) ran before the log had
    landed and failed "no log is loaded". The runner now waits for an open step's load to settle (success or
    failure — both pass through setBusy(false)), up to 120s, before the next step; a failed load is a failed
    step with the status bar's reason.
  2 The wait then TIMED OUT while the log sat loaded: render("open") hops onto the EDT, so the runner was
    spinning on the EDT and blocking the completion it waited for. `open {analysis}` is now routed BEFORE the
    EDT hop (doOpenAnalysis); each step hops on its own through render(). 3/3 in 0.2s after the fix.
  Both are the kind of defect a sequence surfaces and a single verb never does — worth remembering for M38.5+.

FOUND LIVE — a hazard for shared profiles (now fixed above; the note stands as the record)
  An OLDER analyser that opens a profile written by a NEWER one drops the keys it does not know on its next
  save: ProjectProfile.write rebuilds the file from the categories it understands. Seen here by accident (a
  failed build left the previous jar in place; it opened the project and re-saved it without destination.*).
  For a team on mixed versions this silently strips M38 facts from a committed profile. Candidate M38.7:
  preserve unknown keys on write (round-trip what you do not understand), or refuse to save over a profile
  carrying a newer share.version. Cheap either way; a decision first.
