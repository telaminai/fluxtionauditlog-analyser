H3 · WINDOW-ID SCREENSHOT CAPTURE
================================================================================
Mechanism chosen: `screencapture -l <CGWindowID> -o`, the id obtained by a JXA one-liner over
CGWindowListCopyWindowInfo (osascript -l JavaScript — ships with macOS; pyobjc does not). Why not the
app printing its own id: the JVM has no public API for a CGWindowID, so that route is an internal-class
hack. Why not osascript/System Events: it hands out AX window ids, not CG ones.
THE FIRST CUT FAILED, and the log said so for every shot ("no window id found — falling back to a
REGION capture"): it matched owner name /java/ and a title prefix. A `java -jar` window's owner name is
the MAIN CLASS ("Main"), and kCGWindowName is only populated for callers holding Screen Recording
permission. Neither is stable. Second cut matches on kCGWindowOwnerPID == the pid the app publishes in
its own rest-endpoint file, plus layer 0 (a normal window, not a popup), largest wins. That is the one
identity both processes agree on, and it needs nothing the capture did not already need.
14 of 15 shots are now window captures; the log prints the mode per shot as evidence. The MENU shot
stays a region capture and says why in the code: a Swing popup is its own window and `-l` takes one
id — so raise_window() remains its mitigation, and the overlap risk is still live for that ONE image.
All 15 regenerated images were READ (rule 1): demo names only (com.acme.demo, DEMO-A), no foreign
window in any frame, title bars present. The "≤3 hops" checkbox (H4) is visible in the Topology
toolbar of every topology shot — a real UI change, not a capture artefact.
Note: capture-docs.py writes to the REAL ~/.fluxtion-analyser/config (theme, hidden columns, REST) as
it always has; this run left it as the script leaves it.

H4 · ROUTES SCOPE AT A TERMINAL NODE
================================================================================
Mechanism: TopologyFocus.routes(topology, seeds, allowBound) → RouteScope {ids, bounded, hops,
unboundedSize}. The rule is stated as constants: bound to ROUTE_HOP_BOUND=3 hops each way when the
unbounded answer exceeds DEGENERATE_SHARE=0.5 of a graph of at least BOUND_MIN_GRAPH=40 nodes.
FocusStack.routesInWorld applies the same rule measured against the WORLD, edges walked in-world only.
UI: a "≤3 hops" checkbox beside Focus (on by default) — a checkbox rather than a fifth scope so the
verb surface (scope: node|neighbours|routes|all) stays as published; the brief froze that surface.
The status line, when bounded: "+ all routes within 3 hops — all routes would be N of M nodes; untick
'≤3 hops' for all". The `topology` echo carries scopeBounded + scopeNote — an agent reads data.
Tests (TopologyFocusRoutesBoundTest, 5): bounded on a 65-node fan-in from the sink (sink + three
layers = 25, not 65; layer 4 excluded); untick → 65; mid-graph node bounded exactly when the rule
says; a 13-node graph never bounded; the world-confined version agrees at full graph and does not
bound inside a 17-node context.
LIVE: on a random 309-node graph, routes from the sink were 111 of 309 (36%) → NOT bounded —
correct, and a reminder that the M24 graph was denser than a random one. On a dense 51-node fan-in
(every node feeds the next layer): scopeBounded=3, note "all routes would cover 51 of 51 nodes";
focusing the bounded scope shows 31 of 51 (sink + 3 layers of 10). Screenshot read: the checkbox
sits at the right of the toolbar, the status carries the note.
