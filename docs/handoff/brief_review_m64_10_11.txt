WHAT TO ATTACK
  1. The grammar. graph:<name> where the name contains "note"/"series" as a WORD (a chart named "Series A"):
     parse("graph:Series A:series:x") — is the cut at the first ":series:" right, and does "graph:Series A" (no part)
     light the plot? What does parse("graph:note:2:series:x") do? Is refusing ':' in a name the right call, or should
     a name be quoted?
  2. alsoOn() for GRAPH_NOTE uses ChartPanel.noteBounds(n) on charts that are NOT showing. Does noteBounds return
     non-null for a chart tab that is not selected (its component has no size)? If it returns null, the refusal will
     never name another chart for a note — a silent gap. Write the test that draws two charts with notes and asks
     for the note on the wrong one.
  3. The lightweight-popup request. The frame sets the two FlatLaf client properties on the JPopupMenu each time it
     opens a menu for a spotlight and never removes them: the menu is shadowless from then on, even when opened by
     hand. Acceptable? If not, restore them when the menu closes (the PopupMenuListener is already there).
     Also: under which LAF do the display tests run? NamedGraphAndMenuSpotlightFrameTest installs FlatLightLaf
     because the bare rig gets Aqua on macOS, whose ScreenPopupFactory is heavyweight-only. Confirm CI (xvfb,
     Metal by default) still exercises the FlatLaf path, not Metal's.
  4. The press-through. spotlightPressed() matches the press against the lit target's bounds AS MEASURED (overlay
     coordinates) and calls JMenuItem.doClick via invokeLater. Between the press and the doClick the menu has already
     closed (the grabber saw the press). Does doClick on a closed menu's item still fire its action for every kind of
     item (JMenuItem, JCheckBoxMenuItem "Follow (tail)", JRadioButtonMenuItem)? The test uses "Close log" only.
  5. Escape with a lit menu: designed (overlay binding first, then the popup's key handler), NOT tested — posted keys
     need window focus, which xvfb gives. Add the case to PersonAtTheScreenFrameTest's pattern if you can: light
     menu:File:Close log, post Escape, expect the menu closed AND nothing lit after ONE press.
  6. A menu opened by the spotlight while ANOTHER menu was open by hand; a menu target in a `targets` set together
     with a tab target (the reveal of the tab does not close the menu — or does it?); `add: true` with a menu target
     when a menu is already lit.
  7. The screenshot popup painting: it paints every showing POPUP-layer component, translated. A tooltip is also a
     lightweight popup — is a tooltip now painted into every screenshot taken while the mouse rests on a control?
  8. M64.12b: the user guide's first sentence changed from a spread threshold to liveOrders above 1. Is that row's
     promise ("it finds the record, selects it, and lights that row") true of the demo series log — record 15?
