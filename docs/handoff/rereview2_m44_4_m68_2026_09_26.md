## Required correction

### F1 — High: converting `key` to an unquoted expression changes the requested values

**RUN + READ.** `src/main/java/telamin/fluxtion/audit/analyser/analyser/ui/ReportSeriesPicture.java:69`
passes the literal key directly to `SeriesScan.parseCall` at line 73. `GraphKey.fromDisplay` validates its
node/key split, but that does not make the string a literal reference in the expression grammar.

Concrete input:

```yaml
eventLogRecord:
  event: Tick
  logTime: 1000
  nodeLogs:
    - rootNode: {v: 100, v+1: 7}
---
```

Stored report section:

```json
{"kind":"series","call":{"key":"rootNode.v+1"}}
```

**Expected: the value 7 of the literal key `v+1`. Actual: 101, calculated as `v + 1`.** The report
action succeeds without a warning, labels the result `rootNode.v+1`, and draws a dot at 101. I inspected
the actual exported PDF. The literal extraction and the verb's backtick-quoted reference both return 7.

This is introduced by this delta, not an old expression limitation. I compiled the unchanged adapter
from `93046a48` against the subject jar and ran the same probe: its plot is centred on **7**. The new
adapter's plot is centred on **101**. Both have one point; the point-count agreement checks cannot detect it.

**Required:** preserve `key` as a literal `GraphKey` while sharing the call's filter and resolution
interpretation. A safe literal-reference conversion is another option where the grammar can represent
the key; never silently treat it as a formula. Add a value-sensitive regression through the production
adapter, plus a mutation reverting to this unquoted conversion that fails the named value assertion.
Check the exported artifact as well. Do not change `expr` semantics to fix `key`.

Evidence: [probe packet](evidence/m44-4-single-state-2026-09-24/rereview2-probe/), particularly
`LiteralKeyProbe.java`, `key-old.png`, `key-new.png`, `LiteralKeyPdfProbe.py`, and
`literal-pdf/literal-key.pdf`. The old adapter was compiled in scratch; no subject source was changed.
