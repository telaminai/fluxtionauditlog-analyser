**What was read.** [PROTOCOL.md](PROTOCOL.md), both earlier review-prediction files and
[predictions-template.md](predictions-template.md); `tools/g14_runner.py` and its tests;
[coldstart/METHOD.md](../coldstart/METHOD.md); the beta proposal ([../README.md](../README.md)); the authoring
ladders of 2026-10-12 and 2026-10-13 (`docs/handoff/evidence/authoring-ladder-2026-10-12/`, `…-release-2026-10-13/`:

the M74 spec r11 and the P2 branch's code (`feature/claude-code-p2` at `71e0c57f`).
**What was not done.** No live `claude` run, no key or token read, no analyser launched. Statements about the P2
code are from reading it.

The successor protocol this review argues for is [../m74-onboarding/PROTOCOL.md](../m74-onboarding/PROTOCOL.md).

## Summary

The instrument is better than most of what gets called LLM evaluation: predictions are sealed by digest before a run,
misses are published, VOID runs are kept and excluded rather than re-labelled, containment is tested against the
kernel in both directions, and the PASS of the ladders is computed by code from an oracle independent of the
subject. Its weaknesses are the ones that grow with repetition: tasks and docs co-evolve across rounds, the answer keys
sit in a public repository that web-capable subjects can read, scoring keeps one hand-judged row and has been
corrected after results, and very little of a run can be re-scored once its base is deleted. **M74 makes the harness
itself out of date**: the analyser now starts Claude Code, so the harness no longer composes the subject's command
line, cannot capture its stream, and must supply a person to press Send, Yes and Allow. The top five findings:

1. **The subject is now the analyser's child.** Every control G14 applies to the `claude` command line
   (`--tools ''`, `--allowedTools`, `dontAsk`, `--no-session-persistence`, `--setting-sources`) is now the
   analyser's posture — the thing under test. Containment has to wrap the analyser's JVM, and the virgin condition has
   to be made by the environment (an empty `CLAUDE_CONFIG_DIR` and the trial token), not by flags.
2. **A person is part of the product's safety model, so "no operator" is no longer available.** METHOD.md calls
   *no operator, `claude -p`, no interaction* "strictly stronger". Under M74 the person alone presses Start, Send, Yes
   and Allow (OD-74.1, OD-74.13, OD-74.17). A virgin run needs a **scripted** operator whose every press is matched
   against the session record's person-act facts, or the run cannot show who approved what.
3. **Session persistence turns on, and with it a cross-run memory channel.** G14 runs with `--no-session-persistence`;
   the analyser runs sessions by id so they can resume. The CLI's history and auto-memory then live under the config
   directory, keyed by working directory. Any shared config — including the owner's real one — lets a later run read an
   earlier run's conclusions.
4. **The answer keys are public, and some subjects have web tools.** Oracles, task texts and scorers are committed to
   this public repository; G14 and the ladders grant `WebFetch`. Nothing scans a transcript for a fetch of them.
5. **The scorecard can be computed from the analyser's own records — mostly.** The P2 session processor already
   records sends, turns, outcomes, refusals, proposals, example downloads and cost as facts and node-log keys. Four
   things it does not record (the verb of a hosted call, the tool of a posture denial, the person's per-item No, and
   P3's approvals) are listed as requirements, and one thing it records that it should not is worth an owner decision:
   **Claude's words and real paths inside several P2 facts** (SCORECARD R6).

## 1. What is strong

- **Predictions before results, and misses kept.** Predictions are digested and dated before launch; the release
  ladder pushed its seal (`a445666d`) before the first run. The ladders publish every miss, including the ones that
  flatter nobody (Haiku underestimated on every rung; "some run reaches the cap", wrong). The two review-prediction
  files here record their own misses in the same file, below the predictions.
- **A PASS that code computes.** The ladders' PASS is ORACLE + VALID + CHART + S6′ from `score_ladder.py`, with an
  oracle that rebuilds the subject's final source offline and drives it, never reading the subject's output. Each oracle
  has wrong-result controls (the unsolved fixture fails at step 1; no eviction fails at output 4).
- **Containment proven where it matters.** `SandboxEnforcementTest` runs `sandbox-exec` over fixtures and asserts both
  directions, after the text-only version passed against a policy that denied every read. The second review's lesson —
  *a negative-only test passes against a deny-everything policy* — is the most transferable result in this folder.
- **Fail-closed everywhere it was looked at.** The key file is decoded as the JDK decodes it, an unsupported line makes
  the scan *unknown* rather than clean, process-group enumeration distinguishes *could not look* from *empty*, `x`-mode
  opens and `started.json` stop an interrupted run being overwritten, exit codes separate a leak from an unconfirmed
  cleanup, and a prestaged comparison is labelled so it can never read as an acceptance.
- **VOID discipline.** The two Repsy-502 runs are preserved, named, excluded from totals and re-run.
- **Observer time, not model time.** The journal was retired because three of three journals carried fabricated
  timing; `ObserverClock` replaced it with drift under 10 ms.
- **The warm-cache decision is argued from measurement** (setup 90–200 s cold versus 5.4 s warm; a Repsy outage voiding
  two unrelated runs), with provenance, sufficiency and a recorded digest.
- **Ground truth measured on a throwaway instance**, never read from source.

## 2. What is weak

### 2.1 Contamination between runs

- **Processes outlived their runs.** Three Mongoose servers started by subjects were reparented to launchd and held
  port 8181 for the next runs while `meta.json` said the group was reaped (2026-10-12, *measured*). The base sweep
  fixed it after the fact; runs before the fix are not marked.
- **Cold and warm mixed inside one result table.** The first five ladder cells ran cold and the rest warm; the
  disclosure is honest, but the table compares them as one population.
- **A tool nobody listed was available to every run.** The subagent tool allows itself under `dontAsk`
  (M72 L4(iii), read from the 2.1.296 binary), so every G14 and ladder run before `--no-subagent` could delegate. One
  did. It is recorded now; it was an uncontrolled variable for every earlier comparison.
- **For M74, new channels**: the config directory's history and auto-memory (finding 3), the analyser's machine-tier
  trust records and remembered mode in `user.home`, the session lock directory, and — under the real login — writes to
  the owner's `~/.claude/projects/`.

### 2.2 Prompt leakage

- **Tasks are frozen and reused while the docs change.** Rung 2 is the 19 September task, run again on 12 and 13
  October. The loop-handoff rule says to rotate and hold one out; the ladders name no held-out task (rung 6 was new, not
  held out), so a rising pass rate cannot be told apart from documentation that now describes the task.
- **The answer keys are in a public repository** (`r2/R2Oracle.java`, `r3/r3_oracle.py`, the task texts), and the
  subjects held `WebFetch`. There is no evidence any subject fetched them and no check that would show it if one had.
- **The task prompt is the only routing control**, and PROTOCOL's rule (*"must not name a file"*) is enforced by the
  operator's care, not by a test.

### 2.3 Scoring subjectivity

- **One G14 pass condition is a judgement**: *"no claim in the subject's report that the transcript does not
  support."* That is the condition most likely to fail, and the one nobody can re-run.
- **Answers are not scored, even when they are wrong.** `lad-r3-s5-1` failed its oracle and *"its final answer claimed
  success"*. The scorer was right to ignore the answer; but a claim of success over a failing oracle is itself a
  finding (an honesty failure), and the ladder has no column for it.
- **The oracle and the scorer changed after results.** The rung-4 oracle was widened after a failing run had ended and
  after another had started; `project_root` changed after runs had started. Both are disclosed with times and both kept
  the sealed verdict beside the corrected one — the right handling — but they show oracles are being written too
  narrowly before the seal.
- **METHOD's `SCORE.md` is written by hand** against the predictions.

### 2.4 Reproducibility

- **n = 1 per cell** in the release checks and for Sonnet in the ladders; METHOD.md says so itself.
- **Little can be re-scored.** Transcripts are not committed (rightly: they carry paths), and the per-run bases under
  `/private/tmp` are deleted. Only the committed JSON survives, so a scorer bug found later can be fixed only for the
  fields that JSON holds.
- **The instrument is not versioned.** METHOD's `runner.py` lives in a git-ignored folder, *"reconstructible from any
  run folder"*.
- **The CLI version is pinned only when `--claude-bin` is passed**, and model names are recorded as given; an alias
  that moves would not show.

### 2.5 Cost

- **Prompts over 100k tokens are routine** (every scored ladder run sent some; Haiku 5.5 bills those at five times
  the rate), and the runner caps time, not spend.
- **Under the trial OAuth token the cost is notional**: a comparison figure, not a charge. It is labelled so in the
  ladder; G14's documents do not say it.

### 2.6 Cache provenance

- **The rule is applied outside the runner.** G14-W is open; the 2026-10-12 seeding was the orchestrator's, and the
  provenance check is `provenance.py` in an evidence folder, untested and without a wrong-result control. (It is now
  a tested function in `tools/m74_onboarding_runner.py`, which the G14 runner can import.)

### 2.7 Predictions-before-results discipline

- **A seal is a digest and a `date -u` line the operator wrote**; it is evidence of time only once pushed. The
  release ladder pushed; the template does not require it.
- **Predictions do not learn.** The ladder's misses were all in one direction and the next prediction set repeated
  them (rung 5 again expected Haiku at ≤ 1/3 and got 2/3). The template has no field for *what the last misses changed*.
- **Predictions are thresholds, not mechanisms.** *"Haiku passes at most 1 of 3"* can be scored; *"Haiku fails
  because it never finds the service binding"* would say why, and the template asks for it only in prose.

## 3. What is out of date given M74

| G14 / METHOD assumes | Under M74 | What the M74 protocol does |
|---|---|---|
| The harness builds the `claude` line | The analyser builds it, from the posture (§4.3) | Pins the jar and the posture; checks the posture from the record (`LocalAgentInitObserved`) |
| `sandbox-exec` wraps `claude` | `claude` is the analyser's child | Wraps the analyser JVM (probe PV-1) |
| `--no-session-persistence`, `--setting-sources project,local` | Sessions persist by id; the default posture uses `--restricted`; the full posture loads the person's whole configuration | An empty `CLAUDE_CONFIG_DIR` per run, asserted; the trial token for login (L1) |
| Real login avoided by an isolated `HOME` + trial token | The spec's capture method uses the real login + `--strict-mcp-config` | L1 by default; L2 only for the default posture, never for the full posture, which would load the owner's skills |
| One-shot `claude -p`, no operator | Multi-turn; Start, Send, Yes and Allow are the person's | A scripted operator in the analyser's JVM, pressing its own controls; a boundary check over person-act facts |
| Transcript = `raw.jsonl` from `claude`'s stdout | The analyser consumes the stream | The session record (exported by the harness), the transcript store, the CLI's own session file in the isolated config |
| The key-leak scan reads `raw.jsonl`, `events.jsonl`, `stderr.log` | Those files do not exist | Scan the CLI session file, the transcript store and the session record (T4) |
| Acquisition is the subject's (download the ZIP itself) | The example entry downloads, the person confirms | Acquisition is a person act through the analyser's code; identity is the commit plus the unpacked tree digest (GitHub archive bytes may change) |
| Pass 3: a chart on the canvas with no identity mark | *Point before you explain* is the product's rule | Correctness is a pointer (selection, flag, spotlight) at the oracle record, read from `context` |
| The external MCP client **is** the instrument | It is now the surface a hosted bridge can break | T5: a deterministic contract gate plus the old instrument, candidate against control |
| Subagents must be denied by a flag | The default posture's `--tools "Read,Grep,Glob"` has no Agent tool | Only T4 (full posture) needs to record delegation |
| The battery is retired | 10–20 cycles of cold runs are a battery in all but name | Answer the retirement's reasons: no self-reported timing, a machine scorecard, a sealed operator |

## 4. Recommendations

1. **Adopt the M74 protocol's split**: T1–T3 on the default posture with no build and no Maven; T4 only after P3; T5 as
   a deterministic gate with an indicative model arm, so the external loop paying users rely on is guarded by checks
   that do not depend on a model's mood.
2. **Hold the oracle out of the public repository until a cycle closes**, commit its digest, and void any run whose
   transcript fetches the protocol or evidence pages (`oracleLeakHits`).
3. **Score answers for contradiction**, mechanically: a sealed forbid list per oracle, so a claim of success over a
   failing oracle, or *"it did not run"* over a silent node, fails the run.
4. **Require the seal to be pushed** before the first launch, and add *what the last misses changed* to the
   predictions template.
5. **Land G14-W** by importing `m2_provenance` and `seed_m2` from the M74 runner, with their tests.
6. **Ask the owner about R6**: P2 facts carry Claude's proposal words and real paths into the session record. Either
   §4.1's rule is relaxed and stated, or those fields become references.
7. **Keep raw evidence for re-scoring** under `.local-evidence/` with a manifest digest, for the length of a cycle
   series, so a scorer fix can be applied to every run it touches.
