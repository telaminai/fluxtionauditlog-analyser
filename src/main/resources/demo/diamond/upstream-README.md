# fluxtion-diamond

A four-node Fluxtion graph, small enough to read in one sitting, built to be opened in the Fluxtion audit log
analyser. It is the teaching example the analyser's *Fluxtion philosophy* prompt packs refer to.

```
        X (an integer event)
        |
        a          A holds the latest x
       / \
      b   c        B = floor(A / 2)      C = 3 * A
       \ /
        d          D = 100 * B + C, and counts how often it runs
```

Each node is an ordinary Java class with a little state. Each one names only its parents, in its constructor.
Nothing in this project says what order the nodes run in: the Fluxtion compiler works that out and writes the
dispatcher. A, B and C return `true` only when their value changed, and every node writes an audit entry each
time it runs, so the log shows what ran and what each node saw.

## Build and run

You need Java 21. Maven comes through the wrapper.

```
./mvnw package                                         # compiles the committed generated source and runs the test
java -jar target/fluxtion-diamond.jar                  # writes out/diamond-audit.yaml
java -jar target/fluxtion-diamond.jar out/spring.yaml spring   # the same, through the Spring-generated processor
```

The default build needs no Fluxtion API key, because the generated processor is committed. To regenerate it
from the builder and the Spring XML, run `./regen.sh`. That calls the hosted Fluxtion compiler through the
Fluxtion Maven plugin, which reads your key from `~/.fluxtion/fluxtion.apiKeyFile` itself.

Versions used: Fluxtion runtime and builder API 1.1.2, Fluxtion BOM and builder 1.0.79 (the generated header
records `api version 1.1.2`, `target generator version 1.0.79`), fluxtion-maven-plugin 1.3.0, Spring 6.2.3
(Spring variant only), JUnit 5.11.4.

## Open it in the analyser

Open `sample/diamond-audit.yaml` (**Audit log ▸ Open log…**) and then
`src/main/resources/com/acme/diamond/generated/DiamondProcessor.graphml` (**Sources ▸ Open GraphML…**). Add
`src/main/java` as a source root if you want the analyser to show the node classes and the generated
processor next to the records.

Checked with analyser 1.34.0: it reads all 6 records, recognises the stream-end marker (`streamEnd: complete`,
6 declared, 6 read), pairs the graph ("the graph declares all 4 node(s) this log writes"), finds audit logging
enabled, reports dispatch order as total, and scores coverage 4 of 4 (`a`, `b`, `c`, `d`).

## What to look at

### 1. The generated dispatcher

Open `DiamondProcessor.java` and find `handleEvent(X typedEvent)`. This is the whole of what happens when an
`X` arrives:

```java
isDirty_a = a.onX(typedEvent);
if (guardCheck_b()) { isDirty_b = b.recalculate(); }
if (guardCheck_c()) { isDirty_c = c.recalculate(); }
if (guardCheck_d()) { d.recalculate(); }
afterEvent();
```

and the guards, further down:

```java
private boolean guardCheck_b() { return isDirty_a; }
private boolean guardCheck_c() { return isDirty_a; }
private boolean guardCheck_d() { return isDirty_b | isDirty_c; }
```

(The audit calls between these lines are left out here.) Things worth noticing, all read from that file:

- The order is fixed in the code: A, then B, then C, then D. Nothing decides it at run time.
- D is called from one place, once, after both B and C. Its guard is "B changed **or** C changed".
- The `true` or `false` a node returns is stored in a dirty flag, and the children's guards read that flag.
  D's return value is not stored anywhere, because nothing depends on D.
- `afterEvent()` clears the dirty flags, so each event starts clean.
- There is no special case for the first event. The only conditions are the dirty flags.
- None of the node classes refers to the processor, and the processor is not written by hand.

### 2. The log, event by event

These are the observed results of the committed run (`sample/diamond-audit.yaml`, `sample/run-console.txt`),
and the test asserts the same numbers against both generated processors.

| x | A | B | C | D ran | D |
|---|---|---|---|---|---|
| 2 (first event) | 0 → 2, changed | 0 → 1, changed | 0 → 6, changed | **once** | 106, invocations 1 |
| 3 | 2 → 3, changed | stays 1, **not changed** | 6 → 9, changed | **once** | 109, invocations 2 |
| 3 again | stays 3, **not changed** | did not run | did not run | **did not run** | still 109 |
| 4 | 3 → 4, changed | 1 → 2, changed | 9 → 12, changed | **once** | 212, invocations 3 |

What that shows:

- **D ran at most once per event**, including x = 2 and x = 4, where both B and C changed. Its `invocations`
  counter reads 1, 2, 3 across the run, and the console shows "d ran 1 time(s)" for those events.
- **When only one side changed** (x = 3 after 2: B stayed at 1, C went to 9), D still ran, once. It read B's
  current value, 1, which B had kept from the previous event. The record shows `b: 1, c: 9, value: 109`.
  In this graph the other mixed case, B changing while C does not, cannot happen: C = 3x changes whenever x
  does.
- **On the repeated 3**, A ran, logged `changed: false`, and returned `false`. Nothing else ran: the record
  for that event has one entry, `a`, and D's counter did not move.
- **The first event** behaved like any other change. Every node starts at Java's default of 0, so x = 2
  was a change for A, B and C alike, and D ran once. Before it, the log holds two framework records with no
  node entries: attaching the audit sink (`EventLogControlEvent`) and `init()` (`LifecycleEvent: Init`).
  Not measured here: a first event of x = 0 would match A's starting value, and by the code above nothing
  downstream would run.

### 3. A record, field by field

```yaml
eventLogRecord:
    eventTime: 1792247960770
    logTime: 1792247960770
    groupingId: null
    event: X
    eventToString: X[value=3]
    thread: main
    nodeLogs:
        - a: { thread: main, method: onX, annotation: OnEventHandler, x: 3, value: 3, changed: true}
        - b: { thread: main, method: recalculate, annotation: OnTrigger, a: 3, value: 1, changed: false}
        - c: { thread: main, method: recalculate, annotation: OnTrigger, a: 3, value: 9, changed: true}
        - d: { thread: main, method: recalculate, annotation: OnTrigger, b: 1, c: 9, value: 109, invocations: 2}
    endTime: 1792247960771
```

- `a`, `b`, `c`, `d` are the names given in `DiamondBuilder`; they are also the field names in the generated
  processor.
- The keys after `annotation` (`x`, `value`, `changed`, and so on) are the ones each node logged itself with
  `auditLog.info(...)`.
- `thread`, `method` and `annotation` inside each entry, and every field outside `nodeLogs`, were added by
  Fluxtion, not by the node code. The generated processor has `eventLogger.trace = true` and
  `traceLevel = INFO`, so every invocation is recorded with its method, and a record is written for every
  event, even one that logged nothing.
- The entries are in the order the nodes were called, the same order as `handleEvent` above.

### 4. Run it twice

Run `Main` twice and compare the files. The node entries are identical. The times (`eventTime`, `logTime`,
`endTime`) are the wall clock, so they differ from run to run. `sample/diamond-spring-audit.yaml` is a second
run through the Spring-generated processor, and it matches `sample/diamond-audit.yaml` everywhere except the
times.

### 5. Builder and Spring XML

`DiamondBuilder` and `src/main/spring/diamond.xml` describe the same graph in two ways. When regenerated for
this commit, the two generated processors were identical apart from the class name, the package and the header
comment, and the two GraphML files were identical apart from the class name.

## How the audit log is produced

`Main` follows the golden path's order: it attaches the sink, then calls `init()`, then sends events.

```java
DataFlow flow = (DataFlow) Class.forName("com.acme.diamond.generated.DiamondProcessor")
        .getDeclaredConstructor().newInstance();
flow.setAuditLogProcessor(audit);   // writes "---" then the record
flow.init();
flow.onEvent(new X(2));
```

The audit level comes from the builder (`cfg.addEventAudit(LogLevel.INFO)`). At the end, `YamlAuditFile`
writes the format's optional stream-end marker (`streamEnd: normal`, `streamEndRecords: 6`) followed by a
closing `---`, so the analyser can tell the file is complete.

## The same diamond in other domains

`domains/` holds four more variants of this graph: the same shape, the same rule (a node tells its children only
when its value changed), and the same skip when an input repeats. Each has its own classes and builder under
`src/main/java/com/acme/diamond/domain/<domain>/`, a processor generated by the Fluxtion compiler (`./regen.sh`
generates them with the rest), and a log from a real run. In every one the third input repeats the second, and
the record for it (record 4, counting from 0) has one node entry, the top node with `changed: false`.

| Domain | Input | Top | Middle | Bottom: what "did not run" means |
|---|---|---|---|---|
| [mathematics](domains/mathematics/README.md) | `Operand` n | `dividend` | `quotient`, `remainder` | `recombination` (3q + r): the identity was not checked |
| [accounting](domains/accounting/README.md) | `InvoiceLine` net | `line` | `tax`, `discount` | `total`: the invoice total was not recalculated |
| [logistics](domains/logistics/README.md) | `Order` items | `order` | `pick`, `pack` | `dispatch`: no dispatch slot was booked |
| [trading](domains/trading/README.md) | `Trade` price | `trade` | `position`, `pnl` | `risk`: the margin was not recalculated |

```
java -cp target/fluxtion-diamond.jar com.acme.diamond.host.DomainMain trading   # writes out/trading-audit.yaml
```
