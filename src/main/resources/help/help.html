Fluxtion Audit Log Analyser — Help

This tool reads Fluxtion event-audit logs: machine-readable records emitted by a Mongoose/Fluxtion EventProcessor. It lets you browse, filter, summarise, graph, view the source behind a node, and ask an LLM to explain records.

Full documentation online: telaminai.github.io/fluxtionauditlog-analyser.

The toolbar across the top gives one-click access to the common actions: Open, Open S3, Flag, Flagged-only, Explain (send the selection to the LLM), and Export CSV. The event-type checklist is the left rail; the right-hand tabs are the outputs (Summary / Source / Graph / Analyser assistant).

What a Fluxtion audit log is

A Fluxtion EventProcessor is a compiled graph of nodes. When an event (or a timer, or an exported service call) enters the processor it propagates through the graph, and each node that runs appends its state to that cycle's audit record. One record = one propagation cycle. Records are separated by a --- line and aim to be YAML, but node values are raw Java toString()s (e.g. NaN, MutableOrder(clOrdId=1, price=19.9)), so the parser is deliberately lenient.

Reading the table

ColumnMeaning
eventTimeEpoch millis of the triggering event, shown in UTC. Blank when -1 (not event-driven — a scheduled trigger or exported call).

Rows are tinted for anomalies: parse error, breach, NaN (tints adapt to the theme). Jump between them with ⚠ Next / ⚠ Prev on the toolbar, or F3 / Shift+F3 — the search wraps around and respects the current filter/sort. The nodeLogs cell shows a bar sized by node count (relative to the busiest cycle) so heavy fan-out stands out. Use the Columns menu to show/hide columns — your choice is remembered (eventTime, groupingId, eventToString and endTime are hidden by default).

Record detail & nodeLogs

Select a row to see the full record (colourised) in the detail panel. Each nodeLogs entry is instanceId: { key: value, ... }, where instanceId is a node's field name in the EventProcessor graph. The same instanceId may appear more than once in a cycle. A graph key is therefore instanceId.key (e.g. hedgeToOrdersNode.hedgeQuantity).

Navigation: click a node-log line to open that node's class scrolled to the method it ran (the line's first key, e.g. orderVenueConnected); right-click for a menu of the record's nodes. Selecting a record also scrolls the Source tab's EventProcessor to the dispatch method for that record's callback. In the Source view, Ctrl-click (⌘-click on macOS) a receiver.method() to jump to that node's method, a field to open its type, or a type name to open its source. Use Back (Alt+Left, or Cmd/Ctrl+[) to return to the previous source file. The node-log viewer has a Wrap toggle (off → horizontal scroll for long lines). Select two records and use Records → Diff selected two records — or right-click the records table (Diff / Explain / Flag) — for a side-by-side that highlights what changed between the two cycles (changed / only-A / only-B). The diff can be exported as CSV, JSON or PDF.

Filtering & search

  • Event types (left rail): tick the dimensions to include (an OR). The list is split into Event types and Callbacks; use Select all / Select none, or right-click an entry for Only this / Add / Remove.
  • Time range (top slider): drag the two thumbs to bound logTime; drag the middle of the selection to move it, keeping its width; double-click to reset. When the log spans hours but the moment of interest is minutes, shrink the visible window with the Window control (All / week / day / hours / minutes) and pan it across the whole log with the bar beneath the slider — the selection thumbs then work at that finer resolution.
  • Search (top box): case-insensitive; matches eventToString, thread and nodeLogs. It combines with the other filters and stays applied as you change them.

All views (table, summary, graph) share one filter, so they always agree.

Summary

The Summary tab groups the filtered records by event dimension with count, first/last time, span and rate. Click a row to cross-filter the whole app to that dimension.

Graphing

The Graph tab plots a numeric instanceId.key over time. Pick a key, click Add for one or more series. The default style is Stairs (values hold until the next update — the right reading for event-log state); Line and Points are also available. Booleans plot as +1 (true) / -1 (false) so flips are obvious; non-numeric points are skipped, and NaN means "no data point" (omitted, not a gap). Zoom with the mouse wheel (Shift = X-only, Ctrl = Y-only), drag to pan, double-click to fit — or use the + / − / Fit buttons (handy on a trackpad / Magic Mouse). Remove one series by clicking its legend entry, or open several graphs (New graph) for side-by-side comparisons. Name a graph with the Rename… button or by double-clicking its tab — names persist in your profile. Click anywhere on the plot to select the record nearest that time and scroll the table to it. By default a graph follows the shared filter's time window; the 📌 button pins it to a fixed window (the tab shows 📌) so an evidence chart keeps its picture even after you move the filter on — click 📌 again to unpin. Add derived (formula) series in the f(x) field — a formula over node-log keys, e.g. a quoted spread askMakerOrder.price − bidMakerOrder.price (operators + − × ÷, parentheses, abs/min/max; locf carries each key's last value so cross-node formulas plot). The assistant can add these too. The f(x) field autocompletes from the discovered keys and your existing formula labels — and a formula can reference another formula by its label (backtick labels containing spaces: `quoted spread` / 2). The formulas combo next to the field lists the graph's derived series with Edit (loads it back into the fields; Add applies the change) and Remove. Derived series appear in the legend under their label; click a legend entry to remove any series. You can also right-click an attribute in the record-detail viewer and choose Add instanceId.key to graph — to the current graph, any named graph, or a new one. The graph exports to CSV/PNG.

Source navigation

Set your source roots in File → Settings (drag folders in, or Add…). The tool resolves a node's instanceId to its declaring class through the selected EventProcessor. On load it infers the processor by matching the log's instanceIds to each candidate's fields; you can override the FQN in Settings. When a class isn't under any source root, the local Maven repos from Settings (default ~/.m2/repository) are searched for its *-sources.jar — disable with the "don't search" checkbox. The Source tab shows the code read-only with Java colouring.

Topology & step-through

The Topology tab draws the processor's node graph and shows what a cycle did to it. Open a processor's .graphml with File → Open GraphML…, from Open recent GraphML, or by dragging it onto the window. Whatever was open when you quit — and the zoom, pan, orientation, spacing and label size — comes back next time.

A node missing from nodeLogs did not necessarily fail to run. Audit output is opt-in per node, so the tab never colours a node "didn't run". It shows four different claims:

  • green ring + number — logged: it wrote audit output, and the number is its dispatch position. The only thing directly observed.
  • solid outline — ran, logged nothing: it is the only way into something that ran, so dispatch had no other route in. Certain.
  • dashed outline — may have run: connected to something that logged, but the log cannot say whether dispatch reached it. A genuine unknown.
  • faded — not on this path: nothing that logged is connected to it.

Build the processor with cfg.addEventAudit(LogLevel.TRACE) and every node that runs logs a method entry. The analyser detects such a record and stops hedging: absence becomes proof a node did not run, and the legend says so.

Stepping. Select a record and the tab shows that cycle. ↓ steps forward and ↑ back, through this record's nodeLogs rows and on into the next record; ◀◀ ▶▶ skip a whole record and Play runs to the end of the log. The status line reads event 8 / 10 · step 2 / 5. A node that logs twice gets two steps. Only edges whose both ends ran are highlighted — a highlighted arrow is an assertion.

Finding your way round a big graph. Fluxtion's own scaffolding (context, clock, dispatcher, audit and service plumbing) is hidden by default — the Scaffolding box shows it, and the status line always says how many nodes are being kept back. Clicking a node scopes the view to it; clicking again widens: node → + neighbours → + all routes → whole graph. Cmd/Ctrl-click adds to the selection. The scope is dimmed rather than hidden, because a node you cannot see reads as a node that is not there; press F or Focus when you do want the rest gone, and Show all (or a click on empty canvas) to return to the plain graph. The collapsible Index at the bottom-left lists Nodes, Events and Services from the whole graph — so it also reaches what the filters are hiding — and clicking an entry scrolls that node into view.

From a node. Right-click for source, graphing a logged value, filtering the records to that node, or copying its id. Enter on a selected node opens its source beside the graph, in a pane with a draggable divider, so the code and the picture stay on screen together. Hovering shows the node's kind, what the log claims about it, and the first line of its Javadoc when the class is under a source root.

A topology from a different build renders perfectly and misleads silently, so the status line reports how well the graph matches the log. Treat a mismatch as a version problem.

LLM assistant

The LLM tab explains records. In Settings choose a provider (Anthropic / OpenAI), a model and an API key. Select record(s), type a question, and Send. The context sent is: the selected record(s), the EventProcessor FQN, and source snippets for the referenced node classes, plus a system prompt describing the audit format. Reset clears the conversation.

Whole-log access (agentic). The prompt is also seeded with the audit log's file path, its shape (size, record count, UTC time span) and framing, and each selected record's byte offset. A model that can read files then treats the selection as a starting point, not the whole story: it can grep/seek the file to read behind an anchor (what led up to a record) or ahead of it, and to count how often something occurs — so follow-ups like "how often does the validator fire?" or "show me the fill that caused this position" become searches it runs itself. For S3 logs the path points at the fetched local temp file. For a model that can't read files the block is simply inert text.

Two-way actions (beta). The assistant can also drive the app: compute over the index (e.g. "how often does failedValidation fire per hour?" — the app runs the aggregation and feeds the numbers back), and build curation — narrow the filter, open/refine a named graph, jump to a cited record, or flag records (with a note, shown on hover) so its findings become reviewable, reversible artifacts in the table. It runs in a short bounded loop (a few rounds, with a Cancel button); you see each computed result in the transcript. On by default, no network required.

No API key? Use Copy prompt (or Send) to copy the full prompt to the clipboard and paste it into any LLM.

Sharing your setup

  • File → Export settings… writes a shareable .fluxtion-settings file (or Copy to clipboard / Email…). Tick what to include: source roots, Maven repos, event processors, named graphs (formulas and pinned windows included), hidden columns and assistant preferences. The LLM provider/model/base-URL is opt-in and off by default.
  • Never shared: your API key, AWS profile/region, recent files, search history and window/theme — the whitelist is enforced on the way out and the way in, so an imported file can never plant or overwrite a secret.
  • Paths under your home are written ~-relative so they survive a move to another machine; a root that doesn't exist on import simply shows red in Settings.
  • File → Import settings… shows a per-category summary (what's new, what would be replaced) before anything changes; deselect any category you don't want. Lists merge (nothing local is deleted); a graph whose name matches an incoming one is replaced, new names are added.
  • To share into Slack/WhatsApp, Copy to clipboard and paste, or Save file… then drag the file into the chat.

Config & performance

  • Settings persist to ~/.fluxtion-analyser/config (cleartext; local single-user tool).
  • All date/times are shown in UTC.
  • Follow (tail): File → "Follow (tail)" or the toolbar Follow toggle polls the open local file (~1 s) and appends newly-completed records live, auto-scrolling to the newest; flags, filters and selection are preserved. A record still being written isn't shown until its closing --- arrives; a shrunk/rotated file triggers a reload. Available for heap-loaded files (at/below the memory threshold); not for S3.
  • Memory threshold (Settings → Performance & S3): files at/below it load into heap, larger ones are memory-mapped (0 = always mapped). Applies to the next file opened.
  • Drag & drop a log file onto the window to open it; drag folders into Settings to add roots.
  • Open logs straight from S3 via File → Open from S3… (s3://bucket/key) — uses your local aws CLI credentials (profile/region in Settings); no AWS SDK required.
  • Theme menu: Light / Dark / IntelliJ / Darcula (FlatLaf) — text, code and chart colouring adapt automatically. Persisted.
  • Export: File → Export records (CSV / YAML) writes the filtered set (YAML re-loads here); graphs export to CSV and PNG.
  • Bookmarks: press F to flag selected rows; Records → "Show flagged only" to focus on them. Search remembers terms (dropdown + inline autocomplete). Settings → History clears search history / saved graphs / recent files.
  • Browsing/filtering/summarising run off a compact in-memory index — node-logs are parsed only for the detail view and graphing, so it stays fast. Very large files switch to a memory-mapped mode.
